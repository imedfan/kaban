# Kaban: рабочий план фронтенда

Основной путь — нативный SwiftUI, BoardStore и существующий типизированный KabanClient.
Состояние реализации — [current-state](current-state.md). Kaban — основной проект;
старые ограничения роли team2 не действуют. Работа над дизайном определяется текущим поручением.

Полная рабочая очередь — [Frontend MVP FE-01–22](development/frontend-mvp-tasks.md):
шесть функциональных блоков без календарных сроков. По поручению Артёма она
планируется для полностью завершённого BE-01–20. Фактическая готовность main/PR
проверяется отдельно по current-state; план не сокращает требования до текущего кода.

## Ближайший инкремент UI

1. Выбрать пользовательский сценарий и соответствующие закреплённые макеты.
2. Реализовать нативные компоненты через текущие BoardStore/BoardProjection/DTO.
   Перенос из экспериментальной UI-ветки не должен переносить отдельный ReferenceDemo-автомат.
3. Проверить commands/events, ошибки, pending state, длинный текст и неизвестные поля.
4. Собрать App и проверить настоящее WindowGroup в двух темах и минимальном размере.
5. Сопоставить изменённые экраны с макетами и записать конкретные оставшиеся расхождения.

Макеты HTML/CSS используются как исходники дизайна; основной runtime — SwiftUI.
Экспорт галереи подтверждает её композицию, но не основное окно с NativeShell,
toolbar, safe areas, inspector и действиями. Проверка основного окна обязательна.

## Интеграция после UI

XPC adapter подключается к существующему KabanClient: snapshot/subscription handshake,
seq/resync/reconnect и повтор commandId. Backend должен реализовать соответствующие
wire-команды до включения реальных действий. UI не рассчитывает WIP, git-policy,
переходы автомата или валидность pipeline за демон.

Далее — живой лог, полные Human Review/settings/quota flows, MenuBarExtra,
уведомления и доступностная/нагрузочная приёмка. Точный объём определяется задачей;
один mock-экран не означает готовность всего фронтенда.
