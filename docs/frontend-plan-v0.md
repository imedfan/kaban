## 1. Проект Xcode и модули

| Таргет / модуль | Что внутри | Зависит от |

| `KabanAppTests` / `KabanUITests` | Swift Testing для сторов и проекции, XCUITest по UC | — |

- Из общего пакета приложение берёт `KabanProtocol` и `KabanKit`. В ядре уже есть валидатор пайплайна, расчёт итоговой git-политики стадии и генератор маскота (в арх. §2 — модуль `KabanModel`), поэтому UI и демон считают это одним кодом. GRDB в приложение не линкуется.
- **Работа на Linux (F1, вместе с бэком M1).** Один SwiftPM-пакет `/workspace/kaban/code/` (один `Package.swift`) с модулями `KabanProtocol` (пишет Архитектор, первым), `KabanKit` и `KabanBoardCore`. Swift toolchain ставится один раз в общий путь на общем компьютере и общий для всех агентов; свой toolchain фронт не ставит. `KabanBoardCore` зависит от `KabanProtocol` и `KabanKit`; фронт пишет в пакете только `KabanBoardCore` и его тесты (`swift build`, `swift test` в `/workspace/kaban/code/`): проекция, `BoardSet`, правила drop, вывод вида карточки, фикстуры раздела 8. Пока первая версия `KabanProtocol` не залита, на Linux пишем только то, что от неё не зависит (`BoardSet`, правила drop на своих типах); проекция и фикстуры — после неё. `KabanClient`, `KabanUI` и само приложение — только macOS, собираются на `mbp` и подключают пакет локальной зависимостью.
- **Сторонних зависимостей в приложении нет.** Markdown — `AttributedString(markdown:)`, лог — `NSTextView`, drag — `Transferable`, анимация — `symbolEffect`. Единственный кандидат — сериализатор YAML (`Yams`) в `KabanModel`: приложение само пишет `pipeline.yaml` (арх. §3.1). Риск: при перезаписи теряются комментарии (спайк FS-8).

## 2. Слой состояния

**Сторы** (`@Observable`, `@MainActor`, через `.environment`):
- `ConnectionStore` — состояние XPC (`connecting / live / catchingUp / resyncing / daemonUnavailable / needsApproval`), `lastSeq`, статус `SMAppService`.
- `BoardStore` — проекты, пайплайны, задачи. Каждая задача — отдельный `@Observable TaskModel` (`stageId`, `status`, `reason`, `bounceByReason`, попытка в текущем заходе в стадию, счётчик автозапусков к `max_runs_per_task`, последнее `report_progress`, бейджи), столбцы держат массивы id: событие по задаче перерисовывает одну карточку.
- `SchedulerStore` — эфемерные `schedulerFlags` из таблицы §3.2: флаги Мака (`paused`, `rate_limited` со временем окончания, `usage_exhausted · unknown` с датой сброса, `runner_unavailable` с причиной), флаги пулов (`usage_exhausted · cm` / `om` с датой сброса) и проектов (`paused`, `intake_paused`, `unavailable`, в том числе `mcp_unexpected`, `merge_blocked`); флаги моделей `model_flag` (`modelFlags` в снимке, `modelFlagsChanged`); состояние квоты Cm/Om, если опция включена (`quota?` в снимке, `quotaUpdated { cm?, om?, billingCycleStart?, billingCycleEnd?, fetchedAt }`, `nil` — «нет данных», а не 0%); результат проверки раннера; слоты `n/max_concurrent_runs`; прогресс runs.
- `TaskDetailStore` (на открытую задачу) — `getTaskDetail(taskId)` → `{ seq, task, feed, runs, artifacts, gitGrants, gitDenials, humanRequests }` из долговечных таблиц (лента живёт столько же, сколько задача). Дальше применяем события этой задачи с `seq` больше полученного; события, пришедшие до ответа, буферизуем. Плюс `LogStore` с `tailLog`.
- `PipelineEditorStore` (на окно проекта) — черновик (живёт только в редакторе до «Сохранить»), `ValidationIssue[]` с `severity: error | warning`, текущая версия, флаг «есть незакоммиченные правки».
- `ModelCatalogStore` — `model_catalog` (вывод `cursor-agent --list-models`, значок «проверь пул») и `model_pool_rule` (префиксы → Cm/Om, исключения); `listModels()` (без `forbidden`), обновление по `modelCatalogChanged`; источник для выбора модели и таблицы пулов.
- `BoardSetStore` — какие проекты на доске и в каком порядке: упорядоченный список `projectId` в настройках приложения (`UserDefaults` / `@AppStorage`), не в демоне, потому что это только вид (арх. v0.10.2 §5, §11). Логика — чистый `BoardSet` в `KabanBoardCore` с тестами на Linux: `add(_:at:)` (повторное добавление не дублирует), `remove(_:)`, `move(_:to:)`, `prune(existing:)` — чистка id удалённых проектов (после события об удалении проекта и при старте по снимку). Новый проект (журнальное событие о добавлении проекта, `projectAdded`, имя — вопрос 5) встаёт в конец. Набор переживает перезапуск. Рядом в `UserDefaults` — вид (дорожки / компактный) и свёрнутые дорожки. При первом запуске без сохранённого набора на доску попадают все проекты **(предложение фронта, вопрос 6)**.
- `PendingCommands` — `commandId → (задача, действие, время)`.

**Синхронизация (арх. §5).**
1. Старт: `getSnapshot()` → `{ seq, projects, pipelines, tasks, schedulerFlags, modelFlags, quota?, openIncidentCount }` (карточки без лент), затем `subscribe(fromSeq: seq)`. XPC-контракт не меняется (арх. v0.10.2 §5, §11): приложение подписывается на **все** проекты — `getSnapshot` и поток событий с `projectIds = nil` — и само фильтрует, какие дорожки показать, по `BoardSetStore`. Так у скрытых проектов в сайдбаре остаются значки `waiting_human` и инцидентов, а счётчики (`openIncidentCount`, «Ждут человека», менюбар) считаются по всем проектам, а не только по доске.
2. Разрыв (рестарт демона, сон Мака): переподключение с backoff 0.5 → 1 → 2 → 5 с, затем `subscribe(fromSeq: lastSeq)`. Эфемерные значения после разрыва берём из свежего `getSnapshot`, из него используем только `schedulerFlags`, `modelFlags` и `quota` (арх. §5: эфемерное приходит текущим значением в снимке) **(прочтение фронта)**. На `resyncRequired` (журнал обрезан) применяем снимок целиком и перечитываем `getTaskDetail` открытой панели. Пока идёт догонка, в шапке полоса «Синхронизация…», командные кнопки выключены.
3. Журнальные события (задачи, проекты, настройки, версии пайплайна, инциденты, вопросы и ответы, `gitDenied`, `gitGrantCreated` / `Delivered` / `Consumed` / `Revoked` / `Expired`, `gitPolicyUpdated`) применяем к проекции. Догонку применяем к копии вне main actor и подменяем одним присваиванием, живые события сливаем ≤ 30 Гц.
4. Эфемерные события (`schedulerFlagsChanged`, `modelFlagsChanged`, `quotaUpdated`, `modelCatalogChanged`, результат проверки раннера, результат проверки ручной правки пайплайна, прогресс run) просто заменяют текущее значение в `SchedulerStore` / `ModelCatalogStore` / `PipelineEditorStore`.

**Ожидаем демона, без оптимистичных переходов.** Каждая команда несёт `commandId`. Ответ возвращает `commandId` и `seq` порождённого события.
- Карточка или кнопка переходит в «отправлено» (приглушена, спиннер, действия выключены), пока не придёт событие с этим `commandId` (или `lastSeq ≥ seq` из ответа).
- Отказ автомата → карточка остаётся на месте, сообщение во всплывающей подсказке. Нет ответа 5 с → «демон не отвечает».
- При drag призрак карточки стоит в целевом столбце в состоянии «отправлено».
- Мгновенно: набор и порядок дорожек, вид, сворачивание, выбор, черновики форм.

## 3. Экраны и ключевые компоненты

Общего «Журнала» в MVP нет: историю показывает лента задачи. Каркас по макету `01-board`: `NavigationSplitView` (сайдбар: Доска / Ждут человека / Инциденты со счётчиком (F22), список проектов с маскотом и значками «ждёт человека» / инцидент, откуда проект перетаскивают на доску (3.10), блок «Этот Мак» с потолком процессов, весами и полосами квоты Cm/Om, 3.13) | доска | `.inspector` с панелью задачи.

Liquid Glass: `.glassEffect()` на шапках столбцов (один `GlassEffectContainer` на дорожку), системный тулбар, панель задачи. Карточки сплошные (`--bg-card`, радиус 10).

**3.1 Флаги планировщика — в шапках (арх. §3.2).** Задачи под флагом остаются `queued` и выглядят как обычная очередь. Исключение по журналу решений: задача, которая ждёт квоту, стоит в `queued` **с причиной**, и карточка показывает её спокойной серой строкой (3.4). Красный цвет — только для инцидентов безопасности; флаги доступности и моделей — янтарные.

| Флаг · причина | Где | Текст и действие |
|---|---|---|
| Мак `paused` · `manual` | `SchedulerBanner` над доской | «Все запуски на паузе», «Продолжить» → `resumeAll` |
| Мак `rate_limited` | `SchedulerBanner` | «Лимит Cursor, возобновление в 16:40», «Снять сейчас» → `resumeAfterRateLimit` |
| Пул `usage_exhausted` · `cm` / `om` | `PoolBanner` над доской, тонкий, по одному на пул (янтарный); метка на шапках столбцов, чьи стадии на моделях этого пула | «Om исчерпан до 14.08 · N стадий» (спека UC-09 б; до `billingCycleEnd` или даты из текста ошибки); встают только стадии этого пула, остальные работают; «Сменить модель» (явная модель из другого пула, 3.8) |
| Мак `usage_exhausted` · `unknown` (пул не определить) | `SchedulerBanner` (янтарный), весь Мак | «Квота Cursor исчерпана до 14.08» (спека UC-09 б); дата неизвестна — «Сброс неизвестен, проверка раз в 6 ч» |
| Мак `runner_unavailable` · `agent_missing` / `agent_not_runnable` / `agent_not_logged_in` / `runner_auth` | `SchedulerBanner` (янтарный) | «Cursor недоступен: не найден / не запускается / не выполнен вход / ошибка авторизации», «Проверить снова» → `recheck(.runner)`; подсказка «выполните `cursor-agent login` в Терминале» |
| Модель `model_flag` · `unavailable` | `ModelBanner` над доской, по одному на модель; метка на шапках столбцов с этой моделью | «Opus недоступен · N стадий» (пропал из `--list-models` или `resource_exhausted`), «Сменить модель»; снимается пробой, появлением в каталоге или `clearModelFlag` |
| Модель `model_flag` · `substituted` | `ModelBanner`, по одному на модель | «Cursor подменяет <модель> · N стадий» (считаем стадии, как у пулов и `unavailable`), «Сменить модель» (тот же список, что в редакторе, 3.8), «Снять флаг» (`clearModelFlag`) |
| Проект `paused` · `manual` | `LaneHeader` | «Проект на паузе», «Продолжить» → `resumeProject` |
| Проект `intake_paused` · `max_waiting_human` | `LaneHeader` | «3/3 ждут человека — новые задачи из Backlog не берутся» |
| Проект `unavailable` · `project_missing` / `no_pipeline` / `pipeline_invalid` | `LaneHeader` | «Папка не найдена» («Указать путь» → `relinkProject`, «Удалить» → `removeProject`), «Нет пайплайна» («Создать шаблон…»: UI пишет шаблон и вызывает `updatePipeline`), «Пайплайн невалиден» (список `ValidationIssue`, «Открыть настройки»); если не хватает моделей — янтарная плашка «Пайплайн не запустится: нет модели у Dev, Test» с кнопкой «Указать модели» (редактор на первой стадии с ошибкой) и меткой на шапках этих столбцов; задачи в Backlog создавать можно; везде «Проверить снова» → `recheck(.project(id))` |
| Проект `unavailable` · `mcp_unexpected` | `LaneHeader` (янтарный) | «Запуск не стартовал: CLI видит лишний MCP-сервер «<имя>»», «Открыть MCP» (3.9), «Проверить снова» |
| Проект `merge_blocked` · `main_dirty` | `LaneHeader` + карточка головы очереди | «Слияние ждёт: в `main` есть ваши правки, пересекающиеся с входящими» |

`LaneHeader` есть у каждой дорожки, даже если на доске один проект: в нём крестик «Убрать с доски» (3.10). Несколько флагов одновременно — один баннер со списком, порядок: `runner_unavailable` > `usage_exhausted · unknown` > `rate_limited` > `paused`, баннеры пулов и моделей — отдельными тонкими строками ниже **(предложение фронта)**.

**3.2 Дорожка проекта.** `BoardView` — горизонтальный `ScrollView` из `StageColumnView` с `LazyVStack`. `StageColumnHeader` (glass): иконка, имя, WIP «4/3» (UC-13), свёрнутость по `display.collapsed`. `kind: gate` — тонкая `GateStripView` со счётчиком, раскрывается по клику. Стадии с `hidden` не рисуются, их задачи доступны через фильтр «скрытые стадии» **(предложение фронта)**.

**3.3 Дорожки и компактный вид.**
- `SwimlanesView`: `LazyVStack(pinnedViews: .sectionHeaders)`, `Section` на проект, закреплённый `LaneHeader` (маскот, ветка, вес, процессы, паузы, сворачивание, кнопка настроек и сразу после неё крестик «Убрать с доски»). Дорожки идут в порядке `BoardSetStore`. Внутри дорожки свой горизонтальный скролл. Высота ограничена, столбцы прокручиваются внутри; свёрнутая дорожка — одна строка сводки **(предложение фронта)**.
- `KindGroupedBoardView` (по проектам с доски): очередь / в работе агентов / ждёт человека / слияние / готово. На карточке `StageChip` с исходной стадией. Любая `waiting_human` (включая `review`) попадает в «ждёт человека» (арх. §11).
- Общие столбцы без дорожек — только при совпадении `id` стадий.

| `waiting_human` · `retries_exhausted` | «Попытки исчерпаны 3/3» | «Перезапустить» (`retryStage`), «Модель» (`setModelOverride`, только явная модель из каталога) |
| `waiting_human` · `run_limit` | «Лимит запусков 12/12» (`max_runs_per_task`, считаются только автоматические запуски, списывающие попытку) | «Замечание агенту», «Перезапустить», «Модель»; любое действие человека обнуляет счётчик |
| `waiting_human` · `model_substituted` | «Подмена: <запрошена> → <ответила>» (янтарный, `--st-waiting`) | «Повторить», «Другая модель», «В Backlog»; результат не принят, попытка не списана |
| `waiting_human` · `bounce_limit` / `conflict_limit` | «Лимит возвратов 3/3» / «Лимит конфликтов 2/2» | «Ещё N попыток» (`retryStage(grantAttempts)`), «Модель» |
| `waiting_human` · `git_denials` | «Политика git: 5 отказов» | «Разрешения…», «Политика…» |
| `waiting_human` · `invalid_result` | «Read-only стадия изменила файлы» | «Перезапустить», «Модель» |
| `waiting_human` · `incident` | «Инцидент · refs откатаны» (заливка `--st-incident`) | красная рамка на всю карточку поверх всех бейджей |
| `paused` | «Пауза» (`--st-paused`) | «Продолжить» (`resumeTask`) |
| `blocked` · `main_dirty` | «main грязная» (`--st-blocked`), только у головы очереди слияния | подсказка с пересекающимися файлами; повтор сам; флаг `merge_blocked` в `LaneHeader` |
| `done` / `cancelled` | «Готово 14:05 → main» (`--st-done`) / «Отменена» (`--st-cancelled`), заголовок зачёркнут | — |

**Бейджи (не статусы):** возвраты по причинам из `bounceByReason` («↩ Test→Dev 2/3», конфликт «1/2» в `--st-conflict`), пересечение файлов (подсказка: с какими задачами), неиспользованное git-разрешение (ключ, `--pol-cond`), переопределённая модель. Порядок по `02-cards`: видно два бейджа, остальное «+N»; приоритет: git-разрешение > возвраты и конфликт > пересечение > модель и прочее.

Контекстное меню карточки дублирует drag для клавиатуры и VoiceOver: «Переместить в ▸» (`moveTask`), «Приоритет ▸» (`setPriority`), «Пауза» (`pauseTask`), «Отменить…» (`cancelTask`, диалог с «Сохранить ветку»).

**3.5 Панель задачи** (`TaskInspector`, glass, по `03-task-details`; данные из `getTaskDetail`).
- Шапка: чип статуса с причиной, «попытка 2 из 3», ветка, модель, путь стадий, «Открыть в Cursor», меню «…» (правка `editTask` в `queued` / `waiting_human` / `paused`, иначе «Поставить на паузу, чтобы править», UC-02; приоритет, отмена).
- Над вкладками блок решения для `waiting_human`: инцидент (`IncidentRow`), вопрос, лимиты, подмена модели.
- `ModelSubstitutionBlock` (`model_substituted`): рядом два блока «Запрошена» и «Ответила» (имя и id; `actual` заполнен только при `substituted`, поэтому у пропавшей модели (`unavailable`) блока «Ответила» нет ни на карточке, ни в баннере, ни в панели), под ними `fallbackModel`, если был, время, номер run, ссылка на лог; кнопки «Повторить» (`retryStage`), «Другая модель» (выбор из 3.8 → `setModelOverride`), «В Backlog» (`moveTask`).
- Инструменты доски в UI: `report_progress` — строка «последнее действие» на карточке и записи ленты; `request_human` — вопрос в блоке решения с полем ответа (`answerHuman`); `return_to_stage` — счётчик «↩ 2/3» на карточке и список замечаний в ленте; `complete_stage` — резюме стадии в «Сводке» и ленте. `get_task_context` в UI не виден.
- Вкладки: **Лента** (`task_feed_item`: переходы, `report_progress`, замечания, гейты, отказы и разрешения git, инциденты, серая строка `model_unconfirmed` — фактическую модель подтвердить не удалось, задача идёт дальше), **Живой лог**, **Сводка** (Human Review, 3.7), **Попытки** (`runs`: стадия, номер попытки в заходе, модель запрошенная и фактическая, длительность, `end_reason`, usage, `refs/kaban/wip/<run-id>` после краша или зависания; запуски без списания попытки помечены; в шапке вкладки «автозапусков 7 из 12» **(предложение фронта)**), **Разрешения git** (`gitGrants`, состояния 3.6).
- Внизу поле «Замечание агенту или ответ…» (F23, UC-06): из `waiting_human` с любой причиной отправляет `answerHuman(taskId, text, requestId?)` (`requestId` — только для `question`), задача встаёт в очередь своей стадии и продолжает сессию с текстом. При `retries_exhausted` / `bounce_limit` / `conflict_limit` под полем подсказка «Добавит одну попытку»; при `run_limit` — «Обнулит счётчик запусков». В `review` то же поле служит комментарием к «Вернуть с комментарием» (3.7) **(предложение фронта)**. В `running` / `gating` поле выключено с подсказкой «Поставьте на паузу».

Быстрые действия по строке таблицы 3.4: «Перезапустить» (`retryStage`), «Модель», «В Backlog» (`moveTask`), «Отменить» → `cancelTask(taskId, keepBranch)`. Диалог отмены везде одинаковый: галочка «Сохранить ветку» (по умолчанию выключена) с подписью «сохранится как `kaban/archive/<task-id>`».

**Раздел «Инциденты» (F22).** `IncidentsView` в сайдбаре: список по всем проектам (маскот, задача, что изменилось, run, время), сверху неразобранные. Счётчик = `openIncidentCount` из снимка (арх. v0.9): любое действие человека по задаче выводит её из этого статуса, инцидент считается разобранным и уходит из счётчика, но остаётся в списке как история с подписью выбранного действия. Клик открывает панель задачи. Список берём командой `listIncidents(projectIds: nil, state)` — по всем проектам, включая скрытые с доски, — из таблицы `incident`.
- `IncidentRow`: что изменилось, в каком run, ссылка на лог. Действия UC-18.4: вернуть на стадию с замечанием (`requestChanges`), модель, «Ужесточить политику…», отменить.
- **Живой лог:** `LogTextView: NSViewRepresentable` (NSTextView, TextKit 2, только чтение, `usesFindBar`). `tailLog(runId, fromOffset)` отдаёт разобранные `AgentEvent` батчами раз в 100–250 мс, дописываем одним `beginEditing/endEditing`; рендер по типу (сообщение, свёрнутый tool call, результат, ошибка, usage). Автопрокрутка только внизу, до ~50 тыс. строк в памяти, раньше — «Загрузить ранее» по смещению; «Открыть сырой лог» — JSONL по пути из run. Подписка, пока вкладка видна.

**3.6 «Разрешить один раз» (UC-17, арх. §8.3).** Отказ — тихая строка ленты `GitDenialRow`: команда, стадия, run, сработавшее правило, время. Кнопки видит только человек, агент ленту не читает.

| Состояние строки | Что видно | Событие |
|---|---|---|
| Отказ, жёсткое правило | замок + «Не настраивается: push делает только Kaban», кнопок нет | `gitDenied` (`rule` — жёсткий инвариант) |
| Отказ, настраиваемое правило | «Разрешить один раз», «Добавить в политику…» | `gitDenied { denialId, runId, argv, rule }` |
| Отправлено | кнопка → спиннер «Выдаём разрешение…» | ответ на `allowGitOnce(denialId)` с `commandId` |
| Создано, ждёт доставки | ключ, «Разрешено один раз · агент узнает при следующем вызове инструмента доски» (run жив) или «…уйдёт в промпт следующего запуска стадии Dev» (run завершён), «Отозвать» (`revokeGitGrant`); бейдж ключа на карточке | `gitGrantCreated { grantId, denialId, argv, by }` |
| Доставлено агенту | «Доставлено агенту 14:27 · в ответе инструмента» / «· в промпте run #4», «Отозвать» | `gitGrantDelivered { grantId, runId, via: mcp_response \| next_prompt }` |
| Использовано | серая галочка «Использовано 14:41 · run #3», бейдж снимается | `gitGrantConsumed { grantId, runId }` |
| Отозвано | «Отозвано вами 14:50» | `gitGrantRevoked { grantId, by }` |
| Истекло | «Не использовано: задача завершена / отменена» | `gitGrantExpired { grantId, reason }` |

В ленте это одна строка с цепочкой «создано → доставлено агенту → списано» (или «отозвано» / «истекло»), где каждый шаг ставит своё время. Повтор команды без разрешения даёт новую строку. Пять отказов за run → `waiting_human · git_denials`: можно выдать несколько разрешений и нажать «Перезапустить стадию».

**«Добавить в политику…»** открывает раздел Git (3.9) в режиме предпросмотра: правило из отказа уже добавлено, выбирается уровень «Проект / Стадия Dev». «Сохранить» → `addDenialToPolicy(denialId, scope: .project | .stage(id))` → новая версия или `ValidationIssue`. По `gitPolicyUpdated { projectId, scope, pipelineVersion }` строка отказа показывает «Добавлено в политику проекта · версия abc123». Действует с новых runs.

**3.7 Human Review** (`ReviewView`, вкладка «Сводка» панели по `03-task-details`): резюме стадий, `DiffstatTable` (файл, +/−, полоска), коммиты, гейты (раскрываемый вывод), время и стоимость, блок «изменено при разрешении конфликта». Кнопки: «Открыть в Cursor» (`cursor <путь клона>`, запасной путь `NSWorkspace` по bundle id); «Одобрить» ⌘↩ (`approve`); «Вернуть с комментарием» — комментарий (поле внизу панели) и стадия, по умолчанию первая агентская (`requestChanges(comments, target)`); «Отклонить» — «Отменить задачу» (галочка «Сохранить ветку», по умолчанию выключена) или «Вернуть в стадию ▸» без комментария → `reject(taskId, target, keepBranch)`, где `keepBranch` учитывается только при `target = cancel`.

**3.8 Настройки пайплайна и стадии.** Окно проекта → «Пайплайн»: список стадий с перестановкой, добавлением и удалением.
- Удаление стадии, где есть задачи в нетерминальном статусе, выключено с подсказкой «сначала перенесите N задач» (UC-13); валидатор демона отклонит его в любом случае.
- `StageEditorForm` — секции по таблице 1.5 спеки, неприменимые к `kind` скрыты. Отображение: имя, иконка, цвет, порядок, свёрнут, скрыт.
- `ModelPicker` у agent-стадии **обязателен**: список из `model_catalog` **без Auto**, сгруппирован по семействам, у каждой модели чип пула Cm/Om, у новой — «проверь пул». Модели по умолчанию нет. Кнопки «Переключить на Auto» и галочки автоподмены нет. Модель, пропавшая из `--list-models`, помечена `model_unavailable` (в протоколе — `model_flag · unavailable`), выбрать её нельзя.
- `StageMcpPicker` (`agent.mcp`, спека 1.5, UC-24): сервер доски отмечен всегда и не снимается, остальные выбираются только из белого списка проекта (вкладка «MCP», 3.9); по умолчанию у стадии только сервер доски. Сервер, выбранный у стадии, но выключенный в белом списке, — **предупреждение** валидатора (`ValidationIssue.severity = warning`, арх. §9), не ошибка: янтарная подсветка строки «Выключен в MCP проекта — не подключится», пайплайн остаётся валидным, «Сохранить» не блокируется, демон просто не кладёт сервер в конфиг запуска; ссылка «Открыть MCP проекта».

Сохранение (арх. §3.1, журнал решений):
1. Черновик живёт только в редакторе. Пока пользователь правит, проверка общим валидатором `KabanModel` и `validatePipeline(projectId, content)` с задержкой 300 мс; `ValidationIssue.path` подсвечивает поле, цвет по `severity`: `error` — красная обводка поля, `warning` — янтарная. **«Сохранить» выключена, пока есть ошибки** (`severity = error`, включая agent-стадию без модели или с `auto`); предупреждения сохранению не мешают и показываются в списке над кнопкой.
2. «Сохранить» → атомарная запись файла + `updatePipeline(projectId, contentHash)`; список `ValidationIssue` из ответа — вторая проверка. Некорректная версия в `main` не попадает. Если демон отклонил версию, черновик остаётся в редакторе с ошибками, а файл на диске возвращаем к прежнему содержимому **(предложение фронта)**.
3. Ручная правка файла приходит эфемерным состоянием: баннер «Есть незакоммиченные правки пайплайна» с результатом проверки и кнопкой «Применить».

Если файл изменился на диске при открытом черновике — «Перезагрузить / Перезаписать» **(предложение фронта)**.

**3.9 Настройки проекта и git-политика.** Разделы:
- Общее: путь, `relinkProject`, базовая ветка, вес и личный максимум (`setProjectWeight`), маскот (`setMascot`), пауза.
- Рабочая копия: `warm_paths`, `on_create`.
- **MCP** (`listProjectMcpServers`, `setProjectMcpAllowlist`): список серверов проекта из `.cursor/mcp.json` и личных серверов Артёма из `~/.cursor/mcp.json`, у каждого переключатель, **по умолчанию выключен** (allowlist). Сервер доски `kaban` всегда включён, переключатель заблокирован с подписью «нужен Kaban». Подпись внизу: «Конфиг MCP Kaban собирает сам на каждый запуск; лишний сервер в CLI — запуск не стартует». Если поднят `mcp_unexpected`, сверху строка «CLI видит сервер «<имя>» вне конфига Kaban». У выключаемого сервера, выбранного в стадиях, подпись «выбран в стадиях: Dev, Test» **(предложение фронта)**.
- Git, по раскладке, подтверждённой дизайнером:
  - `GitPresetPicker` (Строгий / Стандартный / Свободный), у «Свободного» постоянная подпись: песочница и проверка результата работают всегда;
  - `GitCommandTable` (`Table`): команда, разрешено / запрещено, маркер «из пресета / переопределено»; жёсткие правила — строки с замком;
  - уровень «Проект / стадия ▸»: на стадии маркеры «унаследовано / переопределено», сужение или расширение по условию;
  - `EffectivePolicyView` — итоговая политика каждой стадии через общую функцию из `KabanModel`.

Глобальные настройки Мака (`Settings`): `setMaxConcurrentRuns`, путь к `cursor-agent`, уведомления о ревью (по умолчанию включены, спека UC-07; значение хранит приложение), вкладка «Квота Cursor» (3.13).

**3.10 Добавление проекта и набор проектов на доске** (журнал решений от 4 октября, арх. v0.10.2 §11).
- `AddProjectFlow`: `fileImporter` → `addProject(path, createTemplate)` с галочкой «создать шаблон и закоммитить» (включена) → ветка (`listBranches`) → гейты (`detectGates`, можно править) → `checkEnvironment`. Чистая копия не нужна. «Не git-репозиторий» — ошибка в листе. Галочку шаблона сняли — проект добавлен с флагом `unavailable: no_pipeline`. `cursor-agent` не готов — проект добавлен, над доской баннер `runner_unavailable` (UC-20). Добавленный проект сразу появляется на доске последней дорожкой.
- Переключателя «Один / Несколько / Все» нет, `ProjectScopePicker` убран целиком. Проект попадает на доску перетаскиванием из списка проектов в сайдбаре в область канбана; тем же перетаскиванием (за `LaneHeader`) меняется порядок дорожек.
- Drag-and-drop проектов: `ProjectDragItem: Transferable` с `projectId` (свой UTType `app.kaban.project-ref`, отдельно от `app.kaban.task-ref`, чтобы карточку нельзя было бросить между дорожками) **(UTType — предложение фронта)**; зоны сброса между дорожками, перед первой и после последней; индикатор вставки — линия между дорожками; проект, уже стоящий на доске, при сбросе переезжает, а не дублируется. Итог — `BoardSetStore.add(at:)` / `move`.
- Крестик «Убрать с доски» в `LaneHeader` справа, сразу после кнопки настроек: `BoardSetStore.remove`. Только скрывает дорожку: проект не удаляется и не ставится на паузу, задачи продолжают выполняться, команд демону нет.
- Пустая доска (в наборе ни одного проекта) — `EmptyBoardView` с подсказкой «Перетащите проект сюда»; вся область — зона сброса.
- Скрытый проект в сайдбаре остаётся со значками `waiting_human` и инцидента; раздел «Ждут человека», «Инциденты», менюбар и уведомления охватывают все проекты.
- Доступность: перетаскивание дублируется пунктами контекстного меню проекта в сайдбаре «Показать на доске» / «Скрыть с доски» (VoiceOver, клавиатура). ⌘1–⌘9 прокручивают доску к N-й дорожке и ставят на неё фокус; ⌘⌥← / ⌘⌥→ сдвигают дорожку в фокусе без мыши (`BoardSetStore.move`). Всё это есть пунктами меню «Вид».

События старше 10 минут после догонки собираются в одну сводку **(предложение фронта)**.

**3.13 Квота Cursor (опция «неофициально», по умолчанию выключена).**
- `QuotaBars` в менюбаре и блоке «Этот Мак»: две полосы — **Cm** (модели Cursor, `composer-*`, `autoPercentUsed`) и **Om** (именные модели, `apiPercentUsed`). Полосы Gb нет. У каждой полосы метка прошедшей доли цикла и метка порога; подпись — обратный отсчёт до сброса по `billingCycleEnd` («сброс через 9 д»). Доля цикла считается от `billingCycleStart`; если его нет в ответе (проверяется в спайке 1), начало цикла считается календарно — тот же день месяцем раньше от `billingCycleEnd` (не «минус 30 дней»); метка доли цикла использует этот запасной расчёт. `billingCycleEnd` демон разбирает из строки с миллисекундами эпохи, UI получает `Date`. Исчерпанный пул (`usage_exhausted · cm` / `om`) — полоса заполнена, подпись «исчерпан».
- **Нет данных ≠ 0%.** Если в `quotaUpdated` процент пула `nil` (в том числе когда Cursor ответил `"enabled": false`), полоса — серая заглушка с подписью «нет данных», не пустая и не полная; без метки порога. Нет `billingCycleEnd` — нет отсчёта и метки доли цикла. Если данным больше 30 минут, полосы тоже серые с подписью «нет свежих данных — работает реактивная схема».
- Экран Мака «Квота Cursor»:
  - блок согласия (`setQuotaOptions(enabled, consent, pollInterval, thresholdCm, thresholdOm)`): включается явно, с пометкой «неофициально»; текст объясняет, что токен читается только для чтения (из `state.vscdb` Cursor IDE или токен CLI), живёт только в памяти, не обновляется, а запрос идёт только к `api2.cursor.sh` `GetCurrentPeriodUsage`;
  - интервал опроса: 1 / 5 / 15 / 30 мин или своё значение (перед каждым стартом запуска демон и так берёт данные не старше 60 с);
  - пороги Cm и Om отдельно, по умолчанию 10% (демон закладывает запас на идущие запуски);
  - таблица «модель → пул»: правила по префиксу и исключения (`setModelPoolRule` / `removeModelPoolRule`), свёрнуто по семействам, значок «проверь пул» (`needs_review`) у новых моделей и фильтр по нему, кнопка «Обновить список» (`refreshModelCatalog`).
- Если чтение `state.vscdb` из-под LaunchAgent вызывает системный запрос, базу читает приложение и передаёт демону проценты (арх. §7, спайк 1); тогда в приложении появляется маленький читатель квоты без записи и без хранения токена.
- Om ниже порога при остатке в Cm — встают только стадии на именных моделях; их задачи показывают серую причину на карточке (3.4).
- Пробные запуски после молчаливого выхода без вызовов инструментов (один на модель за раз, не чаще раза в 10 минут; при неизвестной дате сброса — раз в 6 часов) попытку не списывают; карточка в это время в `retry_wait: silent_exit` (3.4).

**Маскот** (`MascotView`, генератор из `KabanModel`). `.breathe` — спит, `.pulse` — агенты работают, `.wiggle` — ждёт человека, `.bounce` — однократно на Done; «тревожится» при инциденте (UC-16.3) готового эффекта не имеет — предлагаю красный бейдж с `.pulse` и красное кольцо, как на макете **(предложение фронта)**. Приоритет: тревога > ждёт > работает > Done > спит. Анимация только в сайдбаре и шапке дорожки, на карточке статичная наклейка. С Reduce Motion всё статично. Эмодзи анимируются через `keyframeAnimator` (FS-5).

**Drag-and-drop.** `TaskDragItem: Transferable` (UTType `app.kaban.task-ref`), `.draggable` / `.dropDestination`. `canDrop` в `KabanBoardCore` проверяет правила UC-11, итог — `moveTask(stage)`: назад — с подтверждением «Прервать текущий запуск? Попытка не спишется»; вперёд — запрещено, кроме Backlog → первая стадия при наличии критериев приёмки; между проектами — нельзя. Перетаскивание самих проектов — в 3.10.

| Что | Где | Значения и поля |
|---|---|---|

| Квота | `quota?` в снимке, `quotaUpdated` | `{ cm?, om?, billingCycleStart?, billingCycleEnd?, fetchedAt }`: проценты и даты необязательны, `nil` — «нет данных», а не 0% (так же при `"enabled": false` в ответе Cursor); даты приходят как `Date` (демон разбирает `billingCycleEnd` из строки с миллисекундами эпохи); без `billingCycleStart` начало цикла — тот же день месяцем раньше; старше 30 мин — «нет свежих данных» |

| Модели | `listModels`, `refreshModelCatalog`, `setModelPoolRule` / `removeModelPoolRule`, `clearModelFlag`, `modelCatalogChanged` | `id`, `name`, `pool`, `needs_review`; `auto` (`forbidden`) в список не попадает |
| Набор проектов на доске | только приложение: `BoardSetStore` в `UserDefaults` | упорядоченный `[projectId]`; команд демону нет; XPC-контракт не меняется: `getSnapshot` / `subscribe` / `listIncidents` вызываются с `projectIds = nil` (параметр остаётся в протоколе необязательным, арх. v0.10.2 §5, §11); новый проект — в конец, удалённый — вычищается |
| MCP | `listProjectMcpServers`, `setProjectMcpAllowlist`; `agent.mcp` стадии | имя сервера, источник `project` / `personal`, вкл/выкл (по умолчанию выкл); `kaban` всегда вкл; стадия выбирает только из белого списка; выбранный у стадии, но выключенный в белом списке сервер — `warning` валидатора, в конфиг запуска не попадает, пайплайн валиден |

Фикстуры: каждая новая строка таблицы 3.4; `usage_exhausted · om` (тонкий баннер «Om исчерпан до 14.08 · N стадий», метки столбцов, задачи с `quota_om`, стадии на `composer-*` работают), `usage_exhausted · cm`, `usage_exhausted · unknown` (глобальный баннер, с датой и без); `model_flag` (`unavailable` без `actual` · N стадий, `substituted` · N стадий); квота без `billingCycleStart` (календарный расчёт начала цикла, включая конец месяца: сброс 31.03 → начало 28/29.02); квота с `cm = nil` / `om = nil` и ответ с `"enabled": false` (серые заглушки «нет данных»); квота без `billingCycleEnd`; стадия с MCP из белого списка и стадия с сервером, выключенным в белом списке (`warning`, янтарная подсветка, «Сохранить» активна); черновик с ошибкой и предупреждением одновременно; плашка «нет модели у <стадии>»; `mcp_unexpected`; полосы квоты в состояниях «норма», «ниже порога», «нет свежих данных», «опция выключена»; каталог с моделью «проверь пул»; три лимитные ошибки — по образцам из спайка 1; набор доски: пустая доска («Перетащите проект сюда»), один проект, несколько в нестандартном порядке, скрытый проект с `waiting_human` и инцидентом (значки в сайдбаре, счётчики по всем), id удалённого проекта в сохранённом наборе (вычищается), только что добавленный проект (встаёт в конец). Паузы ретраев в фикстурах `[30s, 2m]` — предложение журнала, ждёт Артёма.

## 9. Открытые вопросы

5. **Архитектору:** имя журнального события о добавлении и удалении проекта. Арх. §5 перечисляет только «проекты»; план пока зовёт их `projectAdded` / `projectRemoved` — по ним `BoardSetStore` добавляет проект в конец и вычищает удалённый.

Остаются:
- **Журнал против плана v0.4.1 — карточки под флагом.** Журнал: «Задача, которая ждёт квоту, остаётся в `queued` с причиной». План: «Задачи под флагом остаются `queued` и выглядят как обычная очередь». Взят журнал: серая причина на карточке.

- **Договорённости против плана — красный цвет.** Договорённость: красный — только для инцидентов безопасности. В плане v0.4.1 баннер `runner_unavailable` был «(красный)», теперь янтарный.
- **Арх. §2 против договорённости о пакете.** Арх. §2: «Swift-пакет `KabanKit`» с модулями `KabanModel`, `KabanStateMachine`, `KabanProtocol`, `KabanStore`, `KabanScheduler` и другими. Договорённость команды: один пакет `/workspace/kaban/code/` с модулями `KabanProtocol`, `KabanKit` и `KabanBoardCore`; `KabanBoardCore` в арх. §2 нет, а `KabanKit` там имя пакета, а не модуля. План идёт по договорённости и ссылается на `KabanModel` только как на часть ядра; нужен ответ Архитектора, где живут типы и валидатор (`KabanModel`), от которых зависит `KabanBoardCore` (вопрос 7).
