# Kaban — журнал решений

Каждое решение здесь утверждено Артёмом или принято CEO и не отменено Артёмом. Принятые изменения переносятся в текущую архитектуру, спецификацию, документы экранов и при необходимости дизайн. Рабочий вход — [current-state](current-state.md); исторические роли не ограничивают основную разработку.

## 2026-10-03, вечер

### Ретраи и лимиты запусков
- Ретрай — это повтор той же стадии после технического сбоя: краш, зависание, таймаут, `no_final_call`, красный гейт. Возврат — это перенос задачи на более раннюю стадию с замечаниями. Это два разных механизма с разными счётчиками.
- Счётчик попыток живёт в пределах одного захода в стадию и обнуляется после возврата.
- Новое правило `max_runs_per_task: 12`. Считаются только автоматические запуски. Запуски, которые не списывают попытку (rate-limit, разлогин, перезапуск демона, остановка из-за подмены модели), не считаются. Любое действие человека обнуляет счётчик. При превышении задача уходит в `waiting_human: run_limit`.
- Перед откатом клона после краша или зависания грязное состояние сохраняется в `refs/kaban/wip/<run-id>`.
- После `gate_failed` и `no_final_call` следующая попытка продолжает работу в том же клоне, а в промпт добавляется вывод гейта.
- **Утверждено Артёмом (4 октября):** 3 попытки, паузы между ними `[30s, 2m]`.

### Лимиты Cursor
- Причины разделены. `usage_exhausted` имеет причину `cm`, `om` или `unknown`: если известно, какой пул кончился, встают только стадии на моделях этого пула, а весь Мак встаёт только при `unknown`. Флаг держится до `billingCycleEnd` или даты из текста ошибки. `model_unavailable` ставится только на стадии с этой моделью. Короткий `rate_limit` работает как раньше, cooldown 15 → 30 → 60 минут.
- Молчаливый выход агента без вызовов инструментов не списывает попытку. Вместо этого запускается пробный запуск: один на модель за раз и не чаще раза в 10 минут. Если дата сброса неизвестна, проба повторяется раз в 6 часов.
- Чтение квоты — опция, выключенная по умолчанию, включается с явным согласием и помечена как неофициальная. Токен читается только для чтения: из `state.vscdb` Cursor IDE или собственный токен CLI, если он найдётся в спайке 1. Токен живёт только в памяти, демон его никогда не обновляет. Запрос идёт только к `api2.cursor.sh` `GetCurrentPeriodUsage`. Пул Cm — это `autoPercentUsed`, пул Om — `apiPercentUsed`. Сессия браузера и `usage-summary` не используются.
- Интервал опроса настраивается: 1, 5, 15, 30 минут или своё значение. Плюс свежая проверка (данные не старше 60 секунд) перед каждым стартом запуска: при взятии из Backlog, при переходе между стадиями, при ретрае. Если данным больше 30 минут, остаток считается неизвестным и работает реактивная схема.
- Если в ответе нет `billingCycleStart`, начало цикла считается как `billingCycleEnd` минус один месяц, календарно (тот же день прошлого месяца, не 30 дней). `billingCycleEnd` приходит строкой с миллисекундами эпохи.
- Нет процента в ответе или `"enabled": false` означает «нет данных» (`nil`), а не 0%: полоса серая, планировщик не считает квоту полной.
- MCP-сервер выбран в стадии, но выключен в белом списке проекта: демон не кладёт его в конфиг запуска, валидатор даёт предупреждение (не ошибку), пайплайн остаётся валидным.
- Порог задаётся отдельно для Cm и Om, по умолчанию 10%. В порог закладывается запас на идущие запуски: число запусков в пуле × средний расход, а пока истории нет — 2% на запуск.
- Если Om ниже порога, а в Cm ещё есть остаток, встают только стадии на именных моделях. Задача, которая ждёт квоту, остаётся в `queued` с причиной, не держит очередь и не занимает WIP-слот.
- Справочник моделей хранится в локальной базе в двух таблицах. `model_pool_rule`: `composer-*` относится к Cm, остальное к Om, плюс ручные исключения. `model_catalog` повторяет вывод `cursor-agent --list-models`, сверяется при старте и раз в сутки. Новая модель получает значок «проверь пул». Модель, пропавшая из списка, сразу даёт `model_unavailable`.

### Модели
- **Auto запрещён.** У каждой agent-стадии модель указывается явно, демон всегда передаёт `--model <id>`.
- **Моделей по умолчанию нет.** Если хотя бы у одной agent-стадии нет модели или стоит `auto`, весь пайплайн проекта некорректен: ставится флаг `unavailable: pipeline_invalid` и ничего не стартует. Ошибка перечисляет стадии, которым нужна модель. Задачи в Backlog создавать можно.
- «Сохранить» в редакторе неактивна, пока есть ошибки. `updatePipeline` проверяет версию синхронно, некорректная версия не попадает в `main`. Если некорректная версия попала в `main` ручным коммитом, идущие запуски доигрывают, а новые не стартуют.
- Модель меняет только человек и только на явную. Кнопки «на Auto» и автоподмены нет.
- **Подмена модели Cursor.** Демон сверяет название модели из `system/init` в stream-json с названием из `model_catalog`. Если названия не совпали, процесс останавливается сразу, задача уходит в `waiting_human: model_substituted`, результат не принимается, попытка не списывается, а на модель ставится флаг `model_flag { modelId, reason, requested, actual, fallbackModel? }`. Поле `actual` необязательное: при `unavailable` его нет. Пользователю явно показываем, какая модель запрошена, какая ответила и было ли `fallbackModel`. Если название не нашлось или неоднозначно, в ленту пишется серая строка `model_unconfirmed`, и задача идёт дальше.

### MCP (одобрено Артёмом)
- Пять инструментов доски (F5): `get_task_context`, `report_progress`, `complete_stage`, `return_to_stage`, `request_human`.
- По умолчанию агенту доступен только MCP-сервер доски. MCP проекта и личные MCP включаются явным списком в настройках проекта, а стадия может только выбрать из этого списка.
- Конфиг MCP демон собирает сам на каждый запуск и перед проверкой результата возвращает `.cursor/mcp.json` из `main`. Токен передаётся только через переменную окружения `${env:KABAN_RUN_TOKEN}`.
- Если перед стартом CLI видит хоть один лишний сервер (проверка через `cursor-agent mcp list`), запуск не стартует (fail closed), а проект получает флаг.

### Безопасность
- Seatbelt запрещает агенту читать `~/Library/Application Support/Cursor/User/globalStorage/`. Это проверяется в спайке 6.
- Токен самого CLI внутри одного профиля не отделить, это записываем в §13 как остаточный риск. Меры: сетевой allowlist для команд агента и попытка в спайке 6 запускать CLI вне песочницы, а песочницу включать только для его инструментов.

### Спайки
- **Спайк 1:** реальный вид трёх лимитных ошибок, сохранить фикстуры; где CLI сообщает фактическую модель; отдельный `HOME` и сохранение логина CLI; `mcp list`; `--list-models`; где лежит токен CLI; чтение `state.vscdb` из-под LaunchAgent; есть ли `billingCycleStart` в `GetCurrentPeriodUsage`.

## 2026-10-04 — доска (решение Артёма)

### Какие проекты на доске
- Переключатель «Один / Несколько / Все» (`ProjectScopePicker`) убираем из тулбара, и кнопок фильтра больше нет.
- Проект попадает на доску перетаскиванием (drag and drop) из списка проектов в сайдбаре в область канбана и появляется там своей дорожкой.
- В шапке дорожки справа, сразу после кнопки настроек, стоит аккуратная кнопка-крестик «Убрать с доски». Она только скрывает дорожку: проект не удаляется и не ставится на паузу, его задачи продолжают выполняться.
- Остальная логика не меняется: дорожки, сворачивание, флаги в шапке, счётчик «ждёт человека» у скрытых проектов в сайдбаре.
- Предлагаю по умолчанию (поправьте, если не так):
  - Набор проектов на доске сохраняется между запусками.
  - Только что добавленный проект сразу появляется на доске.
  - На пустой доске показывается подсказка «Перетащите проект сюда».
  - Порядок дорожек меняется тем же перетаскиванием.
- Скриншоты v0.1 не перерисовываем. Изменение вносится в макеты Penpot, когда дизайнер будет делать экраны для фронта, а также в спеку (F17, UC-15) и во фронт-план (3.10, `ScopeStore`).
- Первый запуск, когда сохранённого набора ещё нет: на доске показываются все проекты. Это то же правило, что «новый проект сразу на доске» (предложил Frontend, CEO согласен, 4 октября).


## 2026-10-04 — передача управления и начало production-разработки

Пользователь поручил команде самостоятельно разрешать технические issues, обновить документы и начать backend/frontend. Прежние ограничения режима team2 на Sources, Package.swift, исправления и существующие документы отменены этим поручением. Отдельные ветки/PR сохраняются; мерж выполняет Артём. Дизайнерские работы и редизайн исключены; готовые макеты используются для реализации SwiftUI.

### Решения по вопросам спецификации
- #9: `answerHuman` только в agent-стадии; для human/gate/merge используются команды их состояний.
- #10: изменение `.kaban/` агентом означает hard-invariant incident, rollback и ожидание явного решения человека; автоматического продолжения нет.
- #11: execution WIP и run slots не заняты задачами waiting_human; human admission capacity учитывает допущенные нетерминальные задачи до выхода из стадии. Queued перед стадией не занимает место; уменьшение лимита не выталкивает допущенные задачи.
- #12: пустой `ValidationIssue.path` — canonical путь всего документа; UI отображает `pipeline.yaml`. Ошибка конкретного поля требует непустой path. Старый regression skip заменяется проверкой этого контракта.

### Контракт данных
- #14: `TaskDetail` получает durable `artifacts`, `gitGrants`, `gitDenials`, независимо от срока хранения journal. Только эти новые пустые коллекции не записываются в старый wire shape и отсутствующие/null читаются как `[]`. Существующие `humanRequests`, `suspiciousFiles`, `acceptedFiles` остаются обязательными при decoding.
- Начальные настройки приходят в `Snapshot.settings: GlobalSettings?`; `nil` от старого сервера означает неизвестное, а не product defaults. `settingsChanged` может нести полные typed settings с сохранением старого key/value.
- #44: `ProjectSummary.openIncidentCount` authoritative; глобальный счётчик — сумма сводок всех проектов снимка/проекции. `incidentOpened` / `incidentResolved` меняют детали/ленту; backend публикует `projectUpdated` в той же транзакции. Итог не зависит от порядка событий транзакции.
- #37: конечный положительный `max_file_mb` выше представимого Int64 byte threshold насыщается до `Int64.max` без trap; продуктовый произвольный верхний предел не вводится. Неконечные/неположительные значения отклоняются существующим кодом валидации.

### Первый инкремент
Backend: исправления Kit, затем GRDB store с атомарными state/journal и reducer-driven reopen/rollback/idempotency tests; fake driver, внешний исполнитель эффектов и реальные Cursor/MCP/XPC ещё не реализованы. Frontend: SwiftUI app shell и доска на mock-клиенте, без реального исполнения агента и без локального угадывания переходов. Готовность инкремента не объявляет завершение M1/MVP. Разработка ведётся в `codex/…`; порядок принятия PR описан в `docs/development/merge-order.md`.

Исходные Drive-файлы сохранены локально целиком с sha256 в `/private/tmp/kaban-takeover-context/original`. После восстановления подключения 4 октября шесть актуальных документов обновлены по прежним file IDs: архитектура, спецификация, frontend/backend планы, приёмка и журнал решений. Перед записью исходники совпали с ранее прочитанными версиями; после записи полное содержимое проверено по SHA-256. Папки, ссылки и права доступа сохранены; старые отдельные файлы-версии не изменены. Код остаётся в PR до принятия Артёмом.


## 2026-10-04 — второй инкремент M1, после PR #62

- Новые PR направляются только в main. Прежние stacked PR восстановлены через #62; команда не мержит. Порядок нового инкремента и проверенные SHA находятся в отчёте.
- TaskDetail.body — optional Markdown: nil неизвестно, пустая строка известна. Nil не превращается в пустое содержимое при редактировании; отдельного поля критериев приёмки не вводим.
- Human admission хранится явным marker до выхода из стадии, включая паузу после допуска. Пауза до допуска места не занимает. TaskMachineState сохраняет optional pausedState; resume возвращает review только при явной паузе из review, legacy ambiguous pause возвращается в queued.
- Managed fake fixture состоит ровно из queue/agent/human/terminal. Исключение merge_count локально этому fixture; все прочие ошибки запрещены, общий production-валидатор и его честный summary не меняются.
- Результат fake effect, transition, detail/journal и receipt/ack коммитятся атомарно. ID command/index не перенумеровываются при восстановлении. Известные lifecycle/git effects лишь симулируются с audit; неизвестные не подтверждаются. Это не exactly-once внешних процессов.
- В этом инкременте приложение остаётся на демо-клиенте. Следом — XPC adapter и подключение к ядру, затем отдельная live-вертикаль и целевые isolation-спайки. Полный M1/MVP не объявляем завершённым. Дизайнерские работы и редизайн исключены.
