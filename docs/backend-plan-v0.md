# Kaban: план бэкенда (демон KabanAgent), черновик v0.1

Автор: Kaban Backend Bot · 3 октября 2026 · опирается на [архитектуру v0.9](architecture-v0.md), спеку аналитика v0.6 и [журнал решений](decisions-log.md) от 3 октября (вечер). Нумерация спайков по §14 архитектуры.

## 1. Что входит в бэкенд
Всё, что живёт в демоне `KabanAgent` и пакете `KabanKit`, кроме `KabanApp`: модель, автомат, хранилище, планировщик, runner `cursor-agent`, MCP-сервер доски, git-слой, гейты, восстановление, `kabanctl`.

## 2. Модули и порядок реализации
| Шаг | Модуль | Готово, когда |
|---|---|---|
| 1 | `KabanModel` | типы Task/Stage/Pipeline/Run/Transition, Codable + Sendable, JSON Schema `pipeline.yaml` генерируется из типов |
| 2 | `KabanStateMachine` | `reduce(state, command) -> (state, [effect])`, валидатор пайплайна, WIP, возвраты по причинам, ретраи; покрытие тестами всех переходов из раздела 3.3 архитектуры |
| 3 | `KabanStore` | GRDB, миграции, WAL, append-only `transition` с `seq`, одна команда = одна транзакция, снимки `pipeline_version` |
| 4 | `KabanDaemon` + фейковый драйвер | планировщик (DRR по весам, курсор в БД), тик + события, `kabanctl` поверх XPC; конвейер гоняется без Cursor |
| 5 | `KabanGit` | локальный клон на задачу, `pushurl = kaban-no-push`, `fetch` ветки демоном, снимок refs до/после run, очередь слияния с блокировкой на проект, автокоммит `.kaban/` под той же блокировкой |
| 6 | `KabanAgentDrivers` | `CursorCLIDriver`: argv, env, явный PATH, process group, парсер stream-json, распознавание rate-limit |
| 7 | `KabanMCPServer` | Streamable HTTP на 127.0.0.1, токен на run, инструменты из раздела 9, идемпотентность повторных вызовов |
| 8 | Гейты и восстановление | гейт-команды с таймаутом и захватом вывода, рестарт демона по разделу 10 |
| 9 | Seatbelt | профиль `sandbox-exec` для `cursor-agent` и гейтов, по итогам спайка 6 |

## 3. Тестирование
- Шаги 1–3 и планировщик с фейковым драйвером не зависят от macOS: собираем и гоняем `swift test` на общем Linux-компьютере (GRDB работает на Linux), так ядро можно разрабатывать, пока Мак не в сети.
- Свойства автомата проверяем генеративными тестами: случайные последовательности команд не нарушают WIP, лимиты возвратов и инварианты «агент не закрывает стадию сам».
- Интеграционные тесты с настоящим git на временных репозиториях: конфликт при rebase, красные гейты после rebase, попытка агента сдвинуть `main` (должен сработать откат refs и инцидент).
- E2E на Маке: спайк 5 превращается в постоянный тест с `cursor-agent` на дешёвой модели.

## 4. Уточнения к архитектуре (учтены в v0.5–v0.9)
1. **Кэши сборки в клоне.** `git clone --local` экономит место на объектах, но каждый клон стартует без `node_modules`, `.build`, `DerivedData`, `build/` и т. п., и первая сборка в каждой задаче будет полной. Предлагаю в конфиге проекта список `warm_paths`, которые демон копирует из основной рабочей копии через APFS clonefile (`cp -c`): копия мгновенная и почти не занимает места. Проверить в спайке 6.
2. **`info/exclude` для `.cursor/mcp.json`** теперь пишется в `.git` клона задачи, а не в общий каталог.
3. **Восстановление (раздел 10, шаг 3)**: `reset --hard` и `clean` выполняются только по пути клона задачи, путь проверяется на префикс `Workspaces/<project>/`, чтобы ошибка в данных не задела основной репозиторий.
4. **Снимок refs** берём не только до и после run, но и периодически во время долгого run, чтобы инцидент поднимался сразу, а не через час.
5. **Логи run**: JSONL с ротацией, маскирование ключей на записи, `tailLog` отдаёт по смещению, чтобы фронт дочитывал после переподключения.

## 5. Бэкенд-часть спайков (что именно проверяю)
- **Спайк 1, `cursor-agent` headless.** `--help` и реальные запуски: запись без подтверждения, `--approve-mcps`, `--model`, формат `result` (usage, session id), `--resume` в `-p`, коды выхода. Плюс по журналу решений:
  - реальный вид трёх лимитных ошибок (месячная квота, `resource_exhausted` с молчаливым выходом, троттлинг): сырой stream-json и stderr сохраняю как фикстуры для фейкового драйвера;
  - фактическая модель: поле `model` в `system/init` (по документации это отображаемое название, не id); меняется ли оно при `fallbackModel` и при `--resume`, бывает ли подмена без ошибки;
  - `--list-models`: точный формат строк `id - название`, поведение при разлогине;
  - где CLI хранит свой токен (Keychain или файл в `HOME`), сохраняется ли логин при отдельном `HOME` запуска;
  - `cursor-agent mcp list` в окружении запуска: какие серверы CLI реально видит, читает ли глобальный `~/.cursor/mcp.json`;
  - авторизация и PATH из-под launchd; читается ли `state.vscdb` Cursor IDE из-под LaunchAgent без системного запроса.
- **Спайк 2, MCP из клона.** Подхват `.cursor/mcp.json` из cwd, `${env:KABAN_RUN_TOKEN}`, вызов по HTTP с Bearer. Плюс: можно ли подключить сервер доски без записи в репозиторий (флаг CLI или `~/.cursor/mcp.json` в отдельном `HOME`); если нельзя, подмена файла проекта и возврат его из `main` перед проверкой результата.
- **Спайк 5, мини-конвейер.** Бэкенд-часть: автомат, очередь слияния, отказ git и «разрешить один раз» на настоящем `cursor-agent`.
- **Спайк 6, Seatbelt и клоны.** Минимальный профиль, при котором работают `cursor-agent`, git и сборка; запрет чтения `~/Library/Application Support/Cursor/User/globalStorage/` из-под агента (тест, что чтение действительно запрещено); можно ли запускать CLI вне песочницы, а песочницу включать только для его инструментов (цель, не обязательство); подключение к `127.0.0.1` только на порт MCP; замеры клона и `warm_paths`.

## 5а. Что добавляется в модули по журналу решений
- `KabanStateMachine`: счётчик попыток на заход в стадию, `max_runs_per_task` без запусков, не списывающих попытку; причины `run_limit`, `model_substituted`, `pipeline_invalid`; ретрай, упёршийся в квоту, освобождает WIP-слот и уходит в `queued`.
- `KabanStore`: `model_pool_rule`, `model_catalog`, `model_flag`, настройки опроса квоты и порогов.
- `KabanDaemon`: проверка квоты перед стартом (данные не старше 60 с), пропуск задач, ждущих квоту, проба на модель (одна за раз, не чаще раза в 10 мин, раз в 6 ч при неизвестной дате сброса).
- `KabanAgentDrivers`: классификатор сбоев (молчаливый выход без инструментов и изменений не списывает попытку), сверка модели по `system/init` с остановкой процесса до первого инструмента, сборка конфига MCP на запуск с fail closed по `mcp list`, `--model <id>` всегда.
- `KabanGit`: `refs/kaban/wip/<run-id>` перед откатом клона после краша или зависания.

## 7. Takeover: первый инкремент M1 (4 октября 2026)

В `KabanDaemonCore` добавлен переносимый GRDB store (точно 7.11.1: Swift tools 6.1 для Linux CI; upstream отключает необязательные SQLite snapshot API на Linux), миграция SQLite и WAL. `createTask` и узкий набор команд (`start`, `completeStage`, `gatesPassed`, `daemonRestarted`, `cancel`) сохраняют полное состояние автомата, карточку и неизменяемый снимок пайплайна задачи. Проекция, последовательный журнал, ответ для идемпотентного повтора и точный Codable payload эффектов фиксируются одной транзакцией. Повтор commandId с другим payload отклоняется. Ошибки откатывают транзакцию; отклонённые команды пока не получают durable receipt.

`DurableSnapshot` — внутренний снимок задач и seq, не реализация протокольного `getSnapshot`. Restart recovery атомарно восстанавливает running/gating задачи, заменяет устаревшие недоставленные эффекты этих задач и сохраняет результат прохода по passId. Outbox отдаёт только ещё не выполненные эффекты (recordTransition уже отражён в журнале); доставка как минимум один раз, подтверждение после успешного выполнения. Подтверждение сейчас относится ко всему batch: при сбое после частичного выполнения batch будет доставлен целиком снова, поэтому каждый эффект будущего worker обязан быть идемпотентным (поштучные receipt/ack пока отсутствуют). Внешний worker обязан быть идемпотентным; реальное исполнение процессов/git/гейтов в этом инкременте не подключено.

Проверены создание → переход → журнал → снимок → повторное открытие, точный outbox, дедупликация после рестарта, конфликт commandId, откат при SQLite write failure после изменения проекции, refund счётчика запуска и повтор прохода recovery. Linux CI требует системные sqlite3 headers (`libsqlite3-dev`) и Swift 6.1. GRDB 7.4.0 не поддерживал Linux и ошибочно ссылался на `sqlite3_snapshot_*`; в [7.10.0](https://github.com/groue/GRDB.swift/releases/tag/v7.10.0) upstream добавил Linux-условие `SQLITE_DISABLE_SNAPSHOT`. [Package.swift 7.11.1](https://github.com/groue/GRDB.swift/blob/v7.11.1/Package.swift) использует эту конфигурацию системной SQLite без локальных патчей зависимости.

Следующие части M1: проект/настройки/полный протокольный snapshot, pipeline_version на вход в стадию и смена пайплайна, долговечные grants/denials/artifacts, incident lifecycle с projectUpdated в той же транзакции (project.openIncidentCount авторитетен, global = сумма), stageLoadChanged, worker/fake driver и scheduler DRR с durable курсором. Этот инкремент не закрывает весь M1 и не объявляет готовыми durable detail reads или incident support.
