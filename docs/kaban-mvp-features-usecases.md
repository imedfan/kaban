# Kaban MVP: фичи и юзеркейсы (v0.7.2)

Основа: решения из чата Kaban Dev, [журнал решений](decisions-log.md), [архитектура v0.10.2](architecture-v0.md) и отчёт `kanban-factory-research.md`. Спека описывает поведение с точки зрения пользователя; технические детали (схема `pipeline.yaml`, XPC, хранилище) живут в архитектуре, и спека на неё ссылается.

## 0. Принятые решения
Артём:
- В MVP сливаем локально в `main`, репозиторий заводит Артём.
- Бюджета в долларах нет. Лимиты Cursor всегда обрабатываются реактивно, а проверка остатка квоты перед стартом это необязательная опция (UC-21).
- **Auto запрещён, моделей по умолчанию нет.** У каждой агентской стадии модель указывается явно; если хотя бы у одной её нет, не запускается весь пайплайн проекта (UC-23).
- Если Cursor ответил не той моделью, человеку прямо показывается, что причина в подмене (UC-22).
- Опрос квоты настраивается, плюс свежая проверка перед каждым стартом; лимит считается по пулу модели стадии (Cm или Om), для этого ведётся справочник моделей (1.6).
- По умолчанию агенту доступен только MCP-сервер доски; MCP проекта и личные включаются явным списком (UC-24).
- После разрешения конфликта задача **всегда** снова идёт на ревью человека.
- WIP и лимиты по умолчанию устраивают, но всё настраивается на каждый столбец.
- Столбец это абстрактная настраиваемая стадия, у каждой команды свой пайплайн.
- Проектов сколько угодно, на доску проект добавляется перетаскиванием из списка и убирается крестиком в шапке дорожки (UC-15), проекты различаются маскотами.
- Разрешения и запреты git-команд настраиваются на проект.

CEO (по сверке фронта):
- Исчерпанные ретраи дают `waiting_human`, состояния `failed` нет.
- При rate-limit текущие запуски доигрывают, новые не стартуют.
- В Human Review есть «Отклонить» с выбором: отменить задачу или вернуть в стадию.
- `max_waiting_human` считается **на проект**.
- Непустую стадию удалить нельзя.
- Изоляция только через отдельный клон на задачу (`git clone --local`), без `git worktree`.
- В MVP есть раздел сайдбара «Инциденты» со счётчиком; общий «Журнал» откладываем, в MVP хватает ленты задачи.
- Уведомление о задаче на ревью человека **включено по умолчанию**: человек это узкое место конвейера.
- «Запуск выключен» это не статус задачи, а флаг: для всего Мака, если `cursor-agent` недоступен или не залогинен, и для проекта, если папка пропала или пайплайна нет.
- Счётчик попыток живёт в пределах одного захода в стадию; общий потолок `max_runs_per_task` (12) считает только автоматические запуски и обнуляется любым действием человека.
- Если остаток Om ниже порога, а Cm ещё есть, встают только стадии на моделях из Om; автоподмены модели нет.

## 1. Модель стадий, статусов и лимитов

Шаблон пайплайна по умолчанию: **Backlog → Dev → Test → AI Review → Human Review → Merge → Done**. Реальный набор столбцов берётся из `.kaban/pipeline.yaml` проекта (раздел 1.5).

### 1.1 Статусы
Единый набор статусов и причин (`reason`) определён в **архитектуре, раздел 3.2**, и спека его не дублирует. Для чтения юзеркейсов достаточно знать:
- задача всегда стоит в одной стадии и имеет один статус: `queued`, `running`, `gating`, `retry_wait`, `waiting_human`, `paused`, `blocked`, `done`, `cancelled`;
- всё, что требует решения человека, это `waiting_human` с причиной (вопрос агента, ревью, исчерпаны ретраи, лимит возвратов, лимит конфликтов, лимит запусков `run_limit`, подмена модели `model_substituted`, отказы git, инцидент, некорректный результат read-only стадии);
- задача в `queued` может нести подпись-причину, почему не стартует: «ждёт места», «ждёт квоту Cm/Om», «на модели флаг». Такая задача **не держит очередь**: планировщик берёт следующую в стадии;
- всё, что касается целого Мака или проекта, это **флаги планировщика**, а не статусы задач (таблица флагов там же, в 3.2): задачи остаются `queued`, новые запуски не стартуют, текущие доигрывают. Флаги Мака (ручная пауза, rate-limit, квота исчерпана с неизвестным пулом, «Cursor недоступен») показываются баннером над доской, исчерпанный пул Cm или Om отдельным баннером пула со знаком на шапках столбцов его моделей, флаги проекта (пауза, лимит ожидающих, проект недоступен, включая некорректный пайплайн и лишний MCP-сервер, слияние заблокировано) в шапке дорожки, флаги модели (недоступна, подменена) тонким баннером над доской и знаком в шапках столбцов на этой модели;
- `blocked` бывает только у задачи в голове очереди слияния, когда `main` в рабочей копии человека грязный;
- счётчик возвратов, пересечение файлов и неиспользованное git-разрешение это бейджи на карточке, а не статусы.

### 1.2 `waiting_human` и WIP
- `waiting_human` **не занимает** WIP-слот стадии: процесс агента завершается, клон задачи и сессия сохраняются. Дефицитный ресурс это агентские слоты и квота Cursor.
- Чтобы недоделки не копились, у каждого проекта есть **`max_waiting_human` (по умолчанию 3)**. Задачи на ревью человека (`reason = review`) в него не входят. Когда лимит достигнут, этот проект перестаёт брать **новые** задачи из Backlog, начатые продолжают двигаться; в шапке дорожки проекта баннер.
- После ответа человека задача встаёт в очередь своей стадии **раньше новых** и продолжает ту же сессию, если resume работает в headless-режиме (спайк 1); иначе стадия стартует заново с ответом в контексте.
- Human Review это обычная стадия типа `human` со своим WIP (по умолчанию 5). Когда она заполнена, задачи перед ней стоят в `queued`.

### 1.3 Возвраты
Возврат это решение агента или демона отправить задачу на более раннюю стадию.
- Test → Dev: **3** на задачу.
- AI Review → Dev: **2**.
- Конфликт слияния → первая агентская стадия: **2**.
- Общий потолок автоматических возвратов на задачу: **5**.
- При превышении задача уходит в `waiting_human` (`bounce_limit` или `conflict_limit`) со сводкой всех замечаний. Варианты для человека: дать ещё попыток, сменить модель, отредактировать задачу, отменить.
- Возвраты **от человека** в лимиты не входят.
- Все лимиты настраиваются в пайплайне на каждую стадию.

### 1.4 Ретраи и лимит запусков
Ретрай это повтор той же стадии из-за технического сбоя: краш, зависание (нет событий 10 мин), общий таймаут стадии (60 мин), агент завершился без финального вызова, гейт не прошёл. Возврат (1.3) это другой механизм со своими счётчиками.
- Пока ждём повтора, задача в `retry_wait` и держит слот. По умолчанию **3 попытки** на стадию: первая и два повтора с паузами **30 с и 2 мин** (пауз на одну меньше, чем попыток; значения ждут решения Артёма, раздел 5). Дальше `waiting_human: retries_exhausted`.
- Счётчик попыток живёт **в пределах одного захода в стадию**: после возврата или нового входа он начинается заново.
- С чем стартует повтор: после красного гейта или выхода без финального вызова агент продолжает в том же клоне, в промпт добавляется вывод гейта или напоминание закончить через `complete_stage`. После краша или зависания демон сохраняет грязное состояние в `refs/kaban/wip/<run-id>` внутри клона и откатывает клон к последнему коммиту стадии; человек может восстановить это состояние из панели деталей.
- **Не списывают попытку:** rate-limit, исчерпанная квота, ошибка авторизации Cursor, перезапуск демона, молчаливый выход (ниже), остановка из-за подмены модели (UC-22), ожидание квоты или флага модели.
- **Молчаливый выход.** Агент вышел, не сделав ни одного вызова инструмента и не изменив ни одного файла. Попытка пока не списывается, демон делает пробный запуск на той же модели (одна проба на модель за раз, не чаще раза в 10 минут). Нашлась лимитная причина → флаг по UC-09; проба прошла чисто → это обычный сбой, попытка списывается.
- Ретрай, который упёрся в квоту или флаг модели, освобождает WIP-слот и уходит в `queued` с причиной.
- **Общий потолок `max_runs_per_task` (по умолчанию 12)** на задачу. Считаются только автоматические запуски, те, что не списывают попытку, не считаются. Любое действие человека над задачей (ответ или замечание, перезапуск стадии, перенос, возврат с комментарием) обнуляет счётчик. При превышении задача уходит в `waiting_human: run_limit` с историей запусков; варианты те же, что в UC-10.

### 1.5 Модель конфигурации стадии (столбца)
Столбец это экземпляр одного из типов стадий, зашитых в код: `queue`, `agent`, `gate` (только команды без ИИ), `human`, `merge`, `terminal`. Всё остальное задаётся в `.kaban/pipeline.yaml` (поля и пример в архитектуре, раздел 3.1).

| Группа | Настройки | Для каких типов | Зачем пользователю |
|---|---|---|---|
| Идентичность | стабильный `id` (не меняется), имя | все | переименование и перестановка не ломают задачи |
| Отображение | иконка, цвет, порядок, свёрнут по умолчанию, скрыт; `gate` рисуется тонкой полосой | все | доска под свой вкус |
| Пропускная способность | WIP-лимит, правило приоритета (по умолчанию: возвращённые, отвеченные человеком, потом по очереди) | `agent`, `gate`, `human` | управлять нагрузкой |
| Исполнитель | харнес (в MVP только Cursor), **явная модель (обязательна, `auto` запрещён)**, скилл (промпт роли) | `agent` | своя роль на стадию, предсказуемое качество |
| Права | запись или только чтение; MCP стадии: сервер доски всегда, остальные только выбором из белого списка проекта (UC-24); git-политика стадии (сузить или расширить по условию) | `agent` | ревьюер не правит код, лишних инструментов у агента нет |
| Окружение | несекретные переменные окружения (секреты только по имени ключа в Keychain); рабочая копия: клон задачи или свежий клон только на чтение | `agent` | изоляция, воспроизводимость |
| Вход | задача, резюме прошлой стадии, дифф, отчёт гейтов, замечания возврата, действующие git-разрешения | `agent`, `human` | агент видит нужный контекст |
| Выход | гейты (сборка, тесты, линтер) | `agent`, `gate`, `merge` | «готово» подтверждается проверками |
| Переходы | куда при успехе; куда можно вернуть и с каким лимитом; поведение при провале гейта и конфликте | все, кроме `terminal` | свой процесс команды |
| Надёжность | число попыток и паузы, таймаут зависания, общий таймаут стадии | `agent`, `gate` | не висеть вечно |
| Хуки и уведомления | свои скрипты на входе и выходе, о каких событиях уведомлять | все | интеграции |

**Уровень пайплайна** (тот же файл, процесс команды):
- `max_waiting_human`, общий потолок возвратов на задачу, `max_runs_per_task`;
- **рабочая копия** (`workspace`): `warm_paths`, которые мгновенно копируются из основной копии через APFS clonefile, и необязательная команда `on_create` (например, `npm ci --prefer-offline`);
- **политика git** (`git`): пресет (строгий, стандартный, свободный) и списки разрешённых и запрещённых команд. В UI видно, что унаследовано, что переопределено, и итоговую политику каждой стадии.

Стандартный пресет: можно `status`, `diff`, `log`, `show`, `add`, `commit`, `restore --staged` в ветке своей задачи. Нельзя `push`, `reset --hard`, `remote`, `config`, теги, удаление веток, любые `--force`, `checkout` и `rebase` на `main`.

**Жёсткие правила, которые не снимает ни один пресет, даже свободный:** агент не двигает `main` и чужие ветки, не пушит, не пишет в `.kaban/`; слияние в `main` делает только демон. Политика из файла настраивает только фильтр (обёртку `git`); песочница и проверка результата демоном работают всегда (архитектура, 8.2).

**Уровень Мака** (локальная база, не в репозитории): общий потолок одновременных процессов агентов на все проекты (по умолчанию 4), вес проекта и его личный максимум, маскот, ручные паузы, белый список MCP проекта (UC-24), справочник моделей и пулов (1.6), опция квоты Cursor (UC-21).

**Где живёт пайплайн.** Источник правды это закоммиченный `main:.kaban/`. Сохранение из настроек демон валидирует и сам коммитит только `.kaban/` отдельным коммитом, правки человека в рабочей копии не трогает. Пока в редакторе есть ошибки, «Сохранить» неактивна: некорректная версия в `main` не попадает, черновик живёт только в открытом редакторе. Ручную правку файла демон валидирует и показывает в настройках как «есть незакоммиченные правки» с кнопкой «Применить»; молча не коммитит.

**Валидатор** не применит пайплайн без пути до Done, с возвратом вперёд по цепочке, без единственной стадии `merge`, с удалённой непустой стадией или с агентской стадией без явной модели (либо с `auto`). Если некорректная версия всё же оказалась в `main` (шаблон нового проекта или ручной коммит), проект получает флаг «пайплайн некорректен»: идущие запуски доигрывают, новые не стартуют и задачи не переходят между стадиями, пока в `main` не появится корректная версия.

### 1.6 Модели и пулы квоты
- Модель стадии всегда явная, демон всегда передаёт её в `cursor-agent`. Auto запрещён: его нет в списках выбора, а `auto` в файле не проходит валидацию. `composer-*` это конкретная модель Cursor, она разрешена.
- У Cursor два месячных пула: **Cm** (модели Cursor, `composer-*`) и **Om** (остальные именные модели). Справочник «модель → пул» хранится локально: встроенное правило `composer-*` → Cm, всё остальное → Om, плюс ручные исключения человека.
- Список моделей берётся из `cursor-agent --list-models` при старте демона и раз в сутки. Новая модель, которую не покрыло ни одно ручное исключение, получает значок «проверь пул» и по умолчанию считается Om. Модель стадии пропала из списка → сразу флаг «модель недоступна» на эту модель (UC-09), без пробного запуска.
- Модель меняет только человек и только на явную; автоподмены нет. Рядом с моделью в редакторе стадии видно, из какого пула она тратит.

| F23 | Замечание агенту из любого `waiting_human`: текст человека уходит агенту, задача продолжает стадию | Must |
| F24 | Явная модель на каждой стадии, справочник моделей и пулов, сверка фактической модели и причина «подмена модели» | Must |
| F25 | Проверка остатка квоты Cm/Om перед стартом (неофициально, выключено по умолчанию), полосы квоты в менюбаре | Should |
| F26 | Белый список MCP: по умолчанию только сервер доски, MCP проекта и личные включаются явно, запуск не стартует при лишнем сервере | Must |
| F27 | Лимит запусков на задачу и сохранение состояния клона перед откатом после сбоя | Must |

**Не входит в MVP:** полноценный diff-viewer, другие харнессы кроме Cursor, импорт из Jira/Linear/GitHub Issues, граф зависимостей, стадия планирования с апрувом плана, best-of-N, авто-разбиение задач, общий журнал событий в сайдбаре, командная работа, бюджет в долларах, свои нарисованные маскоты (Rive или Lottie).

## 3. Юзеркейсы

Актёры: **Человек** (Артём), **Демон** (`KabanAgent`), **Агент** (`cursor-agent` на стадии). Команды XPC, на которые опираются действия человека, перечислены в архитектуре, раздел 5.

### UC-01. Подключить проект
1. Человек выбирает папку репозитория и базовую ветку.
2. Демон проверяет, что это git-репозиторий, и проверяет окружение: `cursor-agent` найден и залогинен, git есть, песочница работает. Чистая рабочая копия **не требуется**.
3. Если в репозитории есть `.kaban/pipeline.yaml`, используется он. Иначе в диалоге галочка «создать шаблон и закоммитить» (включена по умолчанию); демон кладёт шаблон по умолчанию и коммитит только `.kaban/`. Моделей в шаблоне нет, поэтому проект сразу получает флаг «пайплайн некорректен» со списком стадий без модели (UC-23).
4. Человек подтверждает команды гейтов, которые демон предложил по файлам сборки (например, `swift build`, `swift test`), или задаёт свои.
5. Проекту назначается маскот от его стабильного id. На доске появляется дорожка проекта.
6. Человек указывает модель для каждой агентской стадии (кнопка «Указать модели» на дорожке) и сохраняет. После этого флаг снимается, и проект начинает брать задачи.

Альтернативы:
- Не git-репозиторий → ошибка с пояснением, проект не добавляется.
- Галочку шаблона сняли и пайплайна нет → проект добавлен с флагом «недоступен: нет пайплайна», задачи можно заводить, они стоят `queued`; в шапке дорожки баннер с кнопкой «Проверить снова».
- `cursor-agent` не найден или не залогинен → проект добавлен, а над доской общий баннер «Cursor недоступен» (UC-20).

### UC-02. Завести задачу
1. Человек создаёт карточку: заголовок, описание, критерии приёмки, приоритет.
2. Задача попадает в Backlog со статусом `queued`.

Правила: без критериев приёмки задачу можно сохранить, но не запустить. Редактировать задачу можно в `queued`, `waiting_human` и `paused`; во время работы агента правка недоступна, вместо неё можно поставить задачу на паузу.

### UC-03. Автозапуск задачи
1. Планировщик видит свободный слот в первой агентской стадии, общий потолок процессов не исчерпан, у Мака и проекта не поднят ни один флаг (пауза, rate-limit, квота исчерпана, Cursor недоступен, проект недоступен, лимит ожидающих), на модели стадии нет флага, а при включённой опции квоты в её пуле хватает остатка (UC-21).
2. Берёт задачу по правилу приоритета стадии (возвращённые и отвеченные раньше новых); слоты между проектами раздаются по кругу с весами.
3. Демон создаёт клон задачи и ветку `kaban/<id>-<slug>` от свежего `main`, прогревает клон, выдаёт токен запуска, собирает конфиг MCP (сервер доски плюс белый список, UC-24), запускает агента со скиллом и явной моделью стадии и сверяет фактическую модель по первому событию (UC-22).
4. Задача `running`, карточка в стадии Dev.

### UC-04. Пройти стадию
1. Агент работает и периодически вызывает `report_progress`.
2. Агент вызывает `complete_stage(summary, artifacts)`.
3. Задача в `gating`, демон гоняет гейты стадии и проверку результата (архитектура, 8.2).
4. Всё зелено → демон делает страховочный коммит, сохраняет резюме стадии и ставит задачу в очередь следующей стадии.

Альтернативы: гейт красный или агент вышел без финального вызова → `retry_wait` и повтор в том же клоне (1.4); агент вышел молча, ничего не сделав → пробный запуск без списания попытки (1.4); read-only стадия оставила изменения → откат, повтор, при повторном нарушении `waiting_human: invalid_result`.

### UC-05. Возврат от тестера
1. Агент стадии Test вызывает `return_to_stage("dev", issues[])`.
2. Демон проверяет лимиты (1.3).
3. В пределах лимита → задача в очереди Dev с приоритетом, замечания в контексте, на карточке бейдж «возврат 1/3».
4. Агент Dev получает замечания через `get_task_context` и исправляет, дальше снова Test.

Альтернатива: лимит исчерпан → `waiting_human: bounce_limit`. Так же работает AI Review → Dev.

### UC-06. Агент просит человека
1. Агент вызывает `request_human(question)`.
2. Демон сохраняет сессию, завершает процесс, задача в `waiting_human: question`, слот освобождается, приходит уведомление.
3. Человек отвечает в карточке.
4. Задача встаёт в очередь своей стадии раньше новых и продолжает сессию с ответом (или начинает стадию заново с ответом в контексте, если resume недоступен).

Альтернатива: человек не отвечает → задача ждёт без таймаута; при достижении `max_waiting_human` проект перестаёт брать новые задачи (1.2).

**Замечание агенту.** Тот же путь работает из `waiting_human` с **любой** причиной, не только с вопросом: человек пишет замечание в карточке («используй другой подход», «тесты в папке X»), задача встаёт в очередь своей стадии и продолжает сессию с этим текстом. Если попытки или лимит возвратов уже исчерпаны, замечание добавляет одну попытку, чтобы задача сразу не вернулась к человеку.

### UC-07. Ревью человеком
1. Задача в Human Review (`waiting_human: review`), приходит уведомление (включено по умолчанию, отключается в настройках).
2. Человек видит сводку: резюме стадий, файлы с +/−, коммиты, результаты гейтов, время и стоимость (если есть), пометку «изменено при разрешении конфликта». Может «Открыть в Cursor» на клоне задачи.
3. Варианты:
   - **Одобрить** → задача в очереди Merge.
   - **Вернуть с комментарием** → в выбранную стадию (по умолчанию первая агентская) с приоритетом; в лимиты возвратов не входит.
   - **Отклонить** → выбор: **отменить** (`cancelled`, клон удаляется; с галочкой «оставить ветку» её копия сохраняется в основном репозитории как `kaban/archive/<task-id>`, без галочки в основном репозитории ничего не остаётся) или **вернуть в стадию** без комментария.

### UC-08. Слияние и конфликт
1. Задачи в Merge проекта обрабатываются строго по одной, в порядке одобрения.
2. Демон забирает ветку из клона задачи, делает rebase на актуальный `main` и прогоняет гейты.
3. Всё чисто → fast-forward `main`, задача `done`, клон удаляется с задержкой.

Альтернативы:
- **Конфликт rebase.** Демон отменяет rebase, задача уходит в первую агентскую стадию с приоритетом, списком конфликтующих файлов и задачами, которые их недавно меняли; политика git этой стадии на этот возврат расширяется командой `rebase`. Дальше задача снова проходит все стадии и **всегда** Human Review. Счётчик конфликтов +1, лимит 2, дальше `waiting_human: conflict_limit`.
- **Rebase чистый, но гейты красные** (семантический конфликт) → тот же путь с логом гейтов.
- **В рабочей копии человека выбран `main` и его незакоммиченные правки пересекаются с входящими файлами** → задача в голове очереди `blocked: main_dirty`, у проекта флаг «слияние заблокировано» в шапке дорожки, остальные задачи ждут в очереди; ничего не теряется, после того как человек уберёт правки, слияние повторяется само.
- **`main` сдвинули руками** во время очереди → демон повторяет rebase на новую голову.

Профилактика: при входе в агентскую стадию и после каждого коммита демон сравнивает изменённые файлы с другими задачами в работе и ставит обеим бейдж пересечения. Слияние это не блокирует.

### UC-09. Лимиты Cursor
Лимитные ошибки демон всегда разбирает реактивно, по выводу агента; проактивная проверка остатка описана в UC-21. Run, получивший лимитную ошибку, попытку не списывает и в `max_runs_per_task` не считается. Текущие запуски других задач **доигрывают**. Точный вид ошибок фиксируется в спайке 1.

**а) Короткий rate-limit.**
1. Включается **глобальный** cooldown (аккаунт Cursor один на все проекты): 15, потом 30, потом 60 минут при повторах. Новые запуски не стартуют ни в одном проекте.
2. Запуск, который получил ошибку, уходит в `retry_wait: rate_limit` и продолжит после cooldown.
3. Над доской баннер и уведомление «лимит Cursor, возобновление в 16:40» с обратным отсчётом. Человек может снять cooldown раньше.

**б) Исчерпана месячная квота (`usage_exhausted`).**
1. Флаг до даты сброса: из данных квоты (UC-21) или из текста ошибки. Если известно, какой пул кончился, это флаг пула (`cm` или `om`): встают только стадии на моделях этого пула (кончился Om → стадии на `composer-*` работают). Флагом Мака он становится только при неизвестном пуле (`unknown`), тогда встаёт весь Мак.
2. Баннер «Om исчерпан до 14.08 · N стадий» (или «Квота Cursor исчерпана до 14.08», если пул неизвестен). Кнопки «на Auto» нет: человек может только сменить модель стадий на явную из другого пула или ждать.
3. Если дату распарсить не удалось, флаг висит до ручного снятия, а раз в 6 часов идёт пробный запуск; проба прошла чисто → флаг снимается.

**в) Модель недоступна (`model_unavailable`).**
1. Флаг ставится только на эту модель: встают стадии, где она выбрана, задачи на других моделях продолжают работать. Задачи этих стадий ждут в `queued` с подписью «на модели флаг» и не держат очередь.
2. Тонкий баннер «Opus недоступен · 2 стадии» и знак в шапках этих столбцов, кнопка «Сменить модель» открывает выбор явной модели.
3. Флаг снимает проба на модели (не чаще раза в 10 минут), возвращение модели в `--list-models` или человек вручную. После снятия ждавшие задачи стартуют сами.

Статус `paused` в этом сценарии не используется: он только для ручной паузы задачи (UC-11).

### UC-10. Сбой агента
1. Краш, зависание, общий таймаут стадии или выход без финального вызова → демон убивает процесс, задача в `retry_wait` с причиной. После краша и зависания грязное состояние клона сохраняется в `refs/kaban/wip/<run-id>`, клон откатывается к последнему коммиту стадии (1.4).
2. После паузы стадия повторяется (до 3 попыток, 1.4).
3. Попытки кончились → `waiting_human: retries_exhausted`, лог последней попытки и уведомление. Если раньше упёрлись в `max_runs_per_task` → `waiting_human: run_limit` с историей запусков.
4. Человек выбирает: перезапустить стадию (при желании добавив попыток), написать замечание агенту (UC-06), сменить модель для этой задачи на другую явную, восстановить сохранённое состояние клона, вернуть в Backlog или отменить. Любое из этих действий обнуляет счётчик `max_runs_per_task`.

### UC-11. Ручное управление
- **Пауза задачи**: текущий запуск прерывается без списания попытки, задача `paused`; возобновление ставит её в `queued` своей стадии.
- **Паузы проекта и всей доски** (из тулбара и менюбара): новые запуски не стартуют, текущие доигрывают.
- **Перетаскивание назад** (в Backlog или более раннюю стадию) прерывает текущий запуск после подтверждения, попытка не списывается.
- **Перетаскивание вперёд** через стадии с гейтами запрещено; исключение только Backlog → первая стадия (ручной старт, если есть слот).
- **Отмена**: процесс останавливается, клон удаляется; галочка «оставить ветку» сохраняет её как `kaban/archive/<task-id>` (как в UC-07).
- **Смена приоритета** действует на следующий выбор планировщика.

### UC-12. Перезапуск демона или Мака
1. Демон стартует и читает журнал событий из SQLite.
2. Живые осиротевшие процессы агентов убиваются, их задачи уходят в `retry_wait: daemon_restart` без списания попытки; задачи в `gating` перезапускают гейты; незакоммиченные изменения в клонах сохраняются в `refs/kaban/wip/<run-id>` и откатываются к последнему коммиту стадии.
3. Демон проверяет результат по всем проектам (как в UC-18).
4. UI переподключается и дочитывает пропущенные события; если журнал уже обрезан, берёт полный снимок.

### UC-13. Изменить пайплайн, пока в нём есть задачи
1. Человек меняет столбцы на экране настройки (демон валидирует и автокоммитит `.kaban/`) или правит файл руками и нажимает «Применить».
2. Ошибки валидации видны прямо в настройках, «Сохранить» неактивна, пока они есть; невалидная версия не применяется.
3. Валидная версия действует сразу: идущий запуск доживает по правилам, с которыми задача вошла в стадию, следующие запуски берут новые.

Правила по видам правок:
- **Удаление столбца с задачами** в любом нетерминальном статусе запрещено. Сначала задачи переносят или ждут, пока стадия опустеет.
- **WIP уменьшили ниже текущего числа задач** → никого не прерываем, новые не берём, на столбце видно «4/3».
- **Переименование, перестановка, смена иконки** → на задачи не влияет, они ссылаются на `id`.
- **Смена модели, скилла, гейтов, git-политики** → со следующего запуска. Удалить модель у стадии нельзя: поле обязательно (UC-23).
- **Лимит возвратов уменьшили ниже набранного** → задача доходит стадию, на следующем возврате уходит к человеку.
- **Новый столбец в середине** → задачи после него его не проходят, задачи до него пройдут.
- **Правка `.kaban/` из клона агента** → откатывается проверкой результата с замечанием задаче.

### UC-14. Работа с несколькими проектами
1. Человек добавляет ещё проекты по UC-01, ограничения на количество нет.
2. Все проекты делят общий потолок процессов. Слоты раздаются по кругу с весами, так что большой бэклог одного проекта не забирает всё; у проекта можно задать вес и личный максимум.
3. Пауза по rate-limit общая, пауза по `max_waiting_human` и очередь слияния у каждого проекта свои.

Альтернативы:
- Папку проекта переместили или удалили → у проекта флаг «недоступен: папка не найдена», задачи остаются в своих статусах, новые запуски по проекту не стартуют, история сохраняется. Человек указывает новый путь, нажимает «Проверить снова» или удаляет проект с подтверждением.
- Пайплайн в `main` стал невалидным (например, его сломали коммитом руками или стёрли модель у стадии) → флаг «недоступен: пайплайн некорректен» с ошибками валидации; идущие запуски доигрывают, новые не стартуют и задачи не переходят между стадиями до исправления.

### UC-15. Выбрать, какие проекты показывать на доске
1. Доска показывает дорожки проектов, каждая со своими столбцами; дорожки сворачиваются. Кнопок «один / несколько / все» нет.
2. Добавить проект: человек перетаскивает его из списка проектов в сайдбаре в область канбана, дорожка появляется в месте сброса. Во время перетаскивания область подсвечивает, куда встанет дорожка. Тот же результат даёт пункт «Показать на доске» в контекстном меню проекта (для клавиатуры и VoiceOver).
3. Убрать проект: крестик в шапке дорожки, справа после кнопки настроек. Проект только скрывается с доски: он не удаляется, не ставится на паузу, его задачи продолжают выполняться.
4. Порядок дорожек меняется перетаскиванием дорожки или ⌘⌥←/→; ⌘1…⌘9 прокручивают доску к N-й дорожке и ставят на неё фокус.
5. Новый подключённый проект сразу появляется на доске. Пустая доска показывает подсказку «Перетащите проект сюда».
6. Скрытие влияет только на отображение: если у скрытого проекта задача ждёт человека или есть инцидент, значок остаётся у проекта в сайдбаре.
7. Набор и порядок дорожек запоминаются между запусками (локально в приложении, демону не нужны).
8. Дополнительный компактный вид группирует столбцы видимых проектов по типу стадии, на карточке чип с именем исходной стадии; задачи в `waiting_human` любой стадии собираются в столбце «ждёт человека».

### UC-16. Маскот проекта
1. При подключении проекту назначается маскот (SF Symbol или эмодзи), стабильный для проекта.
2. Человек может сменить его на любой эмодзи или SF Symbol.
3. Маскот отражает состояние: спит, когда очередь пуста; работает, когда агенты заняты; машет, когда задача ждёт человека; радуется на Done; тревожится при инциденте.
4. Анимированный маскот живёт в сайдбаре и шапке дорожки, на карточке статичная наклейка. Анимации следуют настройке «Уменьшить движение».
5. Для доступности у проекта дополнительно есть фактура края карточки (полоски, точки).

Маскот хранится локально и в репозиторий не попадает.

### UC-17. Агент пытается выполнить запрещённую git-команду
1. Агент запускает git-команду, которую итоговая политика стадии запрещает (например, `git reset --hard`).
2. Обёртка `git` спрашивает демон, проверка не проходит, и агент **сразу** получает отказ с причиной: «команда запрещена политикой проекта, запрос отправлен человеку; продолжай без неё или дождись разрешения». Агент не ждёт, чтобы не сработал таймаут зависания.
3. В ленте задачи появляется тихая запись об отказе: команда, стадия, какое правило сработало.
4. Под записью у человека (и только у него) две кнопки:
   - **«Разрешить один раз»**: демон выдаёт одноразовое разрешение на эту команду для этой задачи. Если запуск ещё идёт, агент узнаёт о нём в ответе на свой следующий вызов любого инструмента доски (поэтому скилл обязывает регулярно вызывать `report_progress`) и может повторить команду; повтор проходит и списывает разрешение. Если запуск уже закончился, разрешение попадает в промпт следующего запуска этой стадии. Неиспользованное разрешение видно бейджем на карточке, человек может его отозвать.
   - **«Добавить в политику»**: открывается экран git-политики с готовым правилом на уровне проекта или стадии; сохранение это обычный автокоммит `.kaban/`, действует со следующих запусков.
5. Если человек ничего не нажал, отказ остаётся записью в ленте, задача работает дальше.

Альтернативы:
- **Команда из жёстких правил** (`push`, сдвиг `main`, запись в `.kaban/`) → отказ сразу, кнопок «разрешить» нет, в ленте объяснение, почему это не настраивается.
- **5 отказов за запуск** → запуск останавливается, `waiting_human: git_denials` со списком отказов. Человек может расширить политику, выдать разовые разрешения, дать подсказку, сменить модель или вернуть задачу в Backlog.
- **Демон не отвечает обёртке** (например, перезапускается) → команда отклоняется, а не пропускается.
- **Агент вызвал git в обход обёртки** → фильтр это не ловит, срабатывает UC-18.

Детали механизма: архитектура, раздел 8.3.

### UC-18. Инцидент: агент изменил то, что ему нельзя
1. После каждого запуска демон сверяет основной репозиторий со снимком: `main`, другие ветки, теги и `config` не сдвинулись; в ветке задачи нет правок `.kaban/`; коммиты задачи лежат поверх её базы.
2. Совпало → задача идёт дальше.
3. Не совпало → демон откатывает refs из снимка, задача в `waiting_human: incident`, в ленте красная плашка инцидента (что изменилось, в каком запуске, лог агента), инцидент появляется в разделе «Инциденты» сайдбара и увеличивает его счётчик, приходит уведомление с повышенной важностью, маскот проекта тревожится.
4. Человек выбирает: вернуть на стадию с замечанием, сменить модель, ужесточить политику или отменить задачу.

5. Инцидент считается разобранным, когда человек выбрал действие по задаче; он остаётся в разделе «Инциденты» как история, но уходит из счётчика.

Правила: инцидент не входит в лимиты возвратов и попыток; после инцидента задача сама никогда не продолжается. Архивная ветка `kaban/archive/<task-id>`, созданная демоном, инцидентом не считается.

### UC-19. Настроить git-политику проекта
1. Человек открывает настройки проекта, раздел git, выбирает пресет.
2. Переключает отдельные команды в таблице «разрешено / запрещено» и при необходимости переопределяет политику на стадиях.
3. Видит итоговую политику каждой стадии; жёсткие правила показаны строками с замком.
4. Сохраняет; демон валидирует и автокоммитит `.kaban/`. Новые правила действуют со следующего запуска.

### UC-20. Cursor недоступен или разлогинен
`cursor-agent` и аккаунт Cursor одни на весь Мак, поэтому это флаг всего Мака, а не проекта.
1. Демон проверяет раннер при старте, раз в 5 минут и по кнопке «Проверить снова»: бинарь есть по сохранённому пути, отвечает `--version`, аккаунт залогинен (без запуска модели).
2. Проверка не прошла → над доской баннер «Cursor недоступен» с причиной (не найден, не запускается, не выполнен вход) и кнопкой «Проверить снова». Новые запуски не стартуют ни в одном проекте, задачи остаются `queued`, текущие запуски доигрывают.
3. **Реактивный путь.** Запуск упал с ошибкой авторизации → флаг включается сразу, запуск уходит в `retry_wait: runner_auth`, попытка не списывается. Так разлогин ночью не сожжёт ретраи и не отправит всю доску в `waiting_human`.
4. Человек чинит причину на Маке (например, выполняет `cursor-agent login` сам) и жмёт «Проверить снова» или ждёт плановой проверки. Флаг снимается, ожидающие запуски продолжаются, планировщик берёт новые задачи.

Уведомление приходит один раз при включении флага, а не на каждую задачу.

### UC-21. Проверка квоты перед стартом (опция)
Опция выключена по умолчанию и помечена «неофициально»: Cursor не даёт публичного API остатка для личных планов.
1. Человек включает опцию в настройках Мака «Квота Cursor» и явно соглашается, что Kaban будет только читать токен Cursor на этом Маке и запрашивать один метод статистики. Выбирает интервал опроса (1, 5, 15, 30 минут или своё значение) и пороги для Cm и Om (по умолчанию 10%).
2. Демон опрашивает остаток с выбранным интервалом и после каждого завершённого запуска. В менюбаре и в блоке «Этот Мак» видны две полосы, Cm и Om, со временем до сброса, отметкой порога и долей прошедшего цикла.
3. Перед каждым стартом запуска (взятие из Backlog, переход в следующую стадию, ретрай) планировщик берёт свежие данные (не старше 60 секунд) по пулу явной модели стадии.
4. Старт разрешён, если остаток минус запас на уже идущие запуски в этом пуле выше порога. Запас считается по среднему расходу одного запуска, пока истории нет, 2% на запуск.
5. Ниже порога → запуск не создаётся, задача остаётся в `queued` с подписью «Ждёт квоту Om · сброс через 13 д», не держит очередь и не занимает WIP-слот; ретрай при этом попытку не списывает.

Альтернативы:
- Om ниже порога, а Cm ещё есть → встают только стадии на моделях из Om, стадии на `composer-*` работают.
- Данным больше 30 минут, токен протух или запрос не прошёл → остаток считается неизвестным, проверка перед стартом пропускается и работает только реактивная схема (UC-09).
- Опция выключена → шага 3 нет, только UC-09.

Правила: токен только читается, хранится только в памяти и никогда не обновляется Kaban (иначе Cursor может разлогинить IDE); сессия браузера не используется.

### UC-22. Cursor подменил модель
1. Демон стартует агента с явной моделью и сверяет название модели из первого события потока с названием из справочника моделей.
2. Названия совпали → работа идёт дальше.
3. Название известно и не совпало → демон сразу останавливает процесс, до первого вызова инструмента: клон чистый, квота почти не потрачена, попытка не списывается и в `max_runs_per_task` не считается. Результат не принимается.
4. Задача уходит в `waiting_human: model_substituted`, на модель ставится флаг «подменена»: остальные задачи на этой модели ждут в `queued` и не стартуют по очереди.
5. Человек видит прямо, что причина в подмене. На карточке строка «Подмена: Opus 4.5 → Sonnet 4». В деталях рядом блоки «Запрошена» и «Ответила» (название и id), `fallbackModel`, если он был в ошибке, время, номер запуска и ссылка на лог. Баннер над доской один на модель и считает стадии, как у пулов: «Cursor подменяет Opus 4.5 · 2 стадии».
6. Варианты: «Повторить» на той же модели, «Другая модель» (только явная), «В Backlog».

Альтернативы:
- Названия нет в справочнике или оно неоднозначно → это не подмена: в ленте серая строка `model_unconfirmed`, задача идёт дальше.
- Флаг модели снимает проба (не чаще раза в 10 минут), в которой пришло ожидаемое название, или человек вручную. Ждавшие задачи стартуют сами, а задача, на которой поймали подмену, остаётся у человека, чтобы он увидел, что произошло.
- Подмену посреди сессии поток не показывает; поймать можно только расхождение на старте (уточняется в спайке 1).

### UC-23. Стадия без модели
1. У агентской стадии не указана модель или стоит `auto` (шаблон нового проекта, ручная правка файла).
2. Весь пайплайн проекта некорректен: флаг проекта «пайплайн некорректен», ни одна задача проекта не стартует ни на одной стадии, идущие запуски доигрывают.
3. В шапке дорожки янтарная плашка со списком стадий, например «Пайплайн не запустится: нет модели у Test», и кнопка «Указать модели», которая открывает редактор на первой стадии с ошибкой. Шапки этих столбцов получают знак.
4. В редакторе пустые поля модели подсвечены, внизу список ошибок, «Сохранить» неактивна, пока у всех стадий нет явной модели. Все пустые модели заполняются за одно сохранение.
5. После сохранения корректной версии флаг снимается сам, проект начинает брать задачи.

Правила: задачи в Backlog создавать можно, они ждут. Модель, которая была указана, но потом пропала из списка Cursor, это не этот сценарий, а флаг модели (UC-09 в).

### UC-24. Настроить MCP для запусков проекта
1. Человек открывает настройки проекта, вкладку «MCP». Первым показан сервер доски, он включён всегда и не отключается. Ниже серверы из `.cursor/mcp.json` проекта и личные серверы человека, у каждого переключатель, по умолчанию выключенный.
2. Человек включает нужные серверы. Белый список хранится локально на Маке. В настройках стадии можно выбрать серверы только из этого списка; по умолчанию стадия получает только сервер доски.
3. Перед каждым запуском демон сам собирает конфиг MCP: сервер доски плюс серверы, которые выбраны у стадии и есть в белом списке проекта. Сервер, выбранный у стадии, но выключенный в белом списке, не подключается, а в редакторе стадии подсвечивается предупреждением: это не ошибка, пайплайн остаётся валидным и «Сохранить» не блокируется. Токен доски передаётся только через окружение процесса и в файлы не пишется. Перед проверкой результата `.cursor/mcp.json` в клоне возвращается к версии из `main`, так что подмена не попадает в diff ветки.
4. Перед стартом демон проверяет, какие серверы на самом деле видит `cursor-agent`.

Альтернативы:
- CLI видит хоть один сервер вне собранного конфига → запуск не стартует, проект получает флаг «недоступен: лишний MCP-сервер» с его именем; человек убирает сервер или включает его явно.
- Как скрыть личные серверы из `~/.cursor/mcp.json` и подключить сервер доски без записи в репозиторий, уточняется в спайках 1 и 2.

## 5. Открытые вопросы
- **Паузы между ретраями** (ждёт Артёма): 3 попытки с паузами 30 с и 2 мин или 4 попытки. До решения в спеке стоит первый вариант.
- **Ждут утверждения презентации и в v0.7 не внесены:** состав трёх git-пресетов («Строгий» только чтение и коммит демоном, «Стандартный» как сейчас, «Свободный» плюс `stash`, `rebase`, `reset` в своей ветке), вкладка git в настройках проекта с переопределениями в стадии, проверка подозрительных файлов (`suspicious_files`) по всему diff ветки.
- Вопрос к дизайнеру из архитектуры (приоритет отображения бейджей на карточке) на поведение не влияет.

## 6. Что зависит от спайков
- Можно ли продолжить сессию после `request_human` в headless-режиме (спайк 1); если нет, стадия стартует заново с ответом в контексте.
- Отдаёт ли `cursor-agent` стоимость и токены (спайк 1), нужно только для метрик.
- Как распознаются rate-limit, исчерпанная квота, недоступная модель, молчаливый выход и ошибка авторизации в выводе `cursor-agent` и какой командой проверить вход без запуска модели (спайк 1, с фикстурами для тестов).
- Где CLI сообщает фактическую модель и видна ли подмена при `fallbackModel` и `--resume` (спайк 1).
- Формат `--list-models`, `mcp list`, отдельный `HOME` без потери логина CLI, где лежит токен CLI, чтение данных Cursor IDE из-под LaunchAgent (спайк 1); подключение MCP без записи в репозиторий (спайк 2).
- Запрет агенту читать данные Cursor IDE и изоляция токена CLI (спайк 6).
