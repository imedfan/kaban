# FE-22: функциональная, визуальная и сквозная приёмка

30 октября 2026. Ветка `codex/fe-22-acceptance` от проверенного после
`git fetch origin` main `593e755` (BE-28, PR #131). Рабочее дерево перед началом
чистое. Source первого прогона автоматизации — `440f766`, финальный QA source —
`8a041a2` (исправлено foreground activation и сохранение launch errors).

**Статус: частичная приёмка; FE-22 и MVP не закрыты.** Полный основной путь
с установленным XPC/helper и четырьмя платными Cursor runs не выполнен.
Ни один платный запуск или системная регистрация в этом инкременте не сделаны.
Ниже автоматические результаты, конкретные blockers и продолжение installed-проверки.

## Что можно повторить

`tools/check-frontend-acceptance.py` собирает один evidence manifest с командами,
exit codes, временем, logs, JSON и кадрами настоящего WindowGroup. Новая папка
на каждый прогон исключает старые успешные файлы. Ошибка, timeout, отсутствующий
report или частичный статус не становятся успехом. Результаты следующих шагов
сохраняются после отказа. Четыре Python tests проверяют эти границы.

Debug содержит opt-in QA; production Release не содержит fixtures/BoardQA.
Оба bundle: ad-hoc подпись App/helper/shim, Hardened Runtime, без App Sandbox.
Проверки состава и подписей читают реальные Mach-O/codesign. Это ещё не
SMAppService, installed XPC или TCC. Developer-проверки используют отдельные
SQLite/Git каталоги в `/tmp`, синтетический CLI и штатный bundled daemon по stdio.

```sh
swift build
KABAN_SCENARIOS=Scenarios/M1 swift test
xcodebuild -project Kaban.xcodeproj -scheme Kaban \
  -destination 'generic/platform=macOS' -derivedDataPath /tmp/kaban-fe22-app \
  ONLY_ACTIVE_ARCH=YES CODE_SIGN_STYLE=Manual CODE_SIGN_IDENTITY=- \
  ENABLE_HARDENED_RUNTIME=YES build
xcodebuild -project Kaban.xcodeproj -scheme Kaban -configuration Release \
  -destination 'generic/platform=macOS' -derivedDataPath /tmp/kaban-fe22-app \
  ONLY_ACTIVE_ARCH=YES CODE_SIGN_STYLE=Manual CODE_SIGN_IDENTITY=- \
  ENABLE_HARDENED_RUNTIME=YES build
python3 tools/check-frontend-acceptance.py \
  --app /tmp/kaban-fe22-app/Build/Products/Debug/Kaban.app \
  --release-app /tmp/kaban-fe22-app/Build/Products/Release/Kaban.app \
  --bin-dir "$(swift build --show-bin-path)" \
  --output /tmp/kaban-fe22-evidence
python3 tools/test-frontend-acceptance.py
python3 tools/check-project-context.py
```

`--core-tests` добавляет полный прогон в manifest; без него Swift test выполняется
отдельно, как выше. Нужна активная GUI-сессия; строгое владение фокусом остаётся
assertion. HEAD/dirty diff hash в manifest — наблюдение checkout, для prebuilt
products дополнительно записываются hashes executable. Связь с source задают
команды сборки и неизменность кода между build/run, а не сам HEAD во время запуска.

280100864/322715648 байт. Итого два процесса на профиль/тему в двух проходах,

85.97–92.86 с; большой stall воспроизводится без параллельного Swift test.
Причинное ускорение/регрессию между двумя проходами не заявляем.

успех прежнего локального build не заменяет этот результат.

## Конкретные blockers

1. **DoD шаг 5: гейтов нет в новом шаблоне.** `StoreProjects.swift`, addProject,
   вызывает `prepareTemplate(identity:commandId:)` без обнаружения команд;
   `PipelineTemplate.defaultYAML` не содержит `gates`. `detectGates` — отдельный
   read. Найденный текст в `ProjectLifecycleSheet` не означает применение.
   Требуются BE-33/FE-26; требования не сокращены до ручного заполнения YAML.
2. **DoD шаг 6: нет «Указать модели».** `BoardView.swift`, laneBody, выводит
   первый ValidationIssue, без требуемого перехода к выбору моделей. FE-24 открыт.
3. **DoD шаг 7: нет начального приоритета.** `Commands.swift` задаёт
   `createTask(projectId:title:body:)`; `setPriority` — отдельная команда.
   Требуются BE-32/FE-28, это не атомарное создание с priority.
4. **Доступность не принята.** У `TaskCardView` есть label и default action,
   но children `.contain`; требуемых роторов «ждут человека / инциденты / дорожки»
   в App нет. VoiceOver, физические клавиши/drag, Reduce Transparency и Increase
   Contrast не проверялись. QA override Reduce Motion подтверждает только этот
   путь views, не системную настройку. Полную доступность по снимку не заявляем.
5. **Stress 10×500 задерживает main actor.** В первом light-процессе все 90
   событий применились, но это заняло 89.92 с; максимальный heartbeat gap 9.69 с,
   peak RSS 319160320 байт. Это функциональная завершённость workload, а не
   отзывчивость. Секундный `sample` и `ps` показали CPU одного ядра и повторные
   SwiftUI transactions, в частности `BoardView.lanes` →
   `BoardProjection.columns(for:)` с проходами taskOrder для каждой стадии.
   Требуется отдельное исправление/повтор; обещания 60 FPS не приняты как gate.
6. **Installed/live доказательства отсутствуют на текущем source.** Исторические
   FE-32 и BE-22 подтверждают свои SHA и не закрывают обновлённый App/helper,
   production Seatbelt run, notifications/reboot или универсальную изоляцию
   credentials. Ограничения BE-28/29 и UC-22 сохраняются.

## Продолжение установленной приёмки

Основной сценарий и бюджет — [DoD §0.3](mvp-fix-tasks.md#03-определение-готовности-mvp-ручная-сквозная-проверка).
Его инструкция: «Платные запуски выполняет **сам Артём на своём Маке**».
Поэтому автоматизация их не инициирует. Четыре приёмочных старта остаются
неиспользованными; модель из BE-22 — `cursor-grok-4.6-medium`, перед запуском
снова проверить наличие в бесплатном каталоге. Два старта спайка уже израсходованы.

После устранения blockers основного пути:

1. Использовать отдельную macOS учётную запись/чистое окружение данных;
   существующий `~/Library/Application Support/Kaban` не удалять. Сохранить SHA,
   `sw_vers`, `xcodebuild -version`, бесплатные `cursor-agent --version`,
   `status --format json` (в отчёт только auth boolean) и id модели из каталога.
2. `KABAN_LOCAL_DERIVED_DATA=/tmp/kaban-fe22-installed tools/package-local-app.sh`.
   Сохранить signing report, установить Release bundle в `/Applications`,
   открыть его обычным способом. Через онбординг разрешить службу в Login Items
   и системные permissions при запросе. Записать status `подключено` и один
   helper PID/path; не запускать демон вручную и не заполнять SQLite.
3. Указать Cursor, проверить version/auth/git/sandbox и каталог. Перезапустить
   App; подтвердить сохранение пути и отсутствие второй регистрации. Добавить
   отдельный тестовый git repo с первым commit и локальной веткой без `main`;
   выбрать эту базу в нативном picker. Проверить один template commit, только
   `.kaban/`, и автоматически найденные гейты у dev/merge. Если их нет — остановить
   приёмку до платных запусков.
4. Через «Указать модели» применить полный Dev/Test/AI Review шаблон с явной
   `cursor-grok-4.6-medium` у трёх agent стадий. Создать одну маленькую задачу
   с критериями и priority. В описании явно потребовать сначала вызвать
   `request_human` с выбором приветствия, дождаться ответа, затем реализовать
   выбранный вариант и завершить стадию через MCP. Зафиксировать текст задачи.
5. Вести ledger **каждого** фактического `-p`: runID/stage, requested/actual model,
   start/end, exit/endReason, MCP result, gate result, screenshot, оплаченный
   номер 1…4. Первый dev спрашивает, второй dev продолжает после ответа,
   третий test, четвёртый ai-review. Отдельные автоматические model probes тоже
   являются платными стартами: при любой ошибке/молчаливом выходе сразу поставить
   Mac на паузу и сверить ledger до продолжения; не разрешать дополнительные
   старты сверх бюджета. Непройденную стадию записать отказом.
6. Проверить OS question notification/ответ, menubar count, progress и реальные
   argv/Seatbelt/shim/MCP-конфиг. Не сохранять токены/env credentials в evidence.
   После ai-review проверить review notification и открытие точной задачи.
7. Без Cursor: проверить summary/files/commits/gates, «Открыть в Cursor»,
   approve → rebase/gates/fast-forward **выбранной** базы → Done; сравнить git log
   и GitIdentity, сохранить run history. Закрыть/открыть окно, App и helper;
   проверить ту же БД, IDs, ответы, pending resolution и merge. Обновить bundle
   с теми же identifiers, снова проверить сохранность. Reboot делает Артём;
