# FE-03: нативный онбординг и среда Cursor

7 октября 2026. Ветка `codex/fe-03-onboarding` перенесена на актуальный main
`ff04e05` после принятия FE-02 в [PR #93](https://github.com/imedfan/kaban/pull/93).
Это отдельный frontend-инкремент. Полная приёмка FE-03 остаётся открытой:
публичные environment-команды и системная установка helper не завершены у бэкенда,
первый проект подключает следующий AddProjectFlow FE-04.

## Что реализовано

Первый запуск и пункт «Служба Kaban → Настройка Kaban…» открывают один
SwiftUI экран. Он показывает подключение службы, факты Cursor, необязательные
уведомления и автозапуск App. Контент прокручивается, footer с переходом к доске
остаётся доступен. Runner не готов или его готовность неизвестна — Backlog
остаётся доступен после настоящего handshake/catch-up.

Helper использует существующий SMAppService lifecycle. requiresApproval и отказ
не показываются как успешное соединение. Возврат в приложение перепроверяет
статус: разрешённый helper проходит handshake, отзыв разрешения закрывает старый
transport и возвращает настройку. Оборванную сессию можно переподключить прямо в настройке. Инициализация принадлежит runtime, закрытие
SwiftUI view не отменяет общий RPC и не запускает вторую регистрацию.
Developer private stdio и явные fixtures остаются отдельными режимами.

`RunnerEnvironmentStore` получает `getCursorEnvironment` / `checkEnvironment`
через тот же KabanClient. Проверяет тип и commandId ответа, сохраняет черновик
при повторном чтении и отклоняет ответ прежнего поколения сессии. Последние
данные после reconnect или ошибки помечаются устаревшими. Отсутствующий report
остаётся неизвестностью. CLI, версия, auth, git и sandbox не подменяются
проверками клиента или успешными значениями fixtures.

Путь выбирается нативным NSOpenPanel либо вводится вручную. Пустое поле означает
discovery только после успешного чтения конфигурации. `configureCursor` и
`recheck(.runner)` проходят обычный durable journal BoardSession; scope runner
проверяется по capabilities. `.ok` не означает сохранение пути. После restart
pending configure восстанавливает точный envelope/ввод, до correlated event
или покрывающего snapshot не становится успешным. После applied UI автоматически перечитывает сохранённую конфигурацию. Старый GET не заменяет новый
ввод. Login выполняет человек в Терминале; секреты приложение не собирает.

Уведомления проверяются у UNUserNotificationCenter самого App, а не по значению
daemon report. Запрос разрешения идёт только по кнопке; отказ имеет инструкцию
в системные настройки и не блокирует доску. Автозапуск SMAppService.mainApp
включается явным переключателем; requiresApproval показывает отдельное действие.
В developer/fixture автозапуск выключен. Завершение настройки хранится локально,
отдельно для installed/developer режима.

Дополнительно `BoardSession.stop()` перед передачей транспорта новому владельцу
сохраняет неизвестный исход отправляемых commands и запрещает поздние RPC/events
перезаписывать журнал следующей сессии. Это защищает отключение/переподключение
helper, не меняя backend state machine.

## Что остаётся открытым

1. В `DaemonService.support` checkEnvironment/getCursorEnvironment/configureCursor
   всё ещё unsupported. UI показывает это; сохранение path и факты настоящего
   окружения на чистой БД нельзя объявить принятыми. Конкретные источники и
   необходимая интеграция — [отдельный файл](frontend-backend-integration-gaps.md).
2. Штатная register → Settings → XPC → restart/reboot приёмка зависит от
   [BE-20](backend-launch-agent-2026-10-06.md). Системная регистрация/реальный
   CLI login в этом UI smoke не выполнялись.
3. Первый проект через UI, его folder permissions и исправление доступа — FE-04.
   Четыре полных критерия FE-03 оставлены незакрытыми до live-приёмки.
4. Developer native launch 7 октября один раз дошёл до реальной БД/создания,
   затем остановился на старой smoke-проверке метаданных. Она требовала reply и
   event одновременно: это расходилось с FE-02, где typed event может подтвердить
   потерянный reply, а после retention — исходный receipt и покрывающий snapshot.
   Driver теперь проверяет эти два доказательства, applied phase, точный payload,
   project/task и одну creation; acceptance недостаточен. Последующие две попытки
   LaunchServices (в том числе fresh) снова не создали WindowGroup: runtime=nil,
   windows=[]; успешного final developer report нет. Тот же startup симптом
   ранее воспроизводился на сохранённом FE-01 bundle. Причина не установлена,
   assertions сохранены; live-приёмка остаётся открытой.
5. Fixture keyboard smoke прошёл на этом App; полный системный compositor,
   VoiceOver и штатный helper не проверены.

Недостающие кадры онбординга записаны в
[frontend-design-gaps](frontend-design-gaps.md). Технические зависимости бэка
не считаются недоработками дизайнера.
