## Изменения

Клиент больше не сохраняет и не восстанавливает security-scoped bookmarks.
App/helper работают без App Sandbox по BE-21 и архитектуре §13. Старые bookmarks
не нужны для этого режима и не определяют доступность проекта. Путь из
NSOpenPanel поступает в существующий ProjectLifecycleStore; доступ проверяет daemon.
При отмене диалога черновик сохраняется.

CI собирает Debug и Release с ad-hoc подписью и проверяет готовые App/helper.
Инструкции запуска и формат будущих FE-отчётов указывают конфигурацию подписи.
Release сохраняет Hardened Runtime и не содержит QA или demo types.

## Конфигурация проверки

- Debug: `KABAN_QA`, ad-hoc подпись App/helper, Hardened Runtime, без App Sandbox.
- Release: обычная поставочная конфигурация, ad-hoc подпись App/helper,
  Hardened Runtime, без App Sandbox, QA отключён.
- Native integration: настоящий bundled daemon, private stdio и отдельные
  тестовые SQLite/Git данные. Cursor CLI не запускался, платная квота не расходовалась.
- Release установлен в `/Applications/Kaban.app` и открыт для ручного одобрения.
  Подписи установленной копии повторно проверены. Сам запуск не подтверждает installed XPC.
- Среда: macOS 27.0.1 `26A434`, Xcode 27.0 `27A266a`.
  CDHash установленного App: `413b923a991008f65068def097dce8d40944ec5d`;
  helper: `f0b5e2509512c1b86e22c974f753f74329357ba0`.

## Повторение

```sh
xcodebuild -project Kaban.xcodeproj -scheme Kaban -configuration Debug \
  -destination 'generic/platform=macOS' -derivedDataPath /tmp/kaban-fe32-debug \
  CODE_SIGN_STYLE=Manual CODE_SIGN_IDENTITY=- ENABLE_HARDENED_RUNTIME=YES build
python3 tools/check-local-client.py --app /tmp/kaban-fe32-debug/Build/Products/Debug/Kaban.app
KABAN_LOCAL_DERIVED_DATA=/tmp/kaban-fe32-release tools/package-local-app.sh
KABAN_SCENARIOS=Scenarios/M1 swift test --filter 'ProjectLifecycleTests|ProjectLifecycleStoreTests|DaemonInstallationTests'
```

Driver сохраняет JSON, логи и кадры в новом `/tmp/kaban-fe32-*`, проверяет
освобождение writer lease после каждого завершения App/helper и оставляет
тестовые репозитории на диске. Для открытия клона нужен установленный Cursor.

## Ручная часть Артёма

Инструкция DOC-03 дополнена в [getting-started](../getting-started.md#личная-сборка-app-и-be-20).
В открытом `/Applications/Kaban.app`:

Если окно не появилось, выбрать **Открыть настройку Kaban…** в менюбар.

1. Через **Объекты входа…** разрешить Kaban работать в фоновом режиме и дождаться
   подключения. **Открывать при входе** относится к отдельному автозапуску App;
   для этого шага включать его не требуется.
2. При блокировке запуска использовать **Конфиденциальность и безопасность → Всё равно открыть**.
3. В разделе уведомлений нажать **Разрешить…** и подтвердить системный диалог.
4. Через **Выбрать…** подключить тестовый git-проект. При запросе доступа helper
   к Documents или Desktop подтвердить системный диалог.
5. После перезапуска App/helper проверить тот же проект, его задачи и чтение
   веток. После перемещения папки выбрать новый путь через relink.
6. Проверить **Открыть в Cursor** и **Показать в Finder** в установленной конфигурации.

Результат Артёма получен частично: фоновая работа разрешена, installed XPC
подключился после перерегистрации helper. FE-04 #4, выбор папки/TCC после
restart, уведомления и полная ручная приёмка FE-32 остаются открытыми.
Developer private stdio не закрывает эти критерии.

## Отказ после одобрения службы

Артём подтвердил включённый переключатель **Kaban.app** снимком от 15 октября
22:11:10 и прислал ошибку подключения снимком 22:12:01 в этой переписке.
Временные файлы вложений уже недоступны, их копии в Git не сохранены.
Само состояние `enabled` не подтверждает запуск helper.

Во время отказа `launchctl print gui/501/app.kaban.agent` показывал повторные попытки запуска,
`spawn failed`, `last exit code = 78: EX_CONFIG`, без живого KabanDaemon.
Актуальный debug log launchd сообщает:

```text
Could not find and/or execute program specified by service: 3: No such process: Contents/MacOS/KabanDaemon
```

Установленный файл существует, запускается с `--help`, его подпись проходит
проверку. Старый `daemon.log` со строками `notBundled` имеет дату 9 октября;
он не подтверждает причину текущего отказа. Обновление регистрации приложения
в LaunchServices через `lsregister -f` этот отказ не устранило.

Три отдельные одноразовые проверки SMAppService с уникальными ID дали
реальный запуск helper: минимальный ad-hoc bundle, вариант без CFBundleVersion
с конфигурацией LaunchAgent Kaban и неизменённый подписанный KabanDaemon с
private scratch DB/stdio. [Результаты](screenshots/fe-32/service-probes.json)
подтверждены созданными файлами, не одним статусом `enabled`. Каждый probe
выполнил unregister; тестовые bundles удалены. Основная служба и БД не менялись.

Эти проверки исключают общее утверждение «ad-hoc helper здесь не запускается».
После **Служба → Перезапустить службу**, который вызывает unregister/register,
Артём ответил «Подключилось». Проверка launchd подтвердила `running`, `runs = 1`,
PID `57457`, без завершений. `proc_pidpath` связал живой PID именно с
`/Applications/Kaban.app/Contents/MacOS/KabanDaemon`.
[Проверка процесса](screenshots/fe-32/installed-running.json) сохранена отдельно.
При включённой службе **Проверить снова** только повторяет подключение.
Почему прежняя системная регистрация потеряла привязку к bundle, не установлено;
восстановление через unregister/register подтверждено. Проверки BE-21 относятся
к своему source и не перенесены на текущий installed XPC.
