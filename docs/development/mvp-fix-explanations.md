## A. Установка, служба и окружение Cursor
Задачи: BE-21, BE-23, FE-23, FE-32, PRE-01.

**Поведение по спеке и архитектуре.**
- Демон — LaunchAgent внутри bundle, регистрируется через `SMAppService.agent`, единственный писатель БД. Закрытие окна не влияет на задачи (арх. §1).
- Приложение: Hardened Runtime, Developer ID, **без App Sandbox** (арх. §13). **Для MVP (ответ Артёма 9.10):** сертификата Apple нет и не будет; сборка локальная, ad-hoc, без App Sandbox. Developer ID, нотаризация и проверка Team ID — не для MVP.
- **Ручное одобрение** (документирует DOC-03): после первого открытия Артём включает Kaban в «Системные настройки → Основные → Объекты входа» (статус `requiresApproval`); если macOS блокирует запуск ad-hoc приложения — «Конфиденциальность и безопасность → Всё равно открыть»; разрешение уведомлений — системный запрос при первом уведомлении (FE-21). До одобрения онбординг показывает «требует одобрения» и кнопку перехода в настройки (FE-23).
- LaunchAgent не получает PATH из shell. Путь к `cursor-agent`, PATH и тулчейны демон берёт из своего конфига: детект при первом запуске через login shell, правка в настройках (арх. §6.2).
- Проверка раннера при старте, раз в 5 мин и по «Проверить снова»: бинарь по сохранённому пути, ответ `--version`, вход без запуска модели (спека UC-20 п.1, арх. §3.2).
- Провал проверки → флаг Мака `runner_unavailable`. Задачи остаются `queued`, текущие запуски доигрывают (UC-20 п.2).
- Реактивный путь: ошибка авторизации в run → флаг сразу, run в `retry_wait: runner_auth`, попытка не списывается (UC-20 п.3).
- UC-01, альтернатива: если `cursor-agent` не найден или не залогинен, проект **всё равно добавляется**, над доской баннер «Cursor недоступен».
- Список моделей обновляется при старте демона и раз в сутки (спека §1.6, §4). После настройки пути — сразу (BE-23).

**Онбординг** (`docs/frontend/projects-and-onboarding.md`, 3.11):
1. `SMAppService.agent(...).register()`. При `.requiresApproval` кнопка «Открыть Объекты входа», статус перепроверяется при возврате в приложение, затем XPC-ping.
2. `SMAppService.mainApp` — автозапуск менюбар-аппки.
3. `requestAuthorization` для уведомлений; шаг можно пропустить.
4. `checkEnvironment`: путь и версия `cursor-agent`, `authOK`, git, `sandboxOK`. Путь можно указать вручную. Для логина — инструкция «`cursor-agent login` в Терминале» и «Проверить снова» (`recheck(.runner)`).
5. Первый проект.

**Контракт** (арх. §5):
- `checkEnvironment() -> { cursorAgentPath, version, authOK, gitVersion, sandboxOK, notificationsAuthorized }`.
- `getCursorEnvironment` / `configureCursor(environment: CursorEnvironment)`:
  - `executablePath = nil` — discovery, иначе абсолютный путь executable;
  - credentials, argv и произвольный env не передаются;
  - ответ на query — `cursorEnvironment`; применённая настройка подтверждается журнальным `cursorEnvironmentChanged`.
- `recheck(scope: .runner | .project(id))`, capability `scopes: ["project", "runner"]`.
- Флаг `runner_unavailable`, причины: `agent_missing`, `agent_not_runnable` (не отвечает `--version`), `agent_not_logged_in`, `runner_auth`. Снимается успешной проверкой (арх. §3.2).

**Тексты.**
- Баннер: «Cursor недоступен: не найден / не запускается / не выполнен вход / ошибка авторизации».
- Кнопка «Проверить снова».
- Подсказка «выполните `cursor-agent login` в Терминале» (`docs/frontend/board-and-cards.md` 3.1).
- Спека UC-20 п.2 требует «Cursor недоступен» с причиной из трёх: не найден, не запускается, не выполнен вход.

**Краевые случаи.**
- Путь не задан на новой БД → это `agent_missing`, а не «pending навсегда». Задачи не резервируются, карточки остаются в `queued`.
- Путь задан, но CLI обновили и бинарь переехал → плановая проверка через ≤5 мин поднимает флаг. «Проверить снова» с новым путём через `configureCursor`.
- Developer-режим App (`DaemonRuntime.swift:192`) берёт тот же сохранённый environment, а не аргументы.
- Отказ системного согласия на helper (`denied`) не выглядит как подключение (критерий FE-03).
- Уведомление о `runner_unavailable` — одно при включении флага, не на каждую задачу (UC-20).
- Без Sandbox клиенту не нужны security-scoped bookmarks: доступ к папке проекта у демона обычный. TCC для Documents и Desktop запрашивается системным диалогом у helper (пояснения архитектора §1). Проверить на сборке с подписью (FE-32).

## B. Запуск агента: argv, промпт, сверка модели, пробы
Задачи: BE-22, BE-24, BE-25, BE-30.

**Запуск** (арх. §6.1, флаги уточняет спайк 1):
- `cursor-agent -p --output-format stream-json --model <id> [--force] --approve-mcps "<prompt>"`;
- cwd — клон задачи, свой process group, запуск внутри Seatbelt;
- `--model` передаётся **всегда**: без него CLI берёт Auto, а Auto запрещён (спека §0, §1.6);
- `--force` только для write-стадий; read-only стадия без `--force`.
- Существующая реализация: `Sources/KabanKit/Agent/CursorLaunch.swift`, `plan()` и `render()`. Сейчас `plan()` не добавляет `--approve-mcps`; после спайка 1 решить по факту.

**Промпт собирает демон** (арх. §6.1, спека §1.5 «Вход»):
- скилл стадии (файл из версии пайплайна, с которой задача вошла в стадию);
- задача и критерии приёмки;
- handoff-резюме прошлой стадии;
- замечания возврата и вывод гейтов;
- действующие git-разрешения (`git_grants`);
- обязательство закончить `complete_stage` / `return_to_stage` / `request_human` и вызывать `report_progress` хотя бы раз в несколько минут.

После `gate_failed` и `no_final_call` следующая попытка продолжает работу в том же клоне, в промпт добавляются вывод гейта или напоминание закончить через `complete_stage` (спека §1.4).

**HOME run** (арх. §9; BE-24): процесс агента получает отдельный HOME, чтобы личный `~/.cursor/mcp.json` не был виден агенту. Если по итогам спайка 1 CLI теряет логин с отдельным HOME, применяется запасной способ из §9, который фиксирует архитектор. Запреты Seatbelt при этом строятся от **реального** HOME пользователя.

**Смена модели для задачи** (`setModelOverride(taskId, stageId, model)`, F13) перекрывает модель стадии только для этой задачи.

**Сверка модели** (UC-22, арх. §6.4):
- Фактическая модель приходит в первом событии `system/init`, только отображаемым именем. Сравнивается с `model_catalog.name` для запрошенного id.
- Имя совпало → работа продолжается.
- Имя известно и не совпало → процесс убивается **до первого вызова инструмента**. Попытка не списывается, в `max_runs_per_task` не считается. Задача в `waiting_human: model_substituted`, флаг модели `substituted`.
- Имени нет в каталоге или оно неоднозначно → серая строка `model_unconfirmed` в ленте, run продолжается.
- Тексты (UC-22 п.5–6):
  - карточка — «Подмена: Opus 4.5 → Sonnet 4»;
  - детали — блоки «Запрошена» и «Ответила» (название и id), `fallbackModel`, время, номер запуска, ссылка на лог;
  - баннер — «Cursor подменяет Opus 4.5 · 2 стадии»;
  - варианты — «Повторить», «Другая модель», «В Backlog».
- Если CLI не даёт гарантии остановки до инструмента, это фиксируется по итогам спайка (критерий BE-14:426) и правится арх. §6.4.

**Классификация** (арх. §6.4):
- `usage limit` / `spendLimitHit` → `usage_exhausted` на пул модели; пул неизвестен → на весь Мак (`unknown`). Дата сброса — `billingCycleEnd` или разбор `chatMessage`.
- `resource_exhausted` / «not available in the slow pool» → флаг модели `unavailable`.
- Прочий rate-limit → `rate_limited`, cooldown 15 → 30 → 60 мин.
- Run, получивший лимитную ошибку, попытку не списывает.

**Пробы** (спека §1.4, UC-09; арх. §6.4; §4):
- Молчаливый выход: агент вышел без единого вызова инструмента и без изменений файлов → `retry_wait: silent_exit`, попытка пока не списывается, демон **делает** пробный запуск: та же модель, короткий промпт.
- Одна проба на модель за раз, не чаще раза в 10 минут.
- Нашлась лимитная причина → флаг по UC-09. Проба прошла чисто → это обычный сбой, попытка списывается задним числом.
- Флаг модели (`unavailable`, `substituted`) снимает проба с ожидаемым именем в `init` (не чаще раза в 10 мин), появление модели в каталоге или `clearModelFlag`.
- `usage_exhausted` с неизвестной датой: флаг **висит до ручного снятия**, раз в 6 часов проба; чистая проба снимает флаг (спека UC-09 б п.3; арх. §3.2). Сейчас код снимает флаг по времени (`StoreLimits.swift:63`, `SchedulerInputs.swift:54`) — это и чинит BE-30.
- Карточка во время ожидания пробы: «Проверяем выход CLI» (`CardPresentation.swift:32`). Задача в `retry_wait` держит слот (спека §1.4), поэтому без пробы слот занят навсегда.
- Сама проба — отдельный короткий запуск, а не run задачи (арх. §6.4; сверка архитектора п. A5): она **не занимает WIP-слот задачи**, не появляется в истории запусков задачи, не списывает попытку и не считается в `max_runs_per_task`. Проба — настоящий процесс `cursor-agent`, поэтому **считается в общем потолке процессов Мака** `max_concurrent_runs` (по умолчанию 4), но не занимает WIP стадии и слот проекта. При заполненном потолке проба ждёт свободного места и не вытесняет запуски задач. Правило «одна проба на модель, не чаще раза в 10 минут» остаётся (ответ архитектора 9.10).

**Краевые случаи.**
- Ретрай, упёршийся в квоту или флаг модели, освобождает слот и уходит в `queued` с причиной «на модели флаг» (спека §1.4, UC-09 в п.1).
- Задача, на которой поймали подмену, после снятия флага остаётся у человека (UC-22, альтернативы).
- Подмену посреди сессии поток не показывает (спека §6).
- Run, остановленный из-за подмены, `rate_limit`, `runner_auth`, `daemon_restart` и `silent_exit` не идут в `max_runs_per_task` (арх. §3.2 «Счётчики»).

## C. MCP доски, `/git/check`, shim, Seatbelt
Задачи: BE-26, BE-27, BE-28, BE-29.

**MCP-сервер** (арх. §9, §11):
- Streamable HTTP на `127.0.0.1:<порт>`, `Authorization: Bearer <run-token>`. Токен определяет проект, задачу, стадию и run; отзывается по завершении run.
- Один сервер на все проекты; `/git/check` на нём же.
- Инструменты (F5): `get_task_context`, `report_progress(text)`, `complete_stage(summary, artifacts?)`, `return_to_stage(target, issues[])`, `request_human(question)`.
- Нелегальный переход возвращает понятную ошибку; повтор в рамках run идемпотентен. Ответ любого инструмента может нести `notices[]` (git-разрешения, ответ человека).
- `complete_stage` задачу сам не двигает: дальше демон после зелёных гейтов и проверки результата (арх. §3.3).
- Run завершился без финального вызова → `retry_wait: no_final_call`.

**Конфиг MCP на run** (UC-24 п.3, арх. §9):
- Состав: сервер доски с `${env:KABAN_RUN_TOKEN}` плюс серверы, выбранные у стадии **и** включённые в allowlist проекта.
- Сервер выбран у стадии, но выключен в allowlist → его нет в конфиге. Валидатор даёт предупреждение `mcp_not_allowlisted`, «Сохранить» не блокируется.
- Файл подменяет `.cursor/mcp.json` клона; если файла не было — добавляется в `info/exclude`. Перед проверкой результата файл возвращается к версии из `main`.
- Перед стартом демон в том же окружении выполняет `cursor-agent mcp list`. Хоть один сервер вне конфига → run не стартует, проект `unavailable: mcp_unexpected` с именем сервера.
- Текст в шапке дорожки: «Запуск не стартовал: CLI видит лишний MCP-сервер «<имя>»», кнопки «Открыть MCP» и «Проверить снова» (`board-and-cards.md` 3.1).

**Git shim и `/git/check`** (арх. §8.2 п.2, §8.3; спека UC-17):
- Обёртка берёт `KABAN_RUN_TOKEN` и перед каждой командой делает `POST /git/check { argv, cwd }`.
- Порядок проверки: жёсткие инварианты → итоговая политика стадии → `git_grant` (`uses_left = 1`, живёт до конца задачи). Списание — в той же транзакции.
- Отказ мгновенный. Текст — **по спеке UC-17 п.2** (арх. v0.11.27, §8.3 п.3): «команда запрещена политикой проекта, запрос отправлен человеку; продолжай без неё или дождись разрешения». Сейчас код использует «жди» (`GitCheck.swift:8`); правка входит в BE-27.
- Событие `git_denied`, счётчик отказов run +1. На 5-м отказе run останавливается → `waiting_human: git_denials`.
- Нет ответа от демона → отказ (fail closed).
- «Разрешить один раз» (`allowGitOnce(denialId)`):
  - run жив → уведомление в ответе на следующий вызов любого инструмента доски;
  - run закончился → вход `git_grants` следующего run и промпт (`GitGrantDelivered.via = next_prompt`).
- «Добавить в политику» (`addDenialToPolicy(denialId, scope)`) — обычная правка `.kaban/` с автокоммитом. Уже работает через draft (`StorePipelines.swift:156-200`).
- Жёсткие правила (спека §1.5): `push`, `remote`, `config`, `tag`, `force`, `foreign_refs`, `kaban_dir`. Для них кнопки «разрешить» нет.

**Seatbelt** (арх. §8.2 п.3, §6.3) — подробно в разделе архитектора ниже, п.4. Коротко:
- закрыто только `.git/config`, `.git/hooks/`, `.git/info/` и `.kaban/` клона;
- objects, refs, index, logs, HEAD доступны, иначе агент не закоммитит в «Стандартном» и «Свободном» пресетах;
- запреты чтения строятся от реального HOME;
- запись разрешена в служебные каталоги `cursor-agent` по минимальному списку из спайка 1 (BE-22 → BE-28; сверка п. A2), иначе `-p` под профилем не заработает;
- параметр `MCP_PORT` профиля = порт MCP-сервера host из BE-26 (сверка п. A3);
- сетевой allowlist и прокси вне MVP, решаются после спайка 6 (арх. v0.11.27).

**Краевые случаи.**
- Рестарт демона: старые токены отозваны (`restart_revoked`). Живые runs по правилам recovery (BE-18) уходят в `retry_wait: daemon_restart`. Новый run получает новый токен и порт.
- Агент вызвал `/usr/bin/git` в обход shim: фильтр не ловит, ловит проверка результата (UC-18). Это принятое поведение (арх. §8.2 п.2).
- Read-only стадия: политика сужена до чтения; изменения в клоне после run → откат и `retry_wait: readonly_violation`; второе нарушение за заход → `waiting_human: invalid_result` (арх. §6.1).

**Правила.**
- Под флагом задачи остаются `queued`: новые запуски не стартуют, текущие доигрывают (спека §1.1).
- Флаг модели останавливает только стадии на этой модели.
- Причины на карточке в `queued`:

## E. Подключение проекта: базовая ветка, гейты, модели
Задачи: BE-31, BE-33, FE-24, FE-26, FE-27.

**Поведение** (UC-01):
1. Человек выбирает папку и **базовую ветку** (обязательно в MVP, решение Артёма 9.10). Подсказка «i» у поля: «От этой ветки создаются ветки задач, в неё же вливается результат».
2. Демон проверяет git-репозиторий и окружение; определяет автора коммитов (это уже работает, тексты совпадают со спекой).
3. Есть `.kaban/pipeline.yaml` → используется он. Иначе галочка «Создать шаблон `.kaban/` и закоммитить» (по умолчанию включена). Моделей в шаблоне нет, поэтому проект сразу получает флаг «пайплайн некорректен» со списком стадий без модели (UC-23).
4. Спека сейчас: человек **подтверждает команды гейтов**. **Решение 9.10 (Артём + архитектор):** шага подтверждения нет. Демон определяет команды по файлам сборки и молча ставит их гейтами на `dev` и `merge`; гейт проверяется на выходе стадии по `complete_stage`; убрать можно в редакторе пайплайна; ничего не найдено — гейтов нет. Лист только сообщает результат. Спека правится в DOC-06.
5. Маскот по сиду = id проекта; дорожка появляется на доске.
6. «Указать модели» на дорожке → сохранение → флаг снимается, проект берёт задачи.

Альтернатива: галочку шаблона сняли → проект с флагом «недоступен: нет пайплайна», задачи можно заводить, в шапке «Проверить снова». Демон кладёт заглушку Backlog (`StoreProjects.swift:168`).

**Контракт сейчас** (арх. §5):
- `addProject(path, createTemplate, identity?)`;
- `listBranches(projectId)`;
- `detectGates(projectId)`;
- `updatePipeline(projectId, contentHash)`, `validatePipeline`, `validatePipelineDraft`, `getPipelineSource`.

**Решения архитектора** (арх. v0.11.27, §5):
- **базовая ветка (BE-31, P0)** — выбор обязателен (решение Артёма 9.10):
  - `addProject(path, createTemplate, identity?, baseBranch?)`; `nil` = `main` (старый клиент);
  - ветка должна существовать локально, иначе `CommandError base_branch_missing` с `params.branch`; текст UI «Локальной ветки «{branch}» нет в этом репозитории»;
  - ветка отдаётся в `ProjectSummary.baseBranch` (`nil` только у старого демона);
  - всё, что сейчас зашито как `refs/heads/main`, берёт базу проекта; источник правды — `<base>:.kaban/`;
  - смены базы у существующего проекта в MVP нет: в настройках ветка только показывается;
  - подсказка «i» у поля в листе (FE-27): «От этой ветки создаются ветки задач, в неё же вливается результат»;
- **гейты (BE-33)** — вопрос 7 закрыт 9.10: подтверждения нет, результат `detectGates` автозаполняет поле `gates` в `addProject` (поле остаётся для этого), проверка на выходе стадии по `complete_stage`:
  - `addProject(..., gates: [String]?)` действует только при `createTemplate = true`; команды вписываются в шаблон до единственного коммита `.kaban/`, второго коммита нет;
  - `createTemplate = false` и непустой `gates` → `invalid`: для готового пайплайна это `updatePipeline` из редактора;
  - команды ставятся в `gates` стадий `dev` и `merge` (повтор после rebase, §8.5); на `test` и `ai-review` не ставятся, это агентские проверки;
  - ничего не найдено → гейтов нет; убрать найденные — в редакторе пайплайна.

**UC-23** (стадия без модели):
- плашка в шапке дорожки: «Пайплайн не запустится: нет модели у Test», кнопка «Указать модели» открывает редактор на первой стадии с ошибкой; шапки этих столбцов получают знак;
- в редакторе пустые поля модели подсвечены, внизу список ошибок, «Сохранить» неактивна, пока у всех стадий нет явной модели; все пустые модели заполняются за одно сохранение;
- после сохранения корректной версии флаг снимается сам.

Модель, которая была указана, но пропала из списка Cursor, — это флаг модели (UC-09 в), а не UC-23.

**Пикер модели** (спека §1.6):
- `auto` нет в списке; `composer-*` разрешена;
- рядом с моделью виден пул (Cm или Om);
- новая модель без ручного исключения → значок «проверь пул», по умолчанию Om;
- пустой каталог — следствие ненастроенного Cursor, а не отсутствия моделей. Поэтому нужен переход к настройке Cursor (FE-24).

**Краевые случаи.**
- Репозиторий с `master` и без `main`. Сейчас отказ (`TaskClone.swift:112`, `rev-parse --verify refs/heads/main`). После BE-31 — работает с `baseBranch: "master"`; ветка, которой нет локально, даёт `base_branch_missing` у поля ветки с текстом «Локальной ветки «{branch}» нет в этом репозитории» (ответ архитектора 9.10; в спеку вносит DOC-06). 
- Шаблон коммитится только при checkout базовой ветки и без конфликтующих `.kaban/` файлов (арх. §5, BE-02); другие ветки не переключаются.
- Гейты для Merge-стадии: по спеке F9 «гейты после rebase». Найденные команды ставятся и в `dev`, и в `merge`; лист (FE-26) после добавления пишет «Гейты: swift build, swift test — добавлены в Dev и Merge» (предложение аналитика, текст не утверждён).

**Отмена и архив** (UC-07 п.3, UC-11, UC-25 п.4):
- галочка **«оставить ветку»**;
- с галочкой копия ветки сохраняется в основном репозитории как `kaban/archive/<task-id>` (так говорит спека); без галочки в основном репозитории ничего не остаётся;

Сейчас код пишет скрытый `refs/kaban/archive/<id>` (`TaskClone.swift:97`). **Артём подтвердил видимую ветку 9.10** (вопрос 3 закрыт), спека не меняется;
- архив создаёт демон при отмене, после снимка refs, поэтому проверка результата (BE-13) его не трогает;
- UI показывает имя, пришедшее от демона, подпись галочки везде — «Оставить ветку» (FE-29).

**Подписи лимитов** (спека §1.3, дословно):
- Настройки пайплайна: «Общий лимит возвратов» (`bounce_limit_total`, 5) и «Лимит возвратов» у пары (например, «Test → Dev: 3»).
- Причина на карточке и в ленте — заголовок плюс уточнение. На карточке заголовок слева, уточнение справа. В ленте одна строка через « · », например «Лимит возвратов · при конфликте, 2 из 2».
- Уточнения:
  - общий (`bounce_limit_total`): «общий, 5 из 5»;
  - пара `returns_to`: «<откуда> → <куда>, 3 из 3», имена стадий из пайплайна, например «Test → Dev, 3 из 3», «AI Review → Dev, 2 из 2»;
  - `on_fail.limit`: «при красном гейте, 3 из 3»;
  - `on_conflict.limit`: «при конфликте, 2 из 2»;
  - `run_limit`: заголовок «Лимит запусков на задачу», уточнение «12 из 12».
- Лист «Вернуть…»: «Всего возвратов N/лимит» (сумма `bounceByReason`) и «<откуда> → <куда> N/лимит».
- Бейдж возврата на карточке: «возврат 1/3» (UC-05 п.3).

**Краевые случаи.**
- После конфликта задача **всегда** снова идёт через Human Review (спека §0).
- `requestChanges` на read-only стадию → `invalid_state`; `moveTask` туда разрешён (спека §1.3).
- Стоимость: если CLI её не отдаёт (спайк 1), поле `nil`, UI не рисует 0.

# Пояснения архитектора к задачам «рабочее MVP»

Срез `main` `484b78d`. Это раздел для документа аналитика: по пяти пунктам, где одной задачи мало, ниже записано, что уже решено в архитектуре (v0.11.26) и чего она требует от реализации. Если реализации нужно отступить от этих пунктов, сначала правится архитектура, а не код.

## 0. Общее предусловие: живой Cursor CLI на Маке Артёма

Спайк 1 (флаги `-p`, auth из-под launchd, `system/init`, `mcp list`, отдельный HOME) и спайк 6 (Seatbelt) на настоящем залогиненном CLI так и не проведены: во всех отчётах бэка CLI «Not logged in». Пункты 2, 3 и 4 ниже без этого не принять.
- Нужен Мак Артёма с залогиненным `cursor-agent` и согласием на платные запуски `-p` для приёмки. Это делает Артём сам, агенту логин не передаётся.
- Результат спайков фиксируется фикстурами в `research/` и попадает в архитектуру. Только после этого закрываются критерии BE-07/10/14.

## 1. App Sandbox и подпись helper

**Решено (§13):** Hardened Runtime, без App Sandbox, Developer ID.
- В `Kaban.xcodeproj` для App (Debug и Release) стоит `ENABLE_APP_SANDBOX = YES`, а в `App/KabanApp/Kaban.entitlements` есть `com.apple.security.app-sandbox`. Это противоречит §13 и ломает SMAppService: sandboxed App не регистрирует unsandboxed LaunchAgent (macOS 14.2+).
- Задача — убрать Sandbox у App и проверить register / requiresApproval / XPC / restart / unregister / reboot на реальной сборке. Отказ автопроверки при прошлой попытке был из-за отсутствия явного разрешения. Решение уже есть в архитектуре, и в задаче на него нужно прямо сослаться.
- Security-scoped bookmarks без Sandbox не обязательны. Доступ к папке проекта у демона обычный, через права пользователя; TCC-разрешения на защищённые папки (Documents, Desktop) берутся системным диалогом у helper. Проверяется на реальной сборке.
- Подпись: пока сертификата Apple нет, сборка ad-hoc, а клиент сверяется по signing ID и хешам (это уже сделано в BE-20). Критерий «другой Team ID отвергается» остаётся открытым до появления сертификата. Для MVP на своём Маке это не стопер, но в задаче это нужно записать честно.

## 2. Как штатный демон получает runner и путь к Cursor

**Решено (§6.2, §5):** путь к `cursor-agent`, PATH и тулчейны лежат в конфиге демона. При первом запуске они определяются через login shell и правятся в настройках, а `configureCursor` / `getCursorEnvironment` / `checkEnvironment` — это wire-команды.
- Аргументы `--runner` и `--cursor-agent` остаются только для разработки и диагностики. `--launch-agent` должен брать путь из сохранённого environment в БД, без аргументов.
- Агентский run в штатном режиме = `CursorCLIDriver`. Он собирает промпт и argv через уже существующие `KabanKit/Agent/CursorLaunch.swift` (`render`, `plan`) из frozen RunSpec. Сейчас `StoreProcesses.swift` запускает runner со статичными аргументами, и это нужно заменить вызовом драйвера. Модель передаётся всегда, `auto` запрещён.
- Вход промпта (§6.1): скилл стадии из версии pipeline, задача и критерии, handoff, замечания возврата и гейтов, действующие git-разрешения (`git_grants`, отсюда `GitGrantDelivered.via = next_prompt`), правила финального вызова и `report_progress`.
- Сверка модели (`observeModelInit`) должна вызываться штатным парсером stream на `system/init`. Сейчас её вызывают только тесты.
- Auth из-под launchd — это спайк 1. Запасной вариант — `CURSOR_API_KEY` из Keychain в env процесса, а не в argv, БД или логах.
- Пока путь не задан или проверка не прошла, проект показывает `runner_unavailable`, и задачи не стартуют. Нельзя делать «молча pending навсегда».

## 3. Время жизни MCP-сервера и `/git/check`

**Решено (§9, §8.3):** один loopback-сервер на `127.0.0.1`, `Bearer <run-token>`. Токен определяет проект, задачу, стадию и run, и отзывается по завершении run. `/git/check` работает на том же сервере.
- В штатном демоне сервер должен подниматься при старте host, до scheduler'а, и жить всё время работы демона. Сейчас `MCPBoardServer` создаётся только в `--mcp-pass`.
- Порт выбирается при старте и передаётся в RunSpec / env run и в собираемый `.cursor/mcp.json` клона. Токен попадает туда только как `${env:KABAN_RUN_TOKEN}`.
- После рестарта демона старые токены отзываются (`restart_revoked` уже есть). Recovery переводит живые runs по правилам BE-18, а новый run получает новый токен и новый порт.
- `recheck(project)` и старт run выполняют свежий `cursor-agent mcp list` в окружении run (fail closed, §9). Это producer для снятия `mcp_unexpected` (FE-16).
- Поведение без финального вызова (`no_final_call`) и при молчаливом выходе (проба) уже описано в §6.4. Проба должна реально выполняться, а не только записываться. Иначе задача навсегда остаётся в `retry_wait(silent_exit)` и держит WIP (находка аналитика).

## 4. Seatbelt: что закрыто в `.git` клона

**Решено (§8.2 п.3, §6.3):** агент запускается внутри Seatbelt вместе со всеми своими потомками.
- Сейчас `SeatbeltProfile` используется только в тестах, а в продакшене `sandbox-exec` не вызывается. Задача — запускать драйвер через профиль.
- Профиль сейчас запрещает запись во **весь** `.git` клона, а это ломает §6.3: в «Стандартном» и «Свободном» агент коммитит сам. По архитектуре запрещена запись только в `.git/config`, `.git/hooks/`, `.git/info/` клона, плюс в `.kaban/` клона. Остальное содержимое `.git` (objects, refs, index, logs, HEAD) агенту доступно.
- В «Строгом» агент не коммитит, но и там запись в index нужна: её используют `git status` и `git add`, разрешённые политикой. Запрет записи в `.git` здесь тоже не нужен. Коммит запрещает git-политика, а не файловая система.
- Запрещены запись в основной репозиторий, `~/.gitconfig`, `Application Support/Kaban`, а также чтение `~/.ssh` и `globalStorage` IDE. Пути берутся **от реального HOME пользователя**, не только от подменного HOME run: иначе абсолютный путь обходит запрет.
- Сеть команд агента идёт по allowlist хостов, на loopback — только порт MCP. Прокси для allowlist в коде нет (`PROXY_PORT` объявлен, но не используется). Как разделить CLI и его инструменты (CLI вне профиля, инструменты внутри) — цель спайка 6. Пока он не проведён, действует остаточный риск из §13: токен CLI читаем изнутри профиля. Это принятый риск, а не стопер MVP.
- Настоящая граница — проверка результата демоном (§8.2 п.4, BE-13). Она уже работает и не ослабляется.

## 5. Как shim попадает в PATH агента

**Решено (§2, §8.2 п.2):** `KabanGitShim` — отдельный executable, «первый в PATH» агента. Он не является границей, это фильтр и источник понятных отказов.
- Сейчас target `KabanGitShim` в `Package.swift` отсутствует, а env агента (`environmentForAgentRun`) содержит только минимальный набор и токен.
- Нужно: собрать shim в bundle рядом с helper, на каждый run класть в PATH run каталог с `git`, который указывает на shim, первым в списке, и передавать адрес `/git/check` и токен через env.
- Shim вызывает `/git/check`, при `allow` делает exec настоящего git по абсолютному пути, а при отказе отдаёт текст отказа и ненулевой код. Если демон недоступен — fail closed.
- Обход через `/usr/bin/git` архитектура признаёт сознательно. Жёсткие инварианты (`push`, `remote`, `config`, запись в `.kaban/`) дополнительно идут в правила `cursor-agent` (§8.2 п.1) и ловятся проверкой результата.

**BE-36, имя архива.** Правильное имя — `kaban/archive/<task-id>` как **видимая ветка** (`refs/heads/kaban/archive/<task-id>`). Спека в UC-07, UC-11 и UC-25 обещает пользователю «оставить ветку», а скрытый ref это обещание не выполняет. §8.1 исправляю под §3.3.
