## Поведение и границы

App использует существующий DaemonKabanClient/DaemonRuntime и KabanTransport.
KabanClient принимает полный CommandEnvelope и возвращает CommandReply без
потери commandId/seq/result; legacy convenience send возвращает result и
используется только там, где caller не ведёт отправку. BoardStore mutations
используют полный reply. `readLog`/`tailLog`, capabilities и session updates
доступны всем экранам через тот же клиент, без нового transport или автомата.

Capabilities проверяются до подключения и после каждого нового connected.
Отсутствующие session operations и несовместимый protocol отклоняют handshake;
missing/unsupported/managedFakeOnly команды не включают production-действие.
Mock перечисляет только свои реализованные действия и явно отказывает в логах.
Команды и связанные кнопки/меню отключены до connected и при отсутствии поддержки.
«Новая задача» в native menu валидируется AppKit по текущему BoardStore;
доступность не фиксируется в первоначальном SwiftUI command tree.

ClientCommandJournal сохраняет исходный envelope до отправки, receipt и
correlated seq в KeyValueStoring. Installed/developer/fixture имеют отдельные
ключи; developer разделяется также по пути БД. Сохраняются все неразрешённые
отправки и до 100 предыдущих resolved receipts. Повреждённый журнал не
подменяется пустым: ошибка видна, новые mutations блокируются.
Потерянный ответ отмечает неопределённую доставку, не снимает pending и не
создаёт новый commandId. Snapshot replacement сам по себе не сбрасывает создание.
`.ok` и correlated event не подтверждают завершение внешнего process/git effect.

Обычный запуск использует installed XPC; developer — embedded private stdio с
отдельной БД; fixture — только явный preview/QA. Источник данных виден в сайдбаре,
путь developer БД доступен в подсказке. Повтор developer подключения закрывает
предыдущий transport перед запуском writer. Runtime/store принадлежат App;
выбор карточки не создаёт клиента. Отмена подписки отменяет forwarding/poll task.

FE-02 остаётся отдельной задачей: replay/reconciliation сохранённых requests
после reopen/retention, drafts, детали и исходы внешних effects. Наличие
ClientCommandJournal не считается выполнением всей FE-02.

## Проверки

- `KABAN_SCENARIOS=Scenarios/M1 swift test`: **516 tests, 0 failures**;
  все пять test executables завершились успешно (27 + 64 + 180 + 174 + 71).
  Включены legacy Protocol fixtures, transport и BoardCore.
- Пять новых ClientCommandJournalTests: точный envelope после reopen/lost reply,
  конфликт commandId, ack без event, event до reply, отказ/corrupt storage,
  truthful mock capabilities/log failure и обязательные session capabilities.
- Unsigned `xcodebuild`, generic macOS, `/tmp/kaban-fe01-app`: build succeeded.
  SwiftPM/Xcode запускались с разрешённым доступом к cache после sandbox ошибки
  `sandbox-exec: sandbox_apply: Operation not permitted`; тесты не ослаблялись.
- Настоящее WindowGroup с embedded daemon, временный git repo и отдельная БД:
  create/edit/pause/resume/cancel прошли через correlated journal, Markdown
  сохранён. Fault injector теряет ответ create **после настоящего commit**;
  transport retry повторяет исходный envelope, в snapshot ровно одна новая задача.
  Receipt содержит commandId/seq, клиентский журнал содержит correlated seq.
- Через тот же live клиент вызваны capabilities, readLog и tailLog. Несуществующий
  run вернул ошибку backend, не пустой успех/fixture log.
- Повторный запуск с той же БД восстановил task/body/journal, seq 23.
- Fixture UI smoke прошёл: create/edit/move/cancel, pause/resume, search/filter,
  настоящие Cmd-N/Cmd-F. Отдельные assertions проверили выключение native
  «Новая задача» при reconnect и повторное включение после connected.
  Keyboard QA сначала явно делает WindowGroup key window. Assertions сохранены.
  Проверка выявила stale disabled menu item; production исправление использует
  NSMenuItemValidation с тем же BoardStore. Поздний createdTaskID не закрывает
  форму, открытую для новой отправки.
- Отдельный live handshake с неверной версией capabilities response отклонён:
  runtime.store остаётся nil, ошибка показана, developer child закрыт, mock не создан.

## Визуальная проверка настоящего окна

Сценарий FE-01 — подключение к службе/ошибка и выбор реального источника.
Источники: base композиция и [tokens](../../design/tokens.css), актуальная доска
v0.2 и карточки v0.2.1. Отдельного reference подключения нет: пробел записан в
[списке дизайнеру](frontend-design-gaps.md).

Проверены обе темы, 1440×900 и минимум 1040×640 pt, длинная service error,
protocol error, existing board при reconnect и fixture-доска с длинными названиями.

кнопки видны. Новый источник данных помещается в карточке «Этот Мак».
Основная композиция доски сохранена; на минимуме стадии доступны через
горизонтальную прокрутку. Нет попытки сжать все столбцы до нечитаемых карточек.

## Оставшаяся системная зависимость

Штатные register/Mach XPC/restart/unregister/reboot не приняты: см.
[BE-20](backend-launch-agent-2026-10-06.md), sandboxed App против unsandboxed helper.
FE-01 не меняет этот security setting и не регистрирует системную службу для smoke.
Paid Cursor/MCP и полного сквозного pipeline эти проверки не запускали.
Шаблон нового QA-проекта без model остаётся invalid; это ожидаемое требование,
не основание ослабить валидатор.
