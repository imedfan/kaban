Дата: 4 октября 2026, Europe/Kaliningrad. Ближайший контрольный срок — до начала спайков в понедельник, 5 октября. План актуализирован после выполнения сессии; фактические PR, SHA и проверки — в общем отчёте. По указанию пользователя Designer полностью исключён.

Журнал утверждённых решений учитываем первым; архитектура определяет статусы и XPC, спека — поведение продукта. При противоречии фиксируем вопрос владельцу, не выбираем новое поведение самостоятельно. В каждом результате записываем версию документа и SHA прочитанного кода.

Локальная исходная база: `main`, SHA `1d647eaf9f937780b8a78dbd6bf5db94a5b98f64`. GitHub подтвердил мерж [PR #5](https://github.com/imedfan/kaban/pull/5) и [PR #8](https://github.com/imedfan/kaban/pull/8). Поэтому ограничения «ждать #5» для B2–B4 и «ждать закрытия TODO(protocol)» для F-T2-1…3 уже выполнены. Перед фактическим стартом задачи повторно проверяем актуальный `main` и новые пересечения с основной командой.

В коде уже реализованы три библиотеки SwiftPM: `KabanProtocol`, `KabanKit`, `KabanBoardCore`. В KabanKit есть MiniYAML, валидатор, git-политика, GitIdentity/DaemonGit и чистый автомат задач; в BoardCore — проекция, подписки, pending-команды, правила переноса и маскоты. `KabanDaemonCore`, GRDB, полноценный планировщик и производственные app/daemon/CLI-таргеты в текущем Package.swift отсутствуют. Их реализация остаётся у основной команды. Спайки уже подготовлены в `spikes/backend/` и `spikes/frontend/`.

README в корне всё ещё говорит о пустых модулях и старой зависимости BoardCore от KabanKit. Локальные спека v0.7.2, архитектура v0.11.1 и план фронта v0.5.2 также отстают от Drive. Это важно для аудитов: не создавать ложные находки по старой копии. Сам README и существующие документы не меняем.

## 3. Координатор / Team Lead

Исполнение: координатор ведёт Analyst, публикацию и CI; три параллельных субагента
выполняют Backend, Architect/security и Frontend. Все субагенты — `gpt-6.1-sol`,
`medium`, как запросил пользователь. Одновременно максимум четыре агента с root.
Роли переиспользуются последовательно внутри независимых веток `team2/…`.
Системные настройки, политика подтверждений и авторизация аккаунтов не менялись;
проектные/временные действия выполнялись в рамках выданного разрешения.


Владелец сборки результатов и передачи основной команде; решения по продукту и мерж остаются у Артёма.

1. Зафиксировать одну рабочую версию каждого источника, SHA базы, владельца каждой задачи. Для одинаково названных файлов Drive использовать ID и версию, а не имя.
2. До понедельника принять P0 у Backend и Architect: каждый открытый вопрос должен иметь конкретную проверку на mbp. Упорядочить прогон 1 → 2 → 6 и таблицу «результат → последствие для архитектуры → кому вопрос».
3. Вести зависимости между ролями и общий список находок; одна проблема — один issue, остальные отчёты ссылаются на него.
4. Проверять ветки `team2/…`, базу PR `main`, разрешённый diff, тесты и CI. Ориентир размера PR — около 400 строк; крупную задачу предварительно разбить на именованные подзадачи с самостоятельными результатами.
5. Собирать один `docs/team2/team2-report-YYYY-MM-DD.md` на сессию по разделу 4 чек-листа: настоящие PR, SHA, проверки, решения, незавершённое, проблемы, вопросы, влияние на других, воспроизведение. По ролям — приложения и ссылки, а не конкурирующие общие отчёты.
6. Перед передачей материалов другой команде обеспечить ей чтение чек-листа и опорных документов. Получателей/группу доступа пока не указали; не считать доступ нашего подключения подтверждением их доступа. Самостоятельно не включать публичный доступ по ссылке.

Дополнительные задачи координатора: T6 getting-started (P1); T12 сравнение лицензий и T13 черновик CONTRIBUTING (P2). T14 — совместно с Backend. Технические и юридические утверждения при выполнении исследований подтверждать актуальными первичными источниками.

## 10. Проверки и передача

Для каждой задачи: одна ветка `team2/<роль>-<id>-<суть>`, один PR в `main`. Перед ревью проверить diff: только новые разрешённые файлы. Существующие Sources, тесты, Scenarios, spikes, design, документы, README и CI не менять. Изменения Package.swift требуют отдельного решения Артёма.

Базовые команды для PR:

```bash
swift build
KABAN_SCENARIOS=Scenarios/M1 swift test
```

Для AN3 отдельно:

```bash
KABAN_SCENARIOS=docs/team2/analyst/scenarios swift test --filter ScenarioDecodeCheck
```

Linux Swift 6 — обязательный CI-сигнал, macOS-job сейчас необязательный. Локальная проверка на новом Apple Swift не заменяет Linux Swift 6.0 и спайки macOS 26. Точные результаты исходного прогона этой сессии — в [отчёте](team2-report-2026-10-04.md).

При подтверждённом дефекте создаём issue `[team2-review] …`: severity, версия источника, SHA, файл:строка, ожидание/факт, минимальное воспроизведение. Production-код не исправляем. Изолируем только новый Team2-тест дефекта через доступный на целевом тулчейне XCTSkip/withKnownIssue со ссылкой на issue; существующие тесты не отключаем. XCTExpectFailure не считать переносимым на Linux без проверки. Пробел в спецификации оформляем вопросом, не выдумываем ожидаемое поведение.

Координатор принимает P0, когда каждый вопрос из спеки §6/архитектуры §14 покрыт проверенным ответом либо точной командой проверки на mbp; есть версии CLI/ОС, ожидаемые результаты и схема фикстур, нет секретов. Сырые stream-json/stderr требуют проверки и маскирования перед коммитом.

Координатор принимает P1/P2, когда критерии задачи выполнены, проверены реальные результаты, CI последнего SHA зелёный, подтверждённые находки имеют issues, а незавершённое отражено в общем отчёте. PR не мержит никто из второй команды. Работы передаются Артёму для мержа и владельцам основной команды для решений.
