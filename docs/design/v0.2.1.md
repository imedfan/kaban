## Токен и значок `suspicious_files` (для фронта)

| Что | Значение |
|---|---|
| Токен | `--st-suspicious`, `--st-suspicious-bg`, `--st-suspicious-fg` — **алиасы** `--st-waiting*` (тот же янтарь «нужно внимание»). Отдельного цвета нет. Класс состояния `.st-suspicious` |
| Значок | `shieldalert` — щит с восклицательным знаком (lucide `shield-alert`). SwiftUI: `Image(systemName: "exclamationmark.shield")` |
| Чем отличается от других `waiting_human` | только значком: у остальных причин `hand`, у `review` — `usercheck` (бирюзовый) |
| Красный | **не используется**. `--st-incident` и значок `siren` — только у `waiting_human · incident`. `suspicious_files` — не инцидент (арх. §3.2, §8.2) |
| Статус-пилюля в панели | `waiting_human · suspicious_files` на янтарном, значок `shieldalert` |
| «Запрещено» в git-таблицах | серое: `--pol-deny` в `../tokens.css` теперь #7d828c (тёмная тема #7b7f88), переопределение в `v021.css` убрано. Жёсткие правила — `--pol-locked` с замком и штриховкой |
| Тег правила | `pattern` → «по шаблону `<pattern>`» (значок `file`, янтарный), `size` → «больше 5 МБ» (значок `box`, серый). «Похоже на секрет» и «> 5 МБ» не используются |
| Ссылка у файла | «дифф» — при `isText && sizeBytes < max_file_mb`, открывается в Cursor по `TaskDetail.clonePath`; иначе — «Показать в Finder». `isText` демон берёт из `git diff --numstat` (арх. §6), от правила (`pattern` / `size`) ссылка не зависит |

## Решения макета

- На карточке показано короткое имя файла (basename) и та же причина, что в панели: «по шаблону `.env*`» или «больше 5 МБ» (с размером, если строка одна и помещается). Строк не больше двух, остальное «+N». Полный путь и размер каждого файла — в панели.
- Карточка не получает бейджей: файлы идут строками под заголовком (как строка подмены модели в v0.2), поэтому правило «не больше двух бейджей» соблюдено.
- Пока ждём ответа на «Принять файлы», на кнопке «Отправлено…» со спиннером, остальные кнопки блока неактивны. Состояние снимается, когда приходит `taskUpdated` с тем же `commandId` (набор пуст, задача уходит дальше) или ошибка (кнопка снова активна, при `stale_suspicious_files` — плашка и перечитанный список).

## Решения макета: лист «Вернуть…»

- Одна кнопка «Вернуть…» в панели (на gate / merge нет «Попросить убрать» как `answerHuman` и поля «Замечание агенту» внизу панели). Лист сверху панели, под её шапкой, — стекло (`glass-strong`): это хром окна. Панель под листом затемнена, путь стадий виден.
- Подпись основной кнопки листа зависит только от поля: пусто → «Принять файлы и вернуть» (`moveTask`), есть текст → «Вернуть с замечанием» (`requestChanges`). Рядом с кнопкой — вызов команды моно, над ней — плашка, принимается ли набор: серо-зелёная галочка «Набор принимается» или янтарный щит «Набор не принимается». Красного нет.
- У каждого файла в листе — что с ним будет: «в принятые · blob» или «останется помеченным».
- «Куда» заполняется из `StageSummary.onFail` (gate) / `onConflict` (merge) по арх. v0.11.5: демон присылает их уже разрешёнными, UI умолчание не вычисляет. Вернуть задачу можно только на agent-стадию с `readOnly = false`: в списке «Куда» read-only стадий нет. `on_fail` без `stage` — ближайшая предыдущая по цепочке `on_success` стадия с `readOnly = false`; `on_conflict` и `requestChanges` без цели — первая agent-стадия с `readOnly = false` (для Human Review — `PipelineSummary.defaultReturnStage`). Явная цель на read-only — `no_return_target` со `stageId` стадии с этим возвратом; ручной `requestChanges` туда — `invalid_state`; `moveTask` разрешён. UI всегда шлёт выбранную стадию явно, обе кнопки одинаково: `moveTask(stage: "test")` / `requestChanges(target: "test")`.
- Счётчики (глоссарий аналитика): «Всего возвратов 4/5» — сумма `bounceByReason` против общего лимита возвратов (`bounce_limit_total`, по умолчанию 5); рядом пара «Checks → Dev 1/3» со своим лимитом возвратов (`returns_to.limit`, `on_fail.limit`, `on_conflict.limit`); подпись «ручной возврат счётчики не меняет». Причина `waiting_human: bounce_limit` показывается как «Лимит возвратов» с уточнением («общий, 5 из 5» или «Test → Dev, 3 из 3»); на экранах v0.2.1 этой причины нет, править было нечего.
- Поле открывается пустым; «Подставить…» под полем вставляет шаблон «Убери из ветки: <пути>» и переключает кнопку на «Вернуть с замечанием» (подтверждено фронтом).

## Автор коммитов (арх. v0.11.21, спека v0.8.23 UC-01)

- Демон подписывает свои коммиты и коммиты агента автором проекта `GitIdentity { name, email }` и передаёт его явно через `-c user.name=… -c user.email=…`. Глобальный git-конфиг пользователя в работе демона не участвует (`GIT_CONFIG_GLOBAL=/dev/null`, арх. §8.2).
- `addProject(path, createTemplate, identity?)`. Без `identity` демон один раз читает автора обычным `git -C <repo> config user.name` / `user.email`, а это конфиг репозитория, глобальный и системный (кадр а). Пробелы по краям демон обрезает; значение из одних пробелов считается пустым (`missing`). Если автора нет нигде или имя / почта пустые, приходит `CommandError identity_required`, и проект не создаётся. Детали — в `CommandError.params`: каждое поле ровно в одном виде — в `missing`, в `invalid` (`name` | `email` | `name,email`) или найденным значением (`name` / `email`). Отклонённое значение не возвращается; `invalid` возможен и на первом вызове без `identity` (арх. v0.11.21).
- **Первый отказ** (вызов без `identity`). Найденные значения подставлены в поля с серой меткой «из настроек git» (значение может прийти из конфига репозитория, глобального или системного, поэтому не «из git репозитория»). Фокус — в первом поле из `missing` или `invalid`. У полей из `missing` подсветки нет. Уточнение под общим текстом плашки — только когда второе поле в `missing`: нашлось только имя → «В настройках git нашлось только имя, почты нет» (кадр б), нашлась только почта → «В настройках git нашлась только почта, имени нет», ничего не нашлось → без уточнения. Если второе поле в `invalid`, уточнения нет, хватает текста под полем (спека v0.8.23, вставка г). Поле из `invalid` пустое, и текст под ним виден сразу, без обводки: «Имя в настройках git содержит служебные символы, укажите вручную» / «Почта в настройках git содержит служебные символы, укажите вручную». «Добавить» повторяет `addProject(path, createTemplate, identity)`.
- **Отказ вызову уже с `identity`.** Поля из `missing` и `invalid` получают оранжевую обводку и текст под полем. По `missing`: «Укажите имя» / «Укажите почту» (кадр в). По `invalid` (перенос строки или NUL): «Имя должно быть в одну строку, без служебных символов» / «Почта должна быть в одну строку, без служебных символов». Если в `params` нет ключей, показывается только общий текст плашки, оба поля без подсветки.
- Строка настроек «Автор коммитов» показывает `ProjectSummary.identity` (приходит в снимке и в `projectUpdated`). Старый демон даёт `nil`, тогда в полях «—», а «Изменить…» доступна. «Изменить…» → `setProjectIdentity(projectId, identity)`: те же проверки и тексты, подсветка сразу (вызов всегда с `identity`), действует с новых коммитов. Так закрыт вопрос 28 фронт-плана (v0.5.33). Фронт-план v0.5.34 (раздел 10) ещё опирается на спеку v0.8.22 и описывает (г) с уточнением «нашлась только почта»; макет следует спеке v0.8.23 — без уточнения.
- Автор хранится у демона на этом Маке, а не в `.kaban/`: `.kaban/` общий через репозиторий, а автор у каждого свой. Это записано в арх. v0.11.20–0.11.21 §8.2 и спеке UC-01. Поэтому пункт «Автор коммитов» стоит в группе «Проект · на этом Маке».
- У зарегистрированного проекта автор есть всегда, поэтому `identity_required` на запуске не бывает. Команды демона, создающие коммиты, без автора не запускаются (`identityRequired` в `KabanKit`).
- Подпись галочки «Создать шаблон `.kaban/` и закоммитить» и тексты под полями взяты из спеки. Почта в примерах — `artem@example.com`. Исходники экрана: `add-project.css`, `add-project.js`, `add-project-identity{,-dark}.html`.
