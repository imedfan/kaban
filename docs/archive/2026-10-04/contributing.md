# Вклад в Kaban: рабочие правила team2

Черновик T13, 4 октября 2026. Основание — [чек-лист второй команды, версия 2, §2 и §6](https://docs.google.com/document/d/1oszVHm1jwJ6HvuQKCnr9Z-6PTICnfJ6_t3csqTWcpk0/edit). Документ создан в docs/; перенос в корневой CONTRIBUTING и изменения README выполняет Артём. Правила ниже относятся к переданной team2 работе, не объявляют новые ограничения для основной команды.

Источники требований читать по свежим версиям: [архитектура v0.11.22](https://drive.google.com/file/d/1q-TwZPODCOF_pogtXJU5N8niNp1ePLEs/view), [спека v0.8.24](https://drive.google.com/file/d/1z7MT3ezZ5V7d5BoIBWaMjnTg_iHMSFKQ/view), [frontend-plan v0.5.36](https://drive.google.com/file/d/1LXl5tv4Wjw6CNfNbs8vezjLSxgkZWtc_/view), [AC v0.1](https://drive.google.com/file/d/14z297h5-6AOABSw-53kHCtnntKW_NxAv/view). Старые копии в репозитории не подменяют свежие документы.

## Ветка, коммит и PR

- Работать только в собственной ветке **team2/**. Одна задача — одна ветка — один PR в **main**. Для отдельной задачи начинать от актуального origin/main; не приносить в PR чужую незамерженную задачу.
- **Мержит только Артём.** Не мержить даже собственный PR; не менять base/head чужого PR и не пушить в чужие ветки. Не ставить approve/request changes от имени основной команды.
- Предпочтительный размер PR — около **400 строк** или меньше. Это ориентир чек-листа; если полный каталог больше, объяснить объём и сохранить одну задачу в PR.
- PR с красным CI не отправлять на ревью. При публикации черновика дождаться проверок; объявлять готовность по результатам конкретного head commit, а не предыдущей версии ветки.
- Для коммитов предлагается короткое описание результата: `docs(team2): catalog Russian frontend strings`, `test(team2): cover projection resync`, `tools(team2): report scenario inventory`. Чек-лист не задаёт обязательный формат: это рекомендация для читаемости, не новый gate.
- Не коммитить секреты, личные контакты/логи, результаты сборки и генерированные проекты спайков. Модель/ключи/токены не добавлять в примеры; использовать явно отмеченные placeholders.

Пример начала отдельной задачи после обновления remote refs:

```bash
git status --short
git fetch origin
git switch -c team2/<задача> origin/main
```

Перед переключением рабочее дерево должно быть свободно от незакоммиченных изменений другой задачи. Не сбрасывать чужие файлы, чтобы получить чистое дерево.

## Занятые зоны

| Зона | Правило team2 / владелец |
|---|---|
| Sources/KabanProtocol/, Tests/KabanProtocolTests/ | Не менять существующие файлы; Architect |
| Sources/KabanKit/ и его тесты | Не менять существующие файлы; Backend |
| Sources/KabanBoardCore/ и его тесты | Не менять существующие файлы; Frontend |
| Scenarios/** | Только чтение; Analyst. Дополнительные сценарии team2 хранить в разрешённой папке docs/team2/analyst/scenarios/ |
| design/**, оригиналы макетов/Penpot, README.md, логотип/баннер | Не менять. В текущем задании человека **все Designer задачи исключены**, включая аудит, копии макетов, контраст/раскладки/тёмные темы/дизайн маскотов |
| docs/architecture* и любые существующие документы docs/ | Не изменять. Создавать только новые документы в разрешённых местах |
| .github/workflows/ci.yml | Не изменять, предложения — отдельный документ |
| Package.swift | Не менять и не добавлять target в рамках team2 без отдельного согласования Артёма, предусмотренного §2 чек-листа |
| Google Drive / Docs | Только чтение в текущем задании; не записывать, не перемещать, не переименовывать и не менять sharing |

Публичные типы протокола не меняются, включая расширения в другом модуле. Факт нахождения проблемы в занятой зоне не даёт разрешения на её исправление.

Разрешённое новое: research/, examples/, tools/, docs/team2/, новые файлы docs/ согласно конкретной задаче. Скрипты Python 3/bash в tools/ живут вне SwiftPM. Для задач роли §6 отчёты класть в docs/team2/<роль>/, когда это указано; явно заданный путь конкретной задачи (например frontend-strings-ru.md) сохранять.

**Узкое исключение для тестов §6:** только **новые** `Tests/<Модуль>Tests/Team2*.swift` и fixtures в `Tests/<Модуль>Tests/Fixtures/team2/`, **ровно в модулях и задачах, разрешённых блоком роли**. Это не общее разрешение писать в любую папку Tests. Существующие тесты не редактировать. F-T2-1…3 начинать только после protocol-v2 BoardCore PR в main (условие выполнено на базе #8); F-T2-4/5 — только новые документы.

Допустимые ключевые решения не «чинить»: у стадии явная модель, Auto/модели по умолчанию нет; MCP по умолчанию только сервер доски, дополнительные — по allowlist; фильтр набора проектов заменён drag/крестиком; GitIdentity хранится у демона на Mac, а DaemonGit работает с GIT_CONFIG_GLOBAL=/dev/null.

## Найденные ошибки и неясности

Ошибку основной команды описывать в отчёте/issue, **не исправлять production или существующие тесты**. Issue содержит файл/строку либо точный раздел/цитату свежего источника, воспроизведение, ожидание, факт и серьёзность; для T9 префикс **[team2-review]**. Сначала проверить существующие issues, чтобы не дублировать одно замечание. Предположение по непроверенному runtime обозначать как вопрос, не как доказанный баг.

Если новый разрешённый Team2-тест выявил баг, §2 требует `XCTSkip`/`withKnownIssue` со ссылкой на issue, чтобы CI оставался зелёным. Для текущих XCTest suites применять подходящий механизм XCTest; не менять framework/package ради упоминания `withKnownIssue`. Не скрывать skip: указать issue и пропущенный сценарий в отчёте. Не ослаблять проверку ради зелёного результата.

Если работа упирается в занятую зону или противоречие, выписать открытый вопрос и продолжить независимую часть задачи. Это не повод вводить подтверждение для каждого нового документа/обратимого действия, уже порученного человеком. Системные настройки, регистрация LaunchAgent, фактические платные CLI-запуски и публикация вне согласованной работы не являются локальной проверкой документа.

## Локальный эквивалент CI

Из корня репозитория, Swift 6:

```bash
swift --version
swift build
KABAN_SCENARIOS=Scenarios/M1 swift test
```

`KABAN_SCENARIOS` обязателен для проверки декодирования сценариев: без него ScenarioDecodeCheck пропускается; папка — Scenarios/M1, не Scenarios. Если задача добавляет разрешённый файл Team2-тестов, дополнительно выполнить содержательный `swift test --filter <Suite>`; до готовности PR полный тестовый прогон остаётся обязательным по CI.

Linux workflow в [.github/workflows/ci.yml](../.github/workflows/ci.yml): `ubuntu-latest`, контейнер `swift:6.0`, build/test. При установленном Docker:

```bash
docker run --rm -v "$PWD":/src -w /src swift:6.0 swift build --scratch-path .build-linux
docker run --rm -e KABAN_SCENARIOS=Scenarios/M1 -v "$PWD":/src -w /src swift:6.0 swift test --scratch-path .build-linux
```

На macOS команды SwiftPM те же; macOS job optional (`continue-on-error: true`), поэтому проверять её conclusion отдельно. Это библиотеки, не запуск приложения/демона, не frontend xcodebuild и не реальные cursor-agent спайки. Не утверждать «прошло на Linux» по локальному Mac-прогону.

При ошибке среды записать toolchain и вывод: например внешняя sandbox может запрещать module cache или добавлять git `confstr()` warning. Production-тесты из-за этого не переписывать. Полный локальный build/test базовых библиотек T6 на macOS27/Xcode27/Swift6.4 прошёл (185 tests, 0 failures вне внешнего sandbox), но каждый PR проверяется на своём head в CI. Отдельного повторного запуска Swift для этого документа не делалось: исходники не менялись.

## Что вернуть в PR/отчёте

1. Что сделано, точный путь нового файла и источник требований; версии свежих документов.
2. Diff только этой задачи; подтверждение, что существующие занятые зоны не затронуты.
3. Команды и итог проверки: ОС/toolchain, число failures/skips, scope локального прогона, ссылки на CI для текущего head. Сырые материалы предварительно очистить от личных данных.
4. Найденные проблемы, связанные issues без дублей; открытые вопросы и уверенность.
5. Что не выполнено и почему. Для текущей передачи указать исключённый Designer; не обещать его задачи как следующий этап.

Новые дополнительные approvals/checklists не вводятся. Этот черновик реализует правила чек-листа §2; существующие README, документы, workflow, тесты и код не редактировались.
