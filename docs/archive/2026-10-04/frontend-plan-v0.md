- **Граница (арх. v0.11.21 §2).** Из общего пакета приложение берёт только `KabanProtocol` и `KabanBoardCore`; `KabanKit` (модель, валидатор `pipeline.yaml`, резолвер итоговой git-политики `GitPolicyResolver`, машина состояний) и GRDB приложение **не импортирует**. Правда о задачах и валидности пайплайна живёт в демоне: черновик пайплайна проверяется командой `validatePipeline` (3.8), а не своей копией валидатора. Всё, что демон разрешает из `pipeline.yaml`, приходит готовым (арх. v0.11.21 §2): итоговая git-политика стадии — `StageSummary.gitPolicy: EffectiveGitPolicy?` (типы `EffectiveGitPolicy`, `ConditionalGitRule`, `StageCommitter` в `KabanProtocol`, резолвер только в `KabanKit`), умолчания возвратов — `onFail` / `onConflict` / `defaultReturnStage`; для `main` — в `PipelineSummary`, для черновика — в `PipelineDraftValidation.resolved`. Маскот рисует `KabanBoardCore` по `ProjectSummary.mascotSeed`, генератора в `KabanKit` нет (вопрос 24 закрыт). PR #6 (`cursor/kaban-board-core-0b78`) границе уже соответствует: в `Package.swift` у `KabanBoardCore` и `KabanBoardCoreTests` зависимость только `KabanProtocol`, `import KabanKit` в `Sources/KabanBoardCore` и тестах нет.
- **Работа на Linux (F1, вместе с бэком M1).** Один SwiftPM-пакет `/workspace/kaban/code/` (один `Package.swift`) с модулями `KabanProtocol` (пишет Архитектор, первым), `KabanKit` и `KabanBoardCore`. Swift toolchain ставится один раз в общий путь на общем компьютере и общий для всех агентов; свой toolchain фронт не ставит. `KabanBoardCore` зависит только от `KabanProtocol` (арх. v0.11.21 §2); фронт пишет в пакете только `KabanBoardCore` и его тесты (`swift build`, `swift test` в `/workspace/kaban/code/`): проекция, `BoardSet`, правила drop, вывод вида карточки, фикстуры раздела 8. Пока первая версия `KabanProtocol` не залита, на Linux пишем только то, что от неё не зависит (`BoardSet`, правила drop на своих типах); проекция и фикстуры — после неё. `KabanClient`, `KabanUI` и само приложение — только macOS, собираются на `mbp` и подключают пакет локальной зависимостью.
- **Тесты `KabanBoardCore` на сценариях аналитика.** Тесты проекции не выдумывают свои состояния, а берут сценарии M1 аналитика из `/workspace/kaban/code/Scenarios/M1/` (33 JSON). Источник правды — `gen_m1.py`, JSON руками не правим, формат описан в `Scenarios/README.md`: задача `{status, reason}`, команда `{protocolVersion, commandId, command: {имя: {поля}}}`, событие `{type, data}`, `then` проверяется частично. Условия приёмки — `/workspace/kaban/acceptance-criteria-v0.md`: M1 принимается, когда все сценарии M1 зелёные в `swift test` на Linux; для UI (M3) там же нефункциональные условия, например восстановление после перезапуска демона меньше чем за 2 с. Сценарии написаны для демона (`driver`, `tick`, фейковые часы), поэтому фронт берёт из них три вещи. `given.tasks` превращаем в снимок и проверяем вывод вида карточки. `then.events` с `taskUpdated` (52 события после каждого шага, где менялись стадия, состояние, `attempt` или `suspiciousFiles`, с `commandId`, если шаг вызван командой) прогоняем через проекцию, а `then.tasks` — ожидаемое состояние карточки после них. `command` — образец JSON команды и `commandError`. Для подозрительных файлов:
  - `M1-SUSP-01`: `suspiciousFilesFound` для `.env.local`, а `.env.example` из `allow` не попадает. Карточка `waiting_human: suspicious_files` с `attempt` 1. В `taskUpdated` полный `SuspiciousFile` (`rule: pattern`, `pattern: .env*`, `sizeBytes`, `blob`), карточка рисует «по шаблону `.env*`». После `acceptSuspiciousFiles` — `taskUpdated` с этим `commandId`, задача `queued` в `test`, `suspiciousFiles: []`, `runsStarted: 0`. В ленте две строки `SuspiciousFilesRow`, карточка уходит в следующую стадию.
  - `M1-SUSP-03`: `acceptSuspiciousFiles` с устаревшим blob → `commandError: stale_suspicious_files`, событий нет, задача остаётся в ожидании. Проверяем янтарную плашку, перечитывание `getTaskDetail` и то, что кнопка доступна.
  - `M1-SUSP-04`: «Попросить убрать» (`answerHuman`) → `queued` в `dev`, `acceptedFiles` пуст, после гейтов снова `suspicious_files`. Проверяем подпись про повторную проверку и что история «Принятые файлы» пуста.
  - `M1-SUSP-05`: `retryStage` → `suspiciousFilesAccepted`, `queued`. Проверяем подпись «примут текущий набор» у этой группы.
  - Порядок `taskUpdated` относительно предметных событий того же шага сценарии не проверяют, поэтому тесты на порядок внутри шага не опираются. На `commandError` событий нет: тест проверяет, что карточка не изменилась и «отправлено» снято по ошибке ответа.
  - **Адаптер только для тестов.** Пока `taskUpdated.data` в сценариях — подмножество `TaskCard` (`id`, `stageId`, `state` и изменённые поля), а не полная карточка (вопрос 12), тестовая обвязка при прогоне сценария накладывает это подмножество на предыдущую карточку и подаёт в проекцию уже полный `TaskCard`. Боевая `BoardProjection.apply` не меняется: она заменяет карточку целиком, как в арх. v0.11.1 §5. Когда аналитик положит в `data` полную карточку, адаптер удаляем.
- **Сторонних зависимостей в приложении нет.** Markdown — `AttributedString(markdown:)`, лог — `NSTextView`, drag — `Transferable`, анимация — `symbolEffect`. Единственный кандидат — сериализатор YAML (`Yams`) в самом приложении: оно само пишет `pipeline.yaml` (арх. §3.1), а `KabanKit` не импортирует (арх. §2); как писать без потери комментариев — вопрос 2. Риск: при перезаписи теряются комментарии (спайк FS-8).

## 2. Слой состояния

**Сторы** (`@Observable`, `@MainActor`, через `.environment`):
- `ConnectionStore` — состояние XPC (`connecting / live / catchingUp / resyncing / daemonUnavailable / needsApproval`), `lastSeq`, статус `SMAppService`.
- `BoardStore` — проекты, пайплайны, задачи. Карточку держит только `taskCreated(TaskCard)` / `taskUpdated(TaskCard)` / `taskEdited(TaskCard)`: в каждом полная карточка (статус, причина, счётчики, `suspiciousFiles`), проекция `BoardProjection.apply` просто заменяет её по `taskId` (арх. v0.11.1 §5). Предметные события (`suspiciousFilesFound` / `suspiciousFilesAccepted`, `humanRequested` / `humanAnswered`, `incidentOpened`, `gitDenied` …) состояние карточки не меняют, они идут в ленту и уведомления; `taskTransitioned { taskId, fromStage, toStage, from, to, by, runId?, note? }` — только для ленты и анимации перехода. Демон шлёт `taskUpdated` в той же транзакции, что и предметное событие, поэтому двойного применения нет. Каждая задача — отдельный `@Observable TaskModel` (`stageId`, `status`, `reason`, `bounceByReason`, попытка в текущем заходе в стадию, счётчик автозапусков к `max_runs_per_task`, последнее `report_progress`, бейджи), столбцы держат массивы id: событие по задаче перерисовывает одну карточку.
- `SchedulerStore` — эфемерные `schedulerFlags` из таблицы §3.2: флаги Мака (`paused`, `rate_limited` со временем окончания, `usage_exhausted · unknown` с датой сброса, `runner_unavailable` с причиной), флаги пулов (`usage_exhausted · cm` / `om` с датой сброса) и проектов (`paused`, `intake_paused`, `unavailable`, в том числе `mcp_unexpected`, `merge_blocked`); флаги моделей `model_flag` (`modelFlags` в снимке, `modelFlagsChanged`); состояние квоты Cm/Om, если опция включена (`quota?` в снимке, `quotaUpdated { cm?, om?, billingCycleStart?, billingCycleEnd?, fetchedAt }`, `nil` — «нет данных», а не 0%); результат проверки раннера; слоты `n/max_concurrent_runs`; прогресс runs.
- `TaskDetailStore` (на открытую задачу) — `getTaskDetail(taskId)` → `{ seq, task, feed, runs, artifacts, gitGrants, gitDenials, humanRequests, suspiciousFiles, acceptedFiles }` из долговечных таблиц (лента живёт столько же, сколько задача). Дальше применяем события этой задачи с `seq` больше полученного; события, пришедшие до ответа, буферизуем. Плюс `LogStore` с `tailLog`.
- `PipelineEditorStore` (на окно проекта) — черновик (живёт только в редакторе до «Сохранить»), `ValidationIssue[]` с `severity: error | warning` и необязательным `stageId` (арх. v0.11.21): по нему подсвечивается стадия в списке и её форма; если `stageId` нет — индекс стадии разбираем из `path` (`stages[2].wip`) по черновику, текущая версия, флаг «есть незакоммиченные правки».
- `ModelCatalogStore` — `model_catalog` (вывод `cursor-agent --list-models`, значок «проверь пул») и `model_pool_rule` (префиксы → Cm/Om, исключения); `listModels()` (без `forbidden`), обновление по `modelCatalogChanged`; источник для выбора модели и таблицы пулов.
- `BoardSetStore` — какие проекты на доске и в каком порядке: упорядоченный список `projectId` в настройках приложения (`UserDefaults` / `@AppStorage`), не в демоне, потому что это только вид (арх. v0.11.1 §5, §11). Логика — чистый `BoardSet` в `KabanBoardCore` с тестами на Linux: `add(_:at:)` (повторное добавление не дублирует), `remove(_:)`, `move(_:to:)`, `prune(existing:)` — чистка id удалённых проектов (после `projectRemoved` и при старте по снимку). Кроме порядка дорожек `BoardSet` хранит отдельный порядок добавления `addedOrder` (по нему разводятся совпадения маскотов, абзац «Маскот»): `add` дописывает id в конец `addedOrder`, только если его там нет; `move` меняет лишь порядок показа; `remove` и `prune` убирают id из обоих списков; повторное добавление после удаления ставит проект в конец `addedOrder`. Старый сохранённый JSON-массив id декодируется с `addedOrder` = порядку показа. Сделано в PR #6 (коммит `30d6734`). Новый проект (`projectAdded(ProjectSummary)`, арх. v0.11.1 §5) встаёт в конец, `projectRemoved(projectId)` вычищает его из набора, `projectUpdated(ProjectSummary)` меняет имя, путь и маскот в сайдбаре и шапке. Набор переживает перезапуск. Рядом в `UserDefaults` — вид (дорожки / компактный) и свёрнутые дорожки. При первом запуске без сохранённого набора на доску попадают все проекты — **решено** (журнал решений, 4 октября: «предложил Frontend, CEO согласен»; то же правило, что «новый проект сразу на доске»).
- `PendingCommands` — `commandId → (задача, действие, время)`.

**Синхронизация (арх. §5).**
1. Старт: `getSnapshot()` → `{ seq, projects, pipelines, tasks, schedulerFlags, modelFlags, quota?, openIncidentCount, stageLoad }` (`openIncidentCount` — сумма `ProjectSummary.openIncidentCount`, арх. v0.11.21 §5) (карточки без лент), затем `subscribe(fromSeq: seq)`. XPC-контракт не меняется (арх. v0.11.1 §5, §11): приложение подписывается на **все** проекты — `getSnapshot` и поток событий с `projectIds = nil` — и само фильтрует, какие дорожки показать, по `BoardSetStore`. Так у скрытых проектов в сайдбаре остаются значки `waiting_human` и инцидентов, а счётчики (`openIncidentCount`, «Ждут человека», менюбар) считаются по всем проектам, а не только по доске.
2. Разрыв (рестарт демона, сон Мака): переподключение с backoff 0.5 → 1 → 2 → 5 с, затем `subscribe(fromSeq: lastSeq)`. Эфемерные значения после разрыва берём из свежего `getSnapshot`, из него используем только `schedulerFlags`, `modelFlags` и `quota` (арх. §5: эфемерное приходит текущим значением в снимке) **(прочтение фронта)**. На `resyncRequired` (журнал обрезан) применяем снимок целиком и перечитываем `getTaskDetail` открытой панели. Пока идёт догонка, в шапке полоса «Синхронизация…», командные кнопки выключены.
3. Журнальные события применяем к проекции. Формат на проводе `{ type, data }`, неизвестный `type` пропускаем (арх. v0.11.1 §5). Задачи: `taskCreated(TaskCard)`, `taskUpdated(TaskCard)`, `taskEdited(TaskCard)` заменяют карточку целиком, `taskTransitioned` идёт в ленту и анимацию. Проекты: `projectAdded(ProjectSummary)`, `projectUpdated(ProjectSummary)`, `projectRemoved(projectId)`. Пайплайн и настройки: `pipelineApplied(PipelineSummary)`, `settingsChanged`. Загрузка стадий: `stageLoadChanged` (`wipUsed` / `wipLimit` стадии, в одной транзакции с `taskUpdated`; арх. v0.11.21 §3.2, §5; ответ Архитектора, подтвердил CEO). Человек: `humanRequested`, `humanAnswered`. Дальше `gitDenied`, `gitGrantCreated` / `Delivered` / `Consumed` / `Revoked` / `Expired`, `gitPolicyUpdated`, `suspiciousFilesFound` / `suspiciousFilesAccepted`, `incidentOpened` / `incidentResolved`. Предметные события карточку не трогают (её держит `taskUpdated` из той же транзакции), они дают ленту, уведомления, счётчик «Инциденты» и значки сайдбара. Догонку применяем к копии вне main actor и подменяем одним присваиванием, живые события сливаем ≤ 30 Гц.
4. Эфемерные события (`schedulerFlagsChanged`, `modelFlagsChanged`, `quotaUpdated`, `modelCatalogChanged`, результат проверки раннера, результат проверки ручной правки пайплайна, прогресс run) просто заменяют текущее значение в `SchedulerStore` / `ModelCatalogStore` / `PipelineEditorStore`.

**Ожидаем демона, без оптимистичных переходов.** Каждая команда несёт `commandId`. Ответ возвращает `commandId` и `seq` порождённого события.
- Карточка или кнопка переходит в «отправлено» (приглушена, спиннер, действия выключены) до `taskUpdated` этой задачи с моим `commandId` или до ошибки в ответе на команду. `commandId` есть в `EventEnvelope` каждого журнального события, в том числе `taskUpdated`: демон ставит id команды-источника, у событий планировщика и демона — `nil` (арх. v0.11.1 §5, `KabanProtocol`). Команды, которые не меняют задачу (`allowGitOnce`, `updatePipeline` и т. п.), снимают «отправлено» по своему событию с этим `commandId` или по `lastSeq ≥ seq` из ответа. Новое состояние карточка берёт из того же `taskUpdated`.
- Отказ автомата → карточка остаётся на месте, сообщение во всплывающей подсказке. Так же показываем `invalid_state`, в том числе на ручной `requestChanges` в read-only стадию (арх. v0.11.21 §3.1): UI такой цели не предлагает, но ответ демона идёт в обычный тост ошибки команды. Исключение — `identity_required` (`CommandError.identityRequiredCode`, детали в `CommandError.params`; протокольный патч ceabd81d…) на `addProject` и `setProjectIdentity`: не тост, а плашка и поля в листе «Добавить проект» или в строке «Автор коммитов» (3.9, 3.10). Нет ответа 5 с → «демон не отвечает».
- При drag призрак карточки стоит в целевом столбце в состоянии «отправлено».
- Мгновенно: набор и порядок дорожек, вид, сворачивание, выбор, черновики форм.

**3.2 Дорожка проекта.** `BoardView` — горизонтальный `ScrollView` из `StageColumnView` с `LazyVStack`. `StageColumnHeader` (glass): иконка, имя, WIP «4/3» (UC-13) — только из `wipUsed` / `wipLimit` стадии: в снимке — `stageLoad`, между снимками — журнальное событие `stageLoadChanged`, которое демон шлёт в той же транзакции, что и `taskUpdated` (арх. v0.11.21 §3.2, §5; ответ Архитектора, подтвердил CEO). Проекция доски обновляет загрузку стадии по `stageLoadChanged` и сама её не считает. Сам UI WIP не считает: правило «кто занимает слот» живёт в протоколе (`occupiesWIP(in: StageKind)` вместо `TaskStatus.occupiesWIP`), в `human`-стадии слот занимают все задачи, кроме `queued`. Если `stageLoad` в снимке нет (старый демон), счётчик скрыт, запасного подсчёта на клиенте нет. В `KindGroupedBoardView` счётчика нет **(предложение фронта)**; свёрнутость по `display.collapsed`. `kind: gate` — тонкая `GateStripView` со счётчиком, раскрывается по клику. Стадии с `hidden` не рисуются, их задачи доступны через фильтр «скрытые стадии» **(предложение фронта)**.

**3.3 Дорожки и компактный вид.**
- `SwimlanesView`: `LazyVStack(pinnedViews: .sectionHeaders)`, `Section` на проект, закреплённый `LaneHeader` (маскот, ветка, вес, процессы, паузы, сворачивание, кнопка настроек и сразу после неё крестик «Убрать с доски»). Дорожки идут в порядке `BoardSetStore`. Внутри дорожки свой горизонтальный скролл. Высота ограничена, столбцы прокручиваются внутри; свёрнутая дорожка — одна строка сводки **(предложение фронта)**.
- `KindGroupedBoardView` (по проектам с доски): очередь / в работе агентов / ждёт человека / слияние / готово. На карточке `StageChip` с исходной стадией. Любая `waiting_human` (включая `review`) попадает в «ждёт человека» (арх. §11).
- Общие столбцы без дорожек — только при совпадении `id` стадий.

**3.4 Карточка: статусы §3.2 → визуал.** Анатомия по `02-cards`: наклейка маскота + id, заголовок до 2 строк, ряд бейджей, статус-строка (значок + текст + мета), фактура левого края по проекту. Цвет живёт только в статус-строке и рамке, всегда вместе со значком и текстом.

**3.5 Панель задачи** (`TaskInspector`, glass, по `03-task-details`; данные из `getTaskDetail`).
- Шапка: чип статуса с причиной, «попытка 2 из 3», ветка, модель, путь стадий, «Открыть в Cursor», меню «…» (правка `editTask` в `queued` / `waiting_human` / `paused`, иначе «Поставить на паузу, чтобы править», UC-02; приоритет, отмена).
- Над вкладками блок решения для `waiting_human`: инцидент (`IncidentRow`), вопрос, лимиты, подмена модели, подозрительные файлы.
- `SuspiciousFilesBlock` (`waiting_human: suspicious_files`, арх. §8.2, спека UC-25, F29). Текущий непринятый набор — `TaskCard.suspiciousFiles` (арх. v0.11.1 §5): из снимка или `TaskDetail.suspiciousFiles` при открытии панели, дальше из каждого `taskUpdated` этой задачи. Набор переживает перезапуск и `resyncRequired`. Элемент набора — тот же `SuspiciousFile {path, rule: pattern | size, pattern?, sizeBytes, isText, blob}`, что в `suspiciousFilesFound`, поэтому таблица и метки строятся прямо из карточки. `suspiciousFilesFound` и `suspiciousFilesAccepted` таблицу не меняют, они нужны только ленте (`SuspiciousFilesRow`) и уведомлению.
  - Таблица файлов (макеты v0.2.1: `02-details-suspicious.png`, тёмная тема — `02-details-suspicious-dark.png`): полный путь (моноширинно), тег правила «по шаблону `<pattern>`» (`rule: pattern`) или «больше 5 МБ» (`rule: size`, фактический порог `max_file_mb`) по спеке v0.8.22 UC-25.4, размер из `sizeBytes` у **каждого** файла отдельной колонкой, короткий `blob`, «В исключения проекта…». Последняя колонка строки: «дифф» при `isText && sizeBytes < max_file_mb` — открывает файл в Cursor в клоне задачи по `TaskDetail.clonePath`; иначе (двоичный — `isText = false`, демон берёт его из `git diff --numstat`, где `-\t-` значит двоичный; или крупный) — «Показать в Finder» (арх. v0.11.21 §5, §8.2; **зависимость:** `isText` и `clonePath` придут в малом PR Архитектора после мержа PR #2, раздел 8). Общей ссылки «Показать в Finder» в подвале таблицы нет (макет v0.2.1). Стадия и run находки — в строке ленты `SuspiciousFilesRow` (`stageId`, `runId?` из `suspiciousFilesFound`), в таблице их нет. Подпись над таблицей: «Проверка всего diff ветки относительно базы; в «Строгом» — и незакоммиченное в клоне».
  - «Принять файлы» (основная кнопка, спека UC-25.4) → `acceptSuspiciousFiles(taskId, files: [FileBlobRef])` — только `{path, blob}` каждой строки, ровно тот набор, что показан в таблице (арх. v0.11.1 §5, §8.2). Включена и в реальном клиенте, и в `MockKabanClient`. Если набор совпал, демон сразу перепроверяет diff и, если чисто, делает переход, на котором задача стояла: в следующую стадию или, в Merge, к слиянию. Нового run нет, попытка не списывается. Как обычно, без оптимистичного перехода: «отправлено» снимается по `taskUpdated` с этим `commandId` (в нём новое состояние и `suspiciousFiles: []`) или по ошибке `stale_suspicious_files`. Анимацию перехода даёт `taskTransitioned`. Подпись у кнопки: «Kaban сразу перепроверит ветку и продолжит без нового запуска агента».
  - Ответ `stale_suspicious_files` (набор изменился, пока человек смотрел: правка человека в клоне, другой клиент — второе окно или CLI, новый rebase в merge-стадии, арх. v0.11.21 §8.2; ничего не принято; макеты v0.2.1: `02b-details-suspicious-stale.png`): над таблицей спокойная плашка «Набор файлов изменился — ничего не принято» (значок `info`, лёгкий тон `--st-suspicious-bg`, заголовок `--st-suspicious-fg`, без заливки и левой полосы; не красная, не алерт), убранный файл назван в тексте, список перечитывается через `getTaskDetail(taskId)` (`suspiciousFiles`), строки «новый» и «изменён» (новый blob) подсвечены, кнопка «Принять файлы» остаётся доступной для нового набора. Пока ждём ответа, на кнопке «Отправлено…» со спиннером, остальные кнопки блока неактивны, карточка не меняется (`01-cards-suspicious.png`).
  - «Попросить убрать» — только в `agent`-стадии: поле «Замечание агенту» с текстом «Убери из ветки: <пути>» → `answerHuman(taskId, text)`. Набор **не** принимается: задача остаётся в стадии, получает новый run с замечанием, после его гейтов проверка идёт заново. Подпись рядом: «Агент получит новый запуск; после гейтов проверка повторится. Файл, оставшийся в ветке, сработает снова».
  - «Вернуть…» — одна кнопка только на `gate`- и `merge`-стадии, открывает лист (арх. v0.11.21 §3.3, §8.2; спека v0.8.22 UC-25.4; макеты v0.2.1: `05-return-sheet-gate.png`, тёмная тема — `05-return-sheet-gate-dark.png`, merge — `05b-return-sheet-merge.png`):
    - **«Куда»** — выбор стадии; выбранная стадия X уходит в обе команды: `moveTask(stage: X)` или `requestChanges(target: X)`, цель лист шлёт **всегда явно** (арх. v0.11.21 §3.1, спека v0.8.22 §1.3). В списке только допустимые цели возврата: `agent`-стадии с `readOnly = false`, которые стоят раньше текущей по цепочке `on_success`; read-only стадии (AI Review) в списке нет. В макетах 05 / 05b и README v0.2.1 и на gate, и на merge — Dev по умолчанию, альтернатива только Test (AI Review нет), подпись «только стадии, которые правят код». Стадия по умолчанию — то, что прислал демон: на `gate` — `StageSummary.onFail.stage`, на `merge` — `StageSummary.onConflict.stage`. Демон отдаёт эти поля уже разрешёнными (с умолчаниями, лимит у `onFail` по умолчанию 3, у `onConflict` — 2), на `gate`- и `merge`-стадиях они всегда заполнены; клиент умолчаний **не вычисляет**. Поля `gates: [String]`, `onFail: StageReturn?`, `onConflict: StageReturn?` (`StageReturn { stage: StageID, limit: Int }`) добавляет протокольный патч Архитектора (`proto-v2/protocol-v2-code.patch`) и придут с протокольным PR после PR #2: в `KabanBoardCore` до тех пор — `TODO(protocol)`, без запасной логики на клиенте. Те же поля дают счётчики пар (`onFail.limit`, `onConflict.limit`). В подсказке — откуда возвращает автоматика (`on_fail` у gate, `on_conflict` у merge).
    - **Счётчики возвратов** (подписи по спеке v0.8.22 §1.3) — итог «Всего возвратов N/5»: N — сумма `bounceByReason`, 5 — `board.bounce_limit_total`; рядом счётчик пары этой стадии со своим лимитом «<откуда> → <куда> N/лимит»: на gate «Checks → Dev 1/3» (лимит — `onFail.limit`), на merge — фиолетовый бейдж «Merge → Dev 1/2» (`--st-conflict`, лимит — `onConflict.limit`; макет 05b); остальные пары — в подсказке. Подпись «ручной возврат счётчики не меняет». Имена не сводим (вопрос 21 закрыт), подписи согласованы в спеке v0.8.22 §1.3: `board.bounce_limit_total` — «Общий лимит возвратов» в настройках пайплайна (3.8) и «Всего возвратов N/5» в листе; лимит пары — «Лимит возвратов» в настройках («Test → Dev: 3»); причина `waiting_human: bounce_limit` / `conflict_limit` — «Лимит возвратов» с уточнением «общий, 5 из 5», «Test → Dev, 3 из 3», «при красном гейте, 3 из 3» или «при конфликте, 2 из 2» на карточке и в ленте (3.4).
    - **Поле «Замечание агенту»** открывается **пустым**, плейсхолдер «Пусто — файлы будут приняты. Напишите замечание, чтобы вернуть без принятия…». Под полем ссылка «Подставить «Убери из ветки: <пути через запятую>»» — вставляет этот шаблон в поле. Текст по умолчанию не подставляем.
    - **Поле пустое (состояние по умолчанию)** → основная кнопка **«Принять файлы и вернуть»** → `moveTask(stage)`, набор **принимается** (требование Архитектора: в варианте без замечания явно видно, что файлы будут приняты). У каждого файла — «в принятые · <короткий blob>», над кнопкой серо-зелёная плашка с галочкой «Набор принимается…»: файлы уйдут в принятые (`acceptedFiles`), попытка не списывается, ручной возврат в лимиты не идёт.
    - **Поле непустое** (набрано или подставлено) → кнопка **«Вернуть с замечанием»** → `requestChanges(taskId, comments, target)`, набор **не** принимается: задача уходит в выбранную agent-стадию, после её гейтов проверка идёт заново (на merge — и ещё раз перед слиянием); ручной возврат в лимиты не идёт. У каждого файла — янтарное «останется помеченным», над кнопкой янтарная плашка со щитом «Набор не принимается…». Красного в листе нет.
    - Внизу листа — «Отмена», основная кнопка и текущий вызов моноширинно (`moveTask(taskId, stage: "dev")` или `requestChanges(taskId, comments, target: "dev")`), меняется вместе с полем и «Куда».
    На `gate` / `merge` это единственный способ попросить убрать файл: `answerHuman` там вернёт `invalid_state`. На `agent`-стадии кнопки «Вернуть…» нет (`requestChanges` только из `human`-, `gate`- и `merge`-стадий, арх. §3.3).
  - Остальные действия: «Перезапустить стадию» (`retryStage`), «В Backlog» (`moveTask`), «Отменить…» (`cancelTask(taskId, keepBranch)` с галочкой «Сохранить ветку → `kaban/archive/<id>`»). Они уводят задачу с этой точки и **принимают** текущий набор (арх. v0.11.21 §8.2, спека v0.8.22 UC-25.4). В Dev — ровно эти три (`retryStage · moveTask · cancelTask(keepBranch)`, макет v0.2.1 `02-details-suspicious.png`), «Отклонить» и «Вернуть» там нет. «Отклонить» (`reject`) есть только в Human Review (UC-07), а проверка там не срабатывает. Подпись только у этой группы: «Эти действия примут текущий набор: файлы с этим содержимым больше не сработают; изменённый или новый файл сработает снова».

    | Действие | Команда | Стадии | Набор |
    |---|---|---|---|
    | «Принять файлы» | `acceptSuspiciousFiles` | любая | принимает показанный набор, сразу перепроверка и переход без нового run |
    | «Попросить убрать» | `answerHuman` | только `agent` | не принимает, новый run, проверка после гейтов |
    | «Вернуть…» → «Вернуть с замечанием» (поле непустое) | `requestChanges(comments, target: X)` | только `gate` / `merge` | не принимает, задача в agent-стадии, проверка после гейтов, в лимиты не идёт |
    | «Вернуть…» → «Принять файлы и вернуть» (поле пустое, по умолчанию) | `moveTask(stage: X)` | только `gate` / `merge` | **принимает**, это написано на кнопке |
    | «Перезапустить стадию», «В Backlog», «Отменить…» | `retryStage`, `moveTask`, `cancelTask(keepBranch)` | любая | принимает |
    | «Отклонить» в стадию или с отменой | `reject(target, keepBranch)` | только Human Review, на `suspicious_files` кнопки нет | принимает (арх. §8.2) |
  - История «Принятые файлы» под таблицей («Принятые ранее» в макете; свёрнута, если пусто) — из `TaskDetail.acceptedFiles`: путь, blob (короткий хеш, моноширинно), кто принял, когда (время по Калининграду). Каким действием приняты, в списке не показываем: поля `via` в MVP нет (решение Архитектора); у `AcceptedFile` есть `commandId`, и переход той же командой виден рядом в ленте задачи. Отдельного живого события для истории нет: по `suspiciousFilesAccepted` открытая панель перечитывает `getTaskDetail` **(прочтение фронта)**, само событие — строка ленты.
  - «Добавить в исключения проекта…» открывает раздел «Подозрительные файлы» настроек проекта (3.9) с путём в `allow` → `updatePipeline` (автокоммит `.kaban/`). Задачу это из ожидания не выводит **(прочтение фронта)**.
  - Цвет: янтарный — `--st-suspicious*`, алиасы `--st-waiting*` (отдельного цвета нет, вопрос 11 закрыт), значок `exclamationmark.shield`; не красный. По арх. §3.2 и §8.2 это отдельная причина, а не инцидент: инцидент не открывается (`incident.kind` — только `refs_moved`, `tags_changed`, `config_changed`, `kaban_dir_changed`, `foreign_base`), в «Инциденты» и `openIncidentCount` не попадает, refs не откатываются, попытка не списывается. Уведомление — обычное `waiting_human`, без `.timeSensitive`.
- `ModelSubstitutionBlock` (`model_substituted`): рядом два блока «Запрошена» и «Ответила» (имя и id; `actual` заполнен только при `substituted`, поэтому у пропавшей модели (`unavailable`) блока «Ответила» нет ни на карточке, ни в баннере, ни в панели), под ними `fallbackModel`, если был, время, номер run, ссылка на лог; кнопки «Повторить» (`retryStage`), «Другая модель» (выбор из 3.8 → `setModelOverride`), «В Backlog» (`moveTask`).
- В проекте со «Строгим» пресетом агент не коммитит: после зелёных гейтов и проверки результата демон делает один коммит стадии, сообщение — `summary` из `complete_stage` (пустое — `kaban: <стадия> <задача>`, арх. §6.3, спека UC-19). В «Сводке» и списке коммитов такой коммит помечен «коммит демона · из резюме стадии», над резюме стадии подпись «станет сообщением коммита»; страховочные коммиты демона в «Стандартном» и «Свободном» помечены «страховочный коммит».
- Инструменты доски в UI: `report_progress` — строка «последнее действие» на карточке и записи ленты; `request_human` — вопрос в блоке решения с полем ответа (`answerHuman`); `return_to_stage` — счётчик «↩ 2/3» на карточке и список замечаний в ленте; `complete_stage` — резюме стадии в «Сводке» и ленте. `get_task_context` в UI не виден.
- Вкладки: **Лента** (`task_feed_item`: переходы, `report_progress`, замечания, гейты, отказы и разрешения git, инциденты, серая строка `model_unconfirmed` — фактическую модель подтвердить не удалось, задача идёт дальше; `SuspiciousFilesRow` — «Найдены подозрительные файлы: 2» со списком по `suspiciousFilesFound` и «Приняты вами 14:50 · <действие>» по `suspiciousFilesAccepted { taskId, files, by, commandId }`), **Живой лог**, **Сводка** (Human Review, 3.7), **Попытки** (`runs`: стадия, номер попытки в заходе, модель запрошенная и фактическая, длительность, `end_reason`, usage, `refs/kaban/wip/<run-id>` после краша или зависания; запуски без списания попытки (`counts_toward_limits = false`, арх. §4) помечены; в шапке вкладки «автозапусков 7 из 12» **(предложение фронта)**), **Разрешения git** (`gitGrants`, состояния 3.6).
- Внизу поле «Замечание агенту или ответ…» (F23, UC-06) — **только в `agent`-стадиях**: на `human`, `gate` и `merge` демон отвечает на `answerHuman` ошибкой `invalid_state` (арх. v0.11.21), поэтому там поля нет, а действия — только `approve`, `requestChanges`, `reject`, `retryStage`, `moveTask` (что из них применимо, решает причина). В `agent`-стадии из `waiting_human` с любой причиной поле отправляет `answerHuman(taskId, text, requestId?)` (`requestId` — только для `question`), задача встаёт в очередь своей стадии и продолжает сессию с текстом. При `retries_exhausted` / `bounce_limit` / `conflict_limit` под полем подсказка «Добавит одну попытку»; при `run_limit` — «Обнулит счётчик запусков». В `review` (`human`-стадия) вместо него поле комментария к «Вернуть с комментарием» → `requestChanges(taskId, comments, target?)`, не `answerHuman` (3.7) **(предложение фронта)**. В `running` / `gating` поле выключено с подсказкой «Поставьте на паузу».

Быстрые действия по строке таблицы 3.4: «Перезапустить» (`retryStage`), «Модель», «В Backlog» (`moveTask`), «Отменить» → `cancelTask(taskId, keepBranch)`. Диалог отмены везде одинаковый: галочка «Сохранить ветку» (по умолчанию выключена) с подписью «сохранится как `kaban/archive/<task-id>`».

**Раздел «Инциденты» (F22).** `IncidentsView` в сайдбаре: список по всем проектам (маскот, задача, что изменилось, run, время), сверху неразобранные. Счётчик = `openIncidentCount` из снимка, значок у проекта в сайдбаре — `ProjectSummary.openIncidentCount` (арх. v0.11.21 §5; поле — в малом PR, раздел 8): любое действие человека по задаче выводит её из этого статуса, инцидент считается разобранным и уходит из счётчика, но остаётся в списке как история с подписью выбранного действия. Клик открывает панель задачи. Список берём командой `listIncidents(projectIds: nil, state)` — по всем проектам, включая скрытые с доски, — из таблицы `incident`.
- `IncidentRow`: что изменилось, в каком run, ссылка на лог. Действия UC-18.4: вернуть на стадию с замечанием (`requestChanges`), модель, «Ужесточить политику…», отменить.
- **Живой лог:** `LogTextView: NSViewRepresentable` (NSTextView, TextKit 2, только чтение, `usesFindBar`). `tailLog(runId, fromOffset)` отдаёт разобранные `AgentEvent` батчами раз в 100–250 мс, дописываем одним `beginEditing/endEditing`; рендер по типу (сообщение, свёрнутый tool call, результат, ошибка, usage). Автопрокрутка только внизу, до ~50 тыс. строк в памяти, раньше — «Загрузить ранее» по смещению; «Открыть сырой лог» — JSONL по пути из run. Подписка, пока вкладка видна.

**3.6 «Разрешить один раз» (UC-17, арх. §8.3).** Отказ — тихая строка ленты `GitDenialRow`: команда, стадия, run, сработавшее правило, время. Кнопки видит только человек, агент ленту не читает.

| Состояние строки | Что видно | Событие |
|---|---|---|
| Отказ, жёсткое правило | замок + «Не настраивается: push делает только Kaban», кнопок нет | `gitDenied` (`rule` — жёсткий инвариант) |
| Отказ, настраиваемое правило | «Разрешить один раз», «Добавить в политику…» | `gitDenied { denialId, runId, argv, rule }` |
| Отправлено | кнопка → спиннер «Выдаём разрешение…» | ответ на `allowGitOnce(denialId)` с `commandId` |
| Создано, ждёт доставки | ключ, «Разрешено один раз · агент узнает при следующем вызове инструмента доски» (run жив) или «…уйдёт в промпт следующего запуска стадии Dev» (run завершён), «Отозвать» (`revokeGitGrant`); бейдж ключа на карточке | `gitGrantCreated { grantId, denialId, argv, by }` |
| Доставлено агенту | «Доставлено агенту 14:27 · в ответе инструмента» / «· в промпте run #4», «Отозвать» | `gitGrantDelivered { grantId, runId, via: mcp_response \| next_prompt }` |
| Использовано | серая галочка «Использовано 14:41 · run #3», бейдж снимается | `gitGrantConsumed { grantId, runId }` |
| Отозвано | «Отозвано вами 14:50» | `gitGrantRevoked { grantId, by }` |
| Истекло | «Не использовано: задача завершена / отменена» | `gitGrantExpired { grantId, reason }` |

В ленте это одна строка с цепочкой «создано → доставлено агенту → списано» (или «отозвано» / «истекло»), где каждый шаг ставит своё время. Повтор команды без разрешения даёт новую строку. Пять отказов за run → `waiting_human · git_denials`: можно выдать несколько разрешений и нажать «Перезапустить стадию».

**«Добавить в политику…»** открывает раздел Git (3.9) в режиме предпросмотра: правило из отказа уже добавлено, выбирается уровень «Проект / Стадия Dev». «Сохранить» → `addDenialToPolicy(denialId, scope: .project | .stage(id))` → новая версия или `ValidationIssue`. По `gitPolicyUpdated { projectId, scope, pipelineVersion }` строка отказа показывает «Добавлено в политику проекта · версия abc123». Действует с новых runs.

**3.7 Human Review** (`ReviewView`, вкладка «Сводка» панели по `03-task-details`): резюме стадий, `DiffstatTable` (файл, +/−, полоска), коммиты, гейты (раскрываемый вывод), время и стоимость, блок «изменено при разрешении конфликта». Кнопки: «Открыть в Cursor» (`cursor <путь клона>`, запасной путь `NSWorkspace` по bundle id); «Одобрить» ⌘↩ (`approve`); «Вернуть с комментарием» — комментарий (поле внизу панели) и стадия (`requestChanges(comments, target)`, цель всегда явная); в выборе стадии только `agent`-стадии с `readOnly = false` раньше текущей по цепочке `on_success` (арх. v0.11.21 §3.1), read-only стадий нет; стадия по умолчанию — `PipelineSummary.defaultReturnStage` (первая `agent`-стадия с `readOnly = false`, разрешает демон тем же правилом, что и `requestChanges` без `target`; арх. v0.11.21 §3.1, спека v0.8.22 §1.3), клиент её не вычисляет, а `target` шлёт всегда явно. Если поле `nil` (такой стадии нет, пайплайн с `no_return_target`), кнопка выключена, под ней мелкая серая вторичная строка «Некуда вернуть: нет стадии, которая правит код» без цвета ошибки и ссылка «Открыть в редакторе» — редактор пайплайна с фокусом на поле «Куда возвращать» стадии из `stageId` этой ошибки, поле в оранжевой обводке (3.8) (согласовано с дизайнером). Для `defaultReturnStage = nil` обычно приходит `no_return_target` **без** `stageId` (уровень пайплайна, только для `requestChanges` и только если в пайплайне есть `human`-, `gate`- или `merge`-стадия, арх. v0.11.21 §3.1): тогда ссылка открывает список ошибок уровня пайплайна. Та же `no_return_target` уже видна на дорожке янтарной плашкой «Пайплайн не запустится» (3.3); старые снимки без поля тоже дают `nil` — до протокольного PR так и показываем; «Отклонить» — «Отменить задачу» (галочка «Сохранить ветку», по умолчанию выключена) или «Вернуть в стадию ▸» без комментария → `reject(taskId, target, keepBranch)`, где `keepBranch` учитывается только при `target = cancel`. `reject` в стадию — это возврат (арх. v0.11.21 §3.3, спека v0.8.22 §1.3): в «Вернуть в стадию ▸» тот же фильтр, что и в «Куда», — только `agent`-стадии с `readOnly = false` раньше текущей по цепочке `on_success`; иначе демон ответит `invalid_state` (обычный тост ошибки команды). `reject` в отмену разрешён всегда. Поведение набора подозрительных файлов не меняется: `reject` принимает набор, как и раньше (3.5).

**3.8 Настройки пайплайна и стадии.** Окно проекта → «Пайплайн»: список стадий с перестановкой, добавлением и удалением.
- Удаление стадии, где есть задачи в нетерминальном статусе, выключено с подсказкой «сначала перенесите N задач» (UC-13); валидатор демона отклонит его в любом случае.
- `StageEditorForm` — секции по таблице 1.5 спеки, неприменимые к `kind` скрыты. Отображение: имя, иконка, цвет, порядок, свёрнут, скрыт.
- Лимиты (спека v0.8.22 §1.3, §4.1). Подписи полей редактора и `{label}` в текстах ошибок берутся из одного источника — таблицы подписей `{label}` спеки §4.1:
  - на уровне пайплайна (`board`): «Общий лимит возвратов» (`bounce_limit_total`, по умолчанию 5), «Лимит задач в ожидании человека» (`max_waiting_human`, по умолчанию 3, на проект), «Лимит запусков на задачу» (`max_runs_per_task`, по умолчанию 12, только автоматические запуски) — умолчания по арх. §3.1;

Если `resolved = nil` (только когда черновик не разобрался как YAML — `yaml_syntax` — или его корень не mapping; при прочих ошибках поле заполнено, арх. v0.11.21 §3.1), превью показывает последнее удачное состояние приглушённым и список ошибок **(предложение фронта)**.
- `StageMcpPicker` (`agent.mcp`, спека 1.5, UC-24): сервер доски отмечен всегда и не снимается, остальные выбираются только из белого списка проекта (вкладка «MCP», 3.9); по умолчанию у стадии только сервер доски. Длительности в `{min}` / `{max}` (спека v0.8.22 §4.1): «У `duration_out_of_range` `{min}` и `{max}` приходят строками длительности (`1s`, `1m`, `2h`). Пример из спеки: «Таймаут зависания должен быть от 1 мин до 30 мин». Из черновика клиент ничего не достаёт и диапазонов не зашивает. Ошибка или предупреждение определяется **только** `severity`, не кодом (арх. v0.11.21): `error` — оранжевая обводка и «Сохранить» выключена, `warning` — янтарная подсветка без оранжевой обводки, сохранению не мешает. Обрабатывается как остальные ошибки `ValidationIssue`: «Сохранить» выключена, стадия подсвечивается по `stageId`, строка `extend` в редакторе стадии (3.8, `StageGitOverrides`) — по `path` оранжевой обводкой; текст из спеки v0.8.22 §4.1 — «Стадия «{stage}» только читает: `{cmd}` разрешить нельзя» (имя стадии в «ёлочках», как у соседних кодов) (`{stage}` — имя стадии по `stageId`, `{cmd}` — из `params`), без ключа — `message`. Команда вне `gitCommandCatalog` в `extend` read-only стадии (арх. v0.11.21 §8.4: «вне каталога — не значит не пишет: `replace`, `gc`, `prune`») даёт **только** `git_unknown_command` — предупреждение, одно сообщение на строку, без `git_readonly_extend` (арх. v0.11.21 §8.4, спека v0.8.22 UC-19, §4.1): строка `extend` подсвечивается янтарным, «Сохранить» не блокируется, а в превью итоговой политики (`PipelineDraftValidation.resolved`) резолвер кладёт команду в `denied` с `source: stage`, и `EffectivePolicyView` показывает её «сужено до чтения» (3.9); в `allowed` она не попадает никогда, клиент ничего не вычисляет. Это не `readonly_violation`: тот — причина `retry_wait` (стадия изменила файлы во время запуска, 3.4), коды не пересекаются и не переиспользуются. Обычно предупреждением приходят четыре кода: `unknown_key`, `mcp_not_allowlisted`, `git_unknown_command` и `field_not_allowed_for_kind` для `wip` (подтверждено аналитиком, спека v0.8.22 §4.1). `unknown_stage` — только ссылка на id, которого нет в пайплайне. `no_return_target` (`ValidationCode.noReturnTarget`): у стадии с возвратом нет подходящей цели (у gate — `on_fail` без `stage`, а раньше по цепочке `on_success` нет `agent`-стадии с `readOnly = false`) **или** явная цель возврата (`returns_to`, `on_fail.stage`, `on_conflict.stage`) — read-only стадия или вообще не `agent`-стадия (арх. v0.11.21 §3.1, спека v0.8.22 §1.3, §4.1). Без `stageId` код приходит только для `requestChanges` (в пайплайне есть `human`-, `gate`- или `merge`-стадия, а `agent`-стадии с `readOnly = false` нет): подсвечиваем не стадию, а список ошибок уровня пайплайна, текст «Некуда вернуть: нет стадии, которая правит код» (§4.1). `stageId` — стадия, которой принадлежит этот возврат (agent, gate или merge), а не всегда gate. Эта стадия подсвечивается в списке тем же механизмом, что и остальные ошибки со `stageId`, а в её форме оранжевой обводкой — поле «Куда возвращать» (`returns_to` / `on_fail.stage` / `on_conflict.stage`) **(предложение фронта)**. В выборе цели этого поля read-only стадии не предлагаем. Коды валидации — только `ValidationCode` в `KabanProtocol`. Код придёт с протокольным PR (после PR #2).
2. «Сохранить» → атомарная запись файла + `updatePipeline(projectId, contentHash)`; список `ValidationIssue` из ответа — вторая проверка. Некорректная версия в `main` не попадает. Если демон отклонил версию, черновик остаётся в редакторе с ошибками, а файл на диске возвращаем к прежнему содержимому **(предложение фронта)**.

Поля `EffectiveGitPolicy` (арх. v0.11.21 §8.4): `preset`, `allowed: [GitRule]`, `denied: [GitRule]`, `hardInvariants: [String]` (id из `HardInvariant`), `conditional: [ConditionalGitRule { returnReason, allowed: [GitRule] }]`, `committer: StageCommitter` (`daemon_only` — «Коммитит демон из резюме», `agent_with_safety_commit` — «Агент + страховочный коммит»), `readOnly`. Каждое правило — `GitRule { rule, source }`, `source: GitRuleSource?` ∈ `preset | project | stage` (`hard` из `GitRuleSource` убран в арх. v0.11.21); неизвестное значение декодируется как `nil`. Правила сопоставляются по префиксу слов (`restore` покрывает `restore --staged`, но не наоборот), и делает это только демон: разрешённое правило, покрытое любым `denied`, в `allowed` уже не попадает, а клиент правила между собой не сравнивает. Слой выбирает резолвер демона (арх. v0.11.21 §8.4, спека v0.8.22 UC-19): `source` — **последний слой, который изменил итог правила** (слои: пресет → проект → стадия); повтор того же решения слой не меняет. Запрет на любом слое сильнее разрешения: `extend` стадии не снимает `deny` проекта, пресеты только разрешают и ничего не запрещают. Поэтому итог «разрешено» меняет только первое разрешение, итог «запрещено» — только первый запрет. У `conditional` **всегда** `stage` (`when` бывает только у стадии); явно запрещённое правило в `conditional` не попадает. Примеры: пресет разрешает, стадия запрещает → `denied`, `source: stage`, «сужено»; проект запрещает, стадия разрешает → остаётся в `denied`, `source: project`, «унаследовано»; пресет разрешает, стадия повторяет `extend` → `allowed`, `source: preset`, «унаследовано». Условные расширения — отдельной строкой со своим `when: return_reason == <returnReason>` (как в макете `04-stage-git-overrides`), неизвестную причину показываем как есть. Клиент ничего не вычисляет. Метки (подтверждены дизайнером по макетам `03` и `04`): замок идёт не из `source`, а из `hardInvariants` — плитка с заштрихованным замком на каждый id, без текстовой метки «унаследовано / …»; `preset` / `project` — «унаследовано» (в редакторе стадии — «из проекта», 3.8); `stage` в `allowed` или `conditional` — «переопределено»; `stage` в `denied` — «сужено», а при `readOnly = true` — «сужено до чтения» (арх. v0.11.21 §8.4, спека v0.8.22 UC-19.3); `nil` — без метки. Пометок четыре — «унаследовано», «переопределено», «сужено», «сужено до чтения» (спека v0.8.22 UC-19.4). Явный `deny` в YAML read-only стадии тоже приходит с `source: stage` и показывается как «сужено до чтения» — так задумано (арх. v0.11.21 §8.4, спека UC-19.3). У read-only стадии всё, что разрешила политика проекта и что не чтение (`add`, `commit`, `restore --staged`, `stash`…), демон присылает в `denied` с `source: stage`; запреты проекта остаются с `source: project` («унаследовано»). «Нет в пресете (из каталога)» у неё — только команды, которых не было в политике проекта (например, `rebase`, `reset`). Команда вне `gitCommandCatalog`, которую read-only стадия перечислила в `extend` (например, `replace`), тоже приходит в `denied` с `source: stage` и показывается «сужено до чтения»; валидатор при этом даёт только предупреждение `git_unknown_command`, не `git_readonly_extend` (арх. v0.11.21 §8.4, спека v0.8.22 UC-19, 3.8). Клиент ничего не вычисляет: метка выбирается по `source` и `readOnly` политики стадии. Раскладка (подтверждена дизайнером): внутри каждой группы («Разрешено» / «По условию» / «Запрещено») правила с одним `source` собираются в одну строку с одной меткой — один `source`, одна строка, как в макете 04; группа «Жёсткие» — плитки по `hardInvariants`. В конце группы «Запрещено» — две серые строки без метки (макеты 03 / 04, перерисованы под арх. v0.11.10): «Нет в пресете (из каталога): <команды>» — команды из `PipelineSummary.gitCommandCatalog`, которых нет ни в `allowed`, ни в `denied` политики этой стадии (в макете — `reset`); «Всё вне каталога — запрещено» — постоянная подпись. В макете 04 в «Запрещено» так: `stash` — «сужено», `cherry-pick` («перенос чужих коммитов») — «унаследовано» (явный запрет проекта `deny: [cherry-pick]`), затем эти две строки; `restore --staged` остаётся разрешённым. Обе строки — только отображение готовых данных, без сопоставления правил на клиенте. Цвета меток (подтверждены дизайнером, как в макетах 03 / 04): «унаследовано» — серая, «переопределено» — синяя, «сужено» — фиолетовая. Разовые `git_grant` в политику не входят — они в панели задачи.
  - Колонка «Политика проекта» в редакторе стадии (`StageGitOverrides`, 3.8; дизайнер перерисовывает макеты 03 и 04, раздел 10). Данные (арх. v0.11.21 §8.4, вопрос 27 закрыт): строки — из `PipelineSummary.gitCommandCatalog: [String]` (каталог известных демону git-команд, по нему же валидатор даёт `git_unknown_command`), состояние проекта — из `PipelineSummary.projectGitPolicy: EffectiveGitPolicy?` (пресет + `allow` / `deny` проекта без стадий, `source` только `preset` / `project`); для черновика — те же поля в `PipelineDraftValidation.resolved`. Без `identity` демон один раз читает `user.name` / `user.email` обычным git пользователя в этом репозитории (конфиг репозитория, глобальный и системный); клиент git сам не читает и автора не угадывает. Правила демона (арх. v0.11.21 §8.2): имя и почта обрезаются по краям, значение из одних пробелов — `missing`; перенос строки и NUL отклоняются (`invalid`), в том числе в значении из git-конфига при первом вызове без `identity`; явный `identity` побеждает, пустое поле в нём на репозиторий не откатывается. Детали — в `CommandError.params: [String: String]` (без поля — `[:]`, как у `ValidationIssue`): `missing` = `name` | `email` | `name,email`, `invalid` с тем же форматом, `name` / `email` — найденные значения. Каждое поле попадает ровно в одно место — `missing`, `invalid` или найденные; отклонённое значение не возвращается, поэтому поле из `invalid` пустое; порядок в списках — `name`, `email` (арх. v0.11.21 §8.2, патч). Лист остаётся открытым с той же папкой и галочкой, показывает общий текст спеки «Не задан автор коммитов: укажите имя и почту», открывает поля «Имя» и «Почта» и по «Добавить» повторяет `addProject(path, createTemplate, identity)`. Две ветки по спеке v0.8.22 UC-01:
  - **Первый отказ** (вызов без `identity`). Найденные `params.name` / `params.email` подставляются с пометкой «из настроек git» (они могут прийти из конфига репозитория, глобального или системного); фокус — в первое поле из `missing` или `invalid` (порядок «Имя», «Почта»). Подсветки у полей из `missing` нет. Под общим текстом уточнение: нашлось только имя → «В настройках git нашлось только имя, почты нет»; нашлась только почта → «В настройках git нашлась только почта, имени нет»; ничего не нашлось → без уточнения; уточнение показываем, **только когда второе поле в `missing`**, при `invalid` второго поля его нет — хватает текста под полем (спека v0.8.23 UC-01). Поле из `invalid` пустое, и текст под ним виден сразу, без обводки: «Имя в настройках git содержит служебные символы, укажите вручную» или «Почта в настройках git содержит служебные символы, укажите вручную».
  - **Отказ вызову с `identity`.** Поля из `missing` и `invalid` получают оранжевую обводку ошибки (как ошибки полей в 3.8, не красную) и текст под полем: `missing` — «Укажите имя» / «Укажите почту»; `invalid` — «Имя должно быть в одну строку, без служебных символов» / «Почта должна быть в одну строку, без служебных символов» (перенос строки или NUL); тексты первого отказа заменяются этими; остальные поля не подсвечиваются. В полях остаётся то, что ввёл пользователь (спека v0.8.24 UC-01).
  - **Ключей нет** (старый демон, `params = [:]`): «только общий текст, оба поля без подсветки»; поля открыты и пусты. Клиент сам пустоту и символы не проверяет и подсветку по отправленному не выводит — только по `params` демона.
  - Автор сохраняется у демона на этом Маке и меняется в настройках проекта (`setProjectIdentity`, 3.9). У зарегистрированного проекта автор есть всегда, поэтому `identity_required` на запуске не появляется: отдельного статуса или причины на карточке для него нет (арх. v0.11.21 §8.2, спека v0.8.22 UC-01).

**3.13 Квота Cursor (опция «неофициально», по умолчанию выключена).**
- `QuotaBars` в менюбаре и блоке «Этот Мак»: две полосы — **Cm** (модели Cursor, `composer-*`, `autoPercentUsed`) и **Om** (именные модели, `apiPercentUsed`). Полосы Gb нет. У каждой полосы метка прошедшей доли цикла и метка порога; подпись — обратный отсчёт до сброса по `billingCycleEnd` («сброс через 9 д»). Доля цикла считается от `billingCycleStart`; если его нет в ответе (проверяется в спайке 1), начало цикла считается календарно — тот же день месяцем раньше от `billingCycleEnd` (не «минус 30 дней»); метка доли цикла использует этот запасной расчёт. `billingCycleEnd` демон разбирает из строки с миллисекундами эпохи, UI получает `Date`. Исчерпанный пул (`usage_exhausted · cm` / `om`) — полоса заполнена, подпись «исчерпан».

## 5. Доступность и производительность

- VoiceOver: карточка — один элемент («SHOP-42, Dev, ждёт человека: лимит возвратов, возвраты 3 из 3») с `accessibilityActions`; роторы «ждут человека», «инциденты» и «дорожки»; у проекта в сайдбаре действия «Показать на доске» / «Скрыть с доски», у `LaneHeader` — «Убрать с доски», «Сдвинуть влево / вправо»; объявления только о `waiting_human` и инцидентах.
- Клавиатура: ⌘1–⌘9 — фокус на N-й дорожке, ⌘⌥← / ⌘⌥→ — сдвиг дорожки в фокусе; фокус на карточках, стрелки, пробел открывает панель, ⌘↩ одобрить, ⌘F поиск в логе.
- Статус никогда не передаётся только цветом: значок + текст + фактура проекта. Контраст по токенам в обеих темах.
- Reduce Motion: маскоты и полосы прогресса статичны. Reduce Transparency и Increase Contrast — проверить, как деградирует `glassEffect`.
- Производительность (цель **(предложение фронта)**: 10 проектов × 500 задач, 60 fps на `mbp`): `Lazy*`-стеки, отдельные `TaskModel`, `Equatable`-карточки, события ≤ 30 Гц; glass только на шапках; анимированных маскотов не больше числа проектов; лог батчами с лимитом строк; `os_signpost` на применение событий.
