Kaban — чек-лист для второй ИИ-команды
Версия 2 · 4 октября 2026 (добавлены блоки ролей, раздел 6) · владелец: Артём
1. Зачем этот документ и коротко о проекте
У основной ИИ-команды (Architect, Backend, Frontend, Analyst, Designer, CEO-координатор) заканчиваются лимиты, поэтому часть работы передаём вам, второй команде (дальше «team2»). Здесь собраны задачи, которые можно делать параллельно, не мешая основной команде, и формат, в котором нужно вернуть результат, чтобы потом быстро ввести её в курс.


Kaban — канбан-приложение для macOS, которое ведёт ИИ-агентов (cursor-agent) по стадиям пайплайна: демон на Swift (launchd) и тонкий клиент на SwiftUI в стиле Liquid Glass. Стадии задаются в .kaban/pipeline.yaml. В репозитории Swift 6 и SwiftPM, CI на GitHub Actions: «Linux (Swift 6)» и «macOS (optional)».


* Репозиторий: https://github.com/imedfan/kaban (публичный, LICENSE пока нет)
* Документы (Google Drive, папка kaban/docs): architecture-v0.md (v0.11.22), kaban-mvp-features-usecases.md (спека v0.8.24), frontend-plan-v0.md (v0.5.36), backend-plan-v0.md, decisions-log.md, acceptance-criteria-v0.md
* Уже в main: #1 каркас, #2 KabanProtocol (XPC-контракт v1, golden-фикстуры), #3 фронтенд-спайки FS-1…9, #4 бэкенд-спайки 1/2/6, #6 KabanBoardCore (проекция доски, BoardSet, DropRules, MascotKit, 33 сценария в Scenarios/M1), #7 патч протокола v2 (GitIdentity, CommandError.params, ProjectSummary.identity, git_readonly_extend, строгий ScenarioDecodeCheck).
* Ключевые решения, которые нельзя «чинить»: агенту по умолчанию доступен только MCP доски, остальные — только через явный allowlist; моделей по умолчанию нет (у каждой агентской стадии явная модель, иначе pipeline_invalid); фильтр доски убран, вместо него перетаскивание из сайдбара и кнопка X на дорожке; GitIdentity хранится в настройках проекта в демоне, DaemonGit работает с GIT_CONFIG_GLOBAL=/dev/null.
2. Правила безопасности (жёсткие)
Нарушение любого пункта — повод закрыть PR без ревью.


1. Ветки. Работаете только в своих ветках с префиксом team2/… (например, team2/research-cursor-cli). Одна задача — одна ветка — один PR.
2. PR только в main. Не мержите ничего, даже свои PR. Мержит только Артём.
3. Чужие PR не трогаете. Не меняете их базу, не пушите в чужие ветки, не ставите approve или request changes от имени основной команды. Комментировать можно.
4. Занятые зоны, файлы не меняются:
   * Sources/KabanProtocol/, Tests/KabanProtocolTests/ (Architect);
   * Sources/KabanKit/ и его тесты (Backend, PR #5 в работе);
   * Sources/KabanBoardCore/ и его тесты (Frontend, PR по TODO(protocol) в работе);
   * Scenarios/ (Analyst);
   * design/ и макеты Penpot (Designer);
   * docs/architecture* и любые существующие документы в docs/;
   * README.md, логотип и баннер (у CEO-бота свой PR);
   * .github/workflows/ci.yml;
   * Package.swift — только после отдельного согласования с Артёмом;
   * документы на Google Drive: только чтение, не редактировать, не перемещать, не переименовывать. Создавать новый файл отчёта можно (раздел 4).
   * Исключение для задач из раздела 6: в папках тестов можно добавлять только новые файлы с префиксом Team2 (Tests/<Модуль>Tests/Team2*.swift) и фикстуры в Tests/<Модуль>Tests/Fixtures/team2/, ровно там, где это указано в блоке роли. Существующие файлы тестов не меняются.
5. Публичные типы протокола не меняются, в том числе через расширения в других модулях.
6. Новое — только в новых папках: research/, examples/, tools/, docs/team2/ (для задач раздела 6 — docs/team2/<роль>/), новые файлы в docs/. Скрипты в tools/ живут вне SwiftPM (Python 3 или bash), чтобы не трогать Package.swift. Новый Swift-таргет — только после согласования.
7. Маленькие PR, зелёный CI. Ориентир — до ~400 строк. PR с красным CI на ревью не отправляется.
8. Сомневаетесь — спросите. Если задача упирается в занятую зону, неясное решение или противоречие в документах, запишите это в раздел «Открытые вопросы» отчёта или заведите issue. Сами не меняйте.
9. Без секретов и личных данных в коммитах, issues и отчётах.
10. Найденные ошибки не чините, а описывайте в отчёте и issues. Это касается и тестов: если Team2-тест падает из-за бага в коде основной команды, пометьте его XCTSkip/withKnownIssue со ссылкой на issue, чтобы CI оставался зелёным.

	A. Исследования к спайкам в понедельник (P0–P1)
Цель — чтобы на mbp Артём не гуглил, а шёл по готовому списку команд. В каждом файле обязательно: источники со ссылками и датой, «что известно точно» и «что проверить на маке», чек-лист команд для копирования, ожидаемый результат и что записать в фикстуры.


* ☐ T1. cursor-agent CLI (спайк 1, арх. §6 и §14, спека §6). Флаги headless-режима: -p, --output-format stream-json, --model, --force, --approve-mcps, --resume/session_id, --list-models, mcp list. Коды выхода, формат события result (usage, стоимость), где видна фактическая модель и подмена при fallbackModel. Как выглядят месячная квота, resource_exhausted, молчаливый выход и разлогин. Как проверить вход без запуска модели. Запуск из-под launchd: PATH, отдельный HOME, где лежит токен.
   * Готово, когда: по каждому вопросу из спеки §6 есть ответ или пометка «проверить на mbp» с командой, а также шаблон, куда складывать фикстуры stream-json и stderr.
* ☐ T2. Изоляция MCP (спайк 2, арх. §9). Подхват .cursor/mcp.json из клона, подстановка env, HTTP-транспорт. Как подключить MCP доски без записи в репозиторий и как не дать закоммиченному .cursor/mcp.json проекта добавить серверы мимо allowlist (fail closed).
   * Готово, когда: описано минимум 2 варианта с плюсами и минусами, есть пошаговый сценарий проверки на mbp.
* ☐ T3. Seatbelt (спайк 6, арх. §8.2, §13). Черновики профилей .sb прямо в markdown (не в Sources/): запрет чтения globalStorage и state.vscdb Cursor, запись только в клон задачи, запрет .git/config, .git/hooks/, .git/info/, .kaban/, сетевой allowlist. Вариант «CLI вне песочницы, песочница на инструментах». Статус sandbox-exec на macOS 26 (deprecated, но работает?).
   * Готово, когда: есть профиль и список команд-проверок вида «должно упасть / должно пройти».
* ☐ T4. launchd + XPC (спайки 3 и 4). SMAppService.agent, Mach-сервис, XPCSession из SwiftUI, проверка подписи клиента, структура бандла, уведомления из агента в бандле.
   * Готово, когда: есть схема бандла, минимальный plist и список граблей со ссылками.
* ☐ T5. Developer ID и нотаризация (Xcode 26, арх. §13, M5). Сертификаты, hardened runtime без App Sandbox, entitlements, notarytool, stapler, подпись вложенного демона и KabanGitShim.
   * Готово, когда: есть пошаговый чек-лист для Артёма, что сделать в Apple Developer и Xcode в понедельник.

4. Что вернуть кроме PR
На каждую пачку задач (сессию работы) — один отчёт team2-report-YYYY-MM-DD.md. Кладите его в репозиторий в docs/team2/ (в одном из PR пачки или отдельным PR) или загружайте новым файлом в Drive kaban/docs. Существующие файлы на Drive не трогаем. Отчёт — главный способ передать контекст основной команде, поэтому пишите его так, чтобы бот без доступа к вашей переписке всё понял.


Шаблон (скопировать целиком):

5. Как основная команда примет работу
1. CEO-бот сверяет PR: база main, ветка team2/…, CI зелёный, в диффе только разрешённые папки (research/, examples/, tools/, docs/team2/, новые файлы в docs/), нет пересечений с PR #5 и PR Frontend.
2. CEO-бот читает отчёт и раздаёт его: резюме всей команде, issues и вопросы по владельцам (Architect, Backend, Frontend, Analyst, Designer). Research-файлы уходят в план понедельничных спайков на mbp.
3. Артём мержит то, что прошло сверку. Остальное возвращается с комментарием в PR.
4. После мержа CEO-бот отмечает задачи в этом чек-листе (☐ → ☑) и, если нужно, добавляет ссылки на результаты в документы основной команды (это делает основная команда, не team2).
