**3.9 Настройки проекта и git-политика.** Окно проекта делится по месту хранения (спека 1.5), подпись в шапке каждого раздела говорит, где живёт настройка **(подпись — предложение фронта)**.

*Проект · .kaban/ в репозитории (как в сайдбаре макетов v0.2.1; `main:.kaban/`, сохранение через «Сохранить» → `updatePipeline`, автокоммит):*
- Пайплайн и стадии (3.8).
- Рабочая копия: `warm_paths`, `on_create`.
- Права и git, по раскладке, подтверждённой дизайнером (`04-column-settings-git`, «Пресет проекта»; макеты v0.2.1: `03-project-git-presets.png`), арх. §8.4, спека UC-19, F28:
  - `GitPresetPicker` на уровне **проекта** (`git.preset: strict | standard | permissive`, по умолчанию «Стандартный»): у каждого пресета коротко «что можно агенту» и «кто коммитит»; у «Строгого» — «агент только читает: `status`, `diff`, `log`, `show`; коммитит демон один раз после зелёных гейтов и проверки результата, сообщение из резюме стадии (`summary`, пустое → `kaban: <стадия> <задача>`)»; у «Стандартного» и «Свободного» — «агент + страховочный коммит демона»; у «Свободного» ещё постоянная подпись: песочница и проверка результата работают всегда. Смена пресета действует с новых runs;
  - `GitCommandTable` (`Table`) проекта: команда, разрешено (`--pol-allow`) / запрещено (`--pol-deny`, **серый**, не красный) / при условии (`--pol-cond`), маркер «из пресета / переопределено» (`git.allow` / `git.deny` проекта поверх пресета); жёсткие инварианты — отдельные плитки с заштрихованным замком (`--pol-locked`), их не снимает ни один пресет и проект. Набор приходит данными: `EffectiveGitPolicy.hardInvariants: [String]` — стабильные id из `HardInvariant` (арх. v0.11.21 §8.2, §8.4). Демон всегда присылает все семь в каноническом порядке спеки v0.8.22 §1.5: `push`, `remote`, `config`, `tag`, `force`, `foreign_refs`, `kaban_dir` (`HardInvariant.all` в протокольном патче переупорядочен так же); клиент рисует плитки в порядке массива и не сортирует. Команде достаётся первый совпавший id (`push --force` → `push`, `branch -f` → `foreign_refs`) — это решает демон, клиент шаблонов не знает. При каноническом порядке проверки `checkout -f main`, `branch --force x` и `switch -C x --force` дают `force` (он стоит раньше `foreign_refs`); это тоже только на стороне демона (`KabanKit`, дифф бэкенда для PR #5, md5 71ce0637…, собран на патче 5a3c659f). Одна плитка на id (спека v0.8.22 §1.5): на плитке — короткая подпись из таблицы подписей §1.5 и значок ⓘ, по наведению или клику открывается стеклянный поповер с полным текстом правила из списка §1.5. Короткие подписи (точные тексты спеки): `push` — «Без push», `remote` — «Remotes не меняются», `config` — «Git config и hooks не меняются», `tag` — «Теги не трогаются», `force` — «Без принудительных флагов», `foreign_refs` — «`main` и чужие ветки не двигаются», `kaban_dir` — «`.kaban/` только для демона». Обе строки — тексты клиента по id (в протоколе приходит только id, полей подписи нет; где хранить, спека не говорит — кладём в локализацию приложения по ключу id) **(предложение фронта)**. Раскладка — компактная сетка по две плитки в ряд в каноническом порядке, и в 03, и в итоговой политике 04 (дизайнер): седьмая плитка одна в последнем ряду, длинная подпись переносится внутри плитки, ⓘ справа. Полные тексты в плане не дублируем (по спеке v0.8.22 §1.5: `force` — `--force*` на любой команде по префиксу, в том числе `rebase --force-rebase`; короткий `-f` закрыт только у `checkout`, `switch`, `add`, `rm`, `mv`, `clean`, `worktree`, `submodule`; любой `clean` без `-n` / `--dry-run` запрещён, включая `clean -i`; `config` — ещё и запись в `.git/config`, `.git/hooks/`, `.git/info/` клона (держит песочница, id тот же, новых id нет); свои git-вызовы в клоне демон делает с отключёнными hooks и fsmonitor (§1.5, арх. v0.11.21); `foreign_refs` теперь включает `branch -C`, `checkout -B`, `switch -C` и `main` в любой записи, а `notes` / `fetch` / `worktree` проверяет `/git/check`); неизвестный id — моноширинным, без подписи, без ⓘ и поповера (спека §1.5: «Незнакомый id показывается моноширинным, без подписи»); счётчик — по данным, число в клиенте не зашито. Под ними — подпись без плитки: «Слияние в `main` делает только демон». Других замков нет; строк `checkout main` / `rebase main` в таблице команд нет — это `foreign_refs`; `git.deny` / `allow` проекта и стадии их не показывают как настраиваемые, а валидатор отвечает на попытку `git_hard_invariant`;
  - `EffectivePolicyView` — итоговая политика каждой `agent`-стадии, как её посчитал демон (арх. v0.11.21 §8.4): на доске и в настройках проекта — из `StageSummary.gitPolicy` (`nil` у не-agent стадий — блок не показываем), в редакторе — из `PipelineDraftValidation.resolved` (3.8). Поля `EffectiveGitPolicy` (арх. v0.11.21 §8.4): `preset`, `allowed: [GitRule]`, `denied: [GitRule]`, `hardInvariants: [String]` (id из `HardInvariant`), `conditional: [ConditionalGitRule { returnReason, allowed: [GitRule] }]`, `committer: StageCommitter` (`daemon_only` — «Коммитит демон из резюме», `agent_with_safety_commit` — «Агент + страховочный коммит»), `readOnly`. Каждое правило — `GitRule { rule, source }`, `source: GitRuleSource?` ∈ `preset | project | stage` (`hard` из `GitRuleSource` убран в арх. v0.11.21); неизвестное значение декодируется как `nil`. Правила сопоставляются по префиксу слов (`restore` покрывает `restore --staged`, но не наоборот), и делает это только демон: разрешённое правило, покрытое любым `denied`, в `allowed` уже не попадает, а клиент правила между собой не сравнивает. Слой выбирает резолвер демона (арх. v0.11.21 §8.4, спека v0.8.22 UC-19): `source` — **последний слой, который изменил итог правила** (слои: пресет → проект → стадия); повтор того же решения слой не меняет. Запрет на любом слое сильнее разрешения: `extend` стадии не снимает `deny` проекта, пресеты только разрешают и ничего не запрещают. Поэтому итог «разрешено» меняет только первое разрешение, итог «запрещено» — только первый запрет. У `conditional` **всегда** `stage` (`when` бывает только у стадии); явно запрещённое правило в `conditional` не попадает. Примеры: пресет разрешает, стадия запрещает → `denied`, `source: stage`, «сужено»; проект запрещает, стадия разрешает → остаётся в `denied`, `source: project`, «унаследовано»; пресет разрешает, стадия повторяет `extend` → `allowed`, `source: preset`, «унаследовано». Условные расширения — отдельной строкой со своим `when: return_reason == <returnReason>` (как в макете `04-stage-git-overrides`), неизвестную причину показываем как есть. Клиент ничего не вычисляет. Метки (подтверждены дизайнером по макетам `03` и `04`): замок идёт не из `source`, а из `hardInvariants` — плитка с заштрихованным замком на каждый id, без текстовой метки «унаследовано / …»; `preset` / `project` — «унаследовано» (в редакторе стадии — «из проекта», 3.8); `stage` в `allowed` или `conditional` — «переопределено»; `stage` в `denied` — «сужено», а при `readOnly = true` — «сужено до чтения» (арх. v0.11.21 §8.4, спека v0.8.22 UC-19.3); `nil` — без метки. Пометок четыре — «унаследовано», «переопределено», «сужено», «сужено до чтения» (спека v0.8.22 UC-19.4). Явный `deny` в YAML read-only стадии тоже приходит с `source: stage` и показывается как «сужено до чтения» — так задумано (арх. v0.11.21 §8.4, спека UC-19.3). У read-only стадии всё, что разрешила политика проекта и что не чтение (`add`, `commit`, `restore --staged`, `stash`…), демон присылает в `denied` с `source: stage`; запреты проекта остаются с `source: project` («унаследовано»). «Нет в пресете (из каталога)» у неё — только команды, которых не было в политике проекта (например, `rebase`, `reset`). Команда вне `gitCommandCatalog`, которую read-only стадия перечислила в `extend` (например, `replace`), тоже приходит в `denied` с `source: stage` и показывается «сужено до чтения»; валидатор при этом даёт только предупреждение `git_unknown_command`, не `git_readonly_extend` (арх. v0.11.21 §8.4, спека v0.8.22 UC-19, 3.8). Клиент ничего не вычисляет: метка выбирается по `source` и `readOnly` политики стадии. Раскладка (подтверждена дизайнером): внутри каждой группы («Разрешено» / «По условию» / «Запрещено») правила с одним `source` собираются в одну строку с одной меткой — один `source`, одна строка, как в макете 04; группа «Жёсткие» — плитки по `hardInvariants`. В конце группы «Запрещено» — две серые строки без метки (макеты 03 / 04, перерисованы под арх. v0.11.10): «Нет в пресете (из каталога): <команды>» — команды из `PipelineSummary.gitCommandCatalog`, которых нет ни в `allowed`, ни в `denied` политики этой стадии (в макете — `reset`); «Всё вне каталога — запрещено» — постоянная подпись. В макете 04 в «Запрещено» так: `stash` — «сужено», `cherry-pick` («перенос чужих коммитов») — «унаследовано» (явный запрет проекта `deny: [cherry-pick]`), затем эти две строки; `restore --staged` остаётся разрешённым. Обе строки — только отображение готовых данных, без сопоставления правил на клиенте. Цвета меток (подтверждены дизайнером, как в макетах 03 / 04): «унаследовано» — серая, «переопределено» — синяя, «сужено» — фиолетовая. Разовые `git_grant` в политику не входят — они в панели задачи.
  - Колонка «Политика проекта» в редакторе стадии (`StageGitOverrides`, 3.8; дизайнер перерисовывает макеты 03 и 04, раздел 10). Данные (арх. v0.11.21 §8.4, вопрос 27 закрыт): строки — из `PipelineSummary.gitCommandCatalog: [String]` (каталог известных демону git-команд, по нему же валидатор даёт `git_unknown_command`), состояние проекта — из `PipelineSummary.projectGitPolicy: EffectiveGitPolicy?` (пресет + `allow` / `deny` проекта без стадий, `source` только `preset` / `project`); для черновика — те же поля в `PipelineDraftValidation.resolved`. Логика клиента — только отображение: **«Нет в пресете»** (серое) — команда есть в `gitCommandCatalog`, но её нет ни в `allowed`, ни в `denied` `projectGitPolicy`; стадия может разрешить её через `extend`, как `rebase`. **«Запрещено проектом»** — команда в `denied` с `source: project`: переключатель «Переопр.» выключен, подсказка «Запрет проекта стадия не снимает · Изменить в проекте» со ссылкой на вкладку git проекта. «Разрешено» — в `allowed` (`preset` / `project`). Совпадения по префиксу (`restore` против `restore --staged`) клиент не вычисляет: показывает правила так, как их отдал демон. Жёсткие — плитками по `projectGitPolicy.hardInvariants`. `projectGitPolicy = nil` (старый демон) — колонка не показывается.

*Проект · на этом Маке (как в сайдбаре макетов v0.2.1; локальная база демона, не в репозитории, сохраняется сразу, без «Сохранить» и автокоммита):*
- Общее: путь, `relinkProject`, базовая ветка, вес и личный максимум (`setProjectWeight`), маскот (`setMascot`), пауза.
- **Автор коммитов** (`GitIdentity { name, email }`; арх. v0.11.21 §5, §8.2; спека v0.8.22 UC-01; протокольный патч ceabd81d…; макет `06-add-project-identity`, нижняя часть). Автор хранится у демона на этом Маке, а не в `.kaban/` (спека v0.8.22 UC-01: «репозиторий общий, а автор у каждого свой»; арх. v0.11.21 §8.2), поэтому строка стоит в этой группе, сохраняется сразу и без автокоммита. Строка показывает текущие имя и почту из `ProjectSummary.identity: GitIdentity?` (снимок, `projectAdded` / `projectUpdated`; после `setProjectIdentity` строка обновляется по `projectUpdated`, без оптимистичной правки). `nil` бывает только у старого демона (арх. v0.11.21 §8.2, патч): тогда «—» (спека UC-01: «у старого демона «—»») и «Изменить…» с пустыми полями. «Изменить…» открывает поля «Имя» и «Почта», заполненные текущим `identity`, и шлёт `setProjectIdentity(projectId, identity)`; подпись «с новых коммитов» (действует с новых коммитов, уже сделанные не переписываются). Единственная ошибка по арх. и патчу — `identity_required` (ничего не изменено), с теми же проверками и текстами, что в листе «Добавить проект» (спека UC-01: «те же проверки и тексты, что ниже»; 3.10): общий текст «Не задан автор коммитов: укажите имя и почту». Этот вызов всегда несёт `identity`, поэтому ветки «первый отказ» (уточнения «В настройках git нашлось…», тексты «… в настройках git содержит служебные символы, укажите вручную») здесь не бывает — только «Отказ вызову с `identity`» спеки v0.8.22 UC-01: поля из `missing` и `invalid` сразу получают оранжевую обводку и текст под полем — `missing`: «Укажите имя» / «Укажите почту»; `invalid`: «Имя должно быть в одну строку, без служебных символов» / «Почта должна быть в одну строку, без служебных символов»; фокус — в первое такое поле (порядок «Имя», «Почта»); без ключей — только общий текст, оба поля без подсветки. В полях остаётся то, что ввёл пользователь (спека v0.8.24 UC-01). Других ошибок у `setProjectIdentity` арх. v0.11.21 не называет. Git клиент сам не читает.
- **MCP** — белый список проекта, хранится на Маке (`project_mcp_allow`, спека 1.5, UC-24.2), а не на уровне всего Мака и не в `.kaban/`: `listProjectMcpServers(projectId)` / `setProjectMcpAllowlist(projectId, servers)`. Список серверов проекта из `.cursor/mcp.json` и личных серверов Артёма из `~/.cursor/mcp.json`, у каждого переключатель, **по умолчанию выключен**. Сервер доски `kaban` всегда включён, переключатель заблокирован с подписью «нужен Kaban». Подпись внизу: «Список хранится только на этом Маке; конфиг MCP Kaban собирает сам на каждый запуск; лишний сервер в CLI — запуск не стартует». Если поднят `mcp_unexpected`, сверху строка «CLI видит сервер «<имя>» вне конфига Kaban». У выключаемого сервера, выбранного в стадиях, подпись «выбран в стадиях: Dev, Test» **(предложение фронта)**.

Глобальные настройки Мака (`Settings`, на все проекты): `setMaxConcurrentRuns`, путь к `cursor-agent`, уведомления о ревью (по умолчанию включены, спека UC-07; значение хранит приложение), вкладка «Квота Cursor» (3.13). Белого списка MCP здесь нет: он у каждого проекта свой (выше).

В рабочей FE-16 `listProjectMcpServers` читает оба JSON-конфига у демона и возвращает
только `[McpServerRef]`, без endpoint, команд, аргументов и секретов. Отсутствующий
файл даёт пустой источник; повреждённый, недоступный или symlink-конфиг — явный
`mcp_config_unreadable` с `params.source`. Ошибка не изображается пустым каталогом.
Одинаковое имя показано в обеих группах; разрешение хранится по имени, поэтому
оба переключателя отражают один подтверждённый факт.

`ProjectSummary.mcpAllowlist: [String]?` и `mcpIssue: McpPreflightIssue?` приходят
через snapshot / `projectUpdated`. `nil` allowlist означает неизвестные разрешения
старого производителя. `setProjectMcpAllowlist` атомарно записывает DB, journal и
receipt; `.ok` ожидает correlated event. Удалённое из каталогов разрешение показано
отдельно и удаляется только явным действием пользователя. Личные конфиги не пишутся.

`recheck(project)` перепроверяет папку и pipeline, но сохраняет MCP-блок до свежего
успешного preflight. Живой `cursor-agent mcp list` к этой команде ещё не подключён;
полная приёмка устранения unexpected через CLI остаётся открытой. Backend seam
`applyMCPPreflight` публикует диагностику и снятие блока; UI не вычисляет этот исход.
