**3.8 Настройки пайплайна и стадии.** Окно проекта → «Пайплайн»: список стадий с перестановкой, добавлением и удалением.
- Удаление стадии, где есть задачи в нетерминальном статусе, выключено с подсказкой «сначала перенесите N задач» (UC-13); валидатор демона отклонит его в любом случае.
- `StageEditorForm` — секции по таблице 1.5 спеки, неприменимые к `kind` скрыты. Отображение: имя, иконка, цвет, порядок, свёрнут, скрыт.
- Лимиты (спека v0.8.22 §1.3, §4.1). Подписи полей редактора и `{label}` в текстах ошибок берутся из одного источника — таблицы подписей `{label}` спеки §4.1:
  - на уровне пайплайна (`board`): «Общий лимит возвратов» (`bounce_limit_total`, по умолчанию 5), «Лимит задач в ожидании человека» (`max_waiting_human`, по умолчанию 3, на проект), «Лимит запусков на задачу» (`max_runs_per_task`, по умолчанию 12, только автоматические запуски) — умолчания по арх. §3.1;
  - у стадии: «Лимит возвратов (у пары, например «Test → Dev»)» — `returns_to.limit` agent-стадии (в поле — «Test → Dev: 3»); «Лимит возвратов при красном гейте» — `on_fail.limit` gate-стадии (по умолчанию 3); «Лимит возвратов при конфликте» — `on_conflict.limit` merge-стадии (по умолчанию 2);
  - длительности стадии (спека v0.8.22 §4.1): «Таймаут зависания» (`stall`, по умолчанию 10m), «Общий таймаут стадии» (`wall`, по умолчанию 60m), «Пауза перед повтором» (`backoff`, по умолчанию `[30s, 2m]`) — умолчания по арх. §3.1.
- `ModelPicker` у agent-стадии **обязателен**: список из `model_catalog` **без Auto**, сгруппирован по семействам, у каждой модели чип пула Cm/Om, у новой — «проверь пул». Модели по умолчанию нет. Кнопки «Переключить на Auto» и галочки автоподмены нет. Модель, пропавшая из `--list-models`, помечена `model_unavailable` (в протоколе — `model_flag · unavailable`), выбрать её нельзя.
- Git стадии (`StageGitOverrides`, арх. §8.4, спека UC-19.3; макеты v0.2.1: `04-stage-git-overrides.png`): своего пресета у стадии нет, редактор показывает **только переопределения** — в каждой строке значение проекта серым с меткой «из проекта» (колонка «Политика проекта» из `PipelineSummary.projectGitPolicy` и `gitCommandCatalog`: «Нет в пресете» / «Запрещено проектом», 3.9), переключатель «Переопр.», значение стадии и «↺ к проекту», вверху «Сбросить всё к проекту»; жёсткие правила заблокированы. Сверху — только для чтения строка «Пресет проекта: Стандартный» со ссылкой «Изменить в проекте» (3.9); ниже переопределения стадии `extend` / `deny` / `when` в той же `GitCommandTable` с маркерами «унаследовано / переопределено»; `when` действует только на `extend`, `deny` стадии действует всегда (арх. v0.11.21 §8.2), поэтому условие показывается только у строк «разрешить при условии», у запрета поля условия нет; read-only стадия показывает «сужено до чтения» поверх любого пресета. В «Строгом» подпись: «Агент не коммитит — коммит стадии делает демон из резюме (`summary`)». Под переопределениями — живое превью итоговой политики стадии (`EffectivePolicyView`, 3.9) из `PipelineDraftValidation.resolved` того же ответа `validatePipeline`: один ответ приносит `gitPolicy` стадий, `onFail` / `onConflict` и `defaultReturnStage` (арх. v0.11.21 §2, §8.4); клиент ничего не вычисляет. Если `resolved = nil` (только когда черновик не разобрался как YAML — `yaml_syntax` — или его корень не mapping; при прочих ошибках поле заполнено, арх. v0.11.21 §3.1), превью показывает последнее удачное состояние приглушённым и список ошибок **(предложение фронта)**.
- `StageMcpPicker` (`agent.mcp`, спека 1.5, UC-24): сервер доски отмечен всегда и не снимается, остальные выбираются только из белого списка проекта (вкладка «MCP», 3.9); по умолчанию у стадии только сервер доски. Сервер, выбранный у стадии, но выключенный в белом списке, — **предупреждение** валидатора (`ValidationIssue.severity = warning`, арх. §9), не ошибка: янтарная подсветка строки «Выключен в MCP проекта — не подключится», пайплайн остаётся валидным, «Сохранить» не блокируется, демон просто не кладёт сервер в конфиг запуска; ссылка «Открыть MCP проекта».

Сохранение (арх. §3.1, журнал решений):
1. Черновик живёт только в редакторе. Пока пользователь правит, проверка — только командой демона `validatePipeline(projectId, content)` с задержкой 300 мс (арх. v0.11.21 §2, §5): своей копии валидатора в приложении нет, `KabanKit` не импортируем. Результат — список `ValidationIssue` в ответе и эфемерное `pipelineDraftValidated(PipelineDraftValidation { projectId, contentHash, issues })`; ответ на устаревший черновик (другой `contentHash`) отбрасываем, без связи с демоном показываем «Проверка недоступна — нет связи с Kaban» и «Сохранить» выключаем **(предложение фронта)**; `ValidationIssue.path` подсвечивает поле, `ValidationIssue.stageId` — стадию в списке и её форму, цвет по `severity`: `error` — оранжевая обводка поля с меткой «ошибка» (правило макетов v0.2), `warning` — янтарная; красной обводки нет, красный — только для инцидентов безопасности. **«Сохранить» выключена, пока есть ошибки** (`severity = error`, включая agent-стадию без модели или с `auto`); предупреждения сохранению не мешают и показываются в списке над кнопкой. Коды: в `ValidationCode` (`KabanProtocol` + протокольный патч Архитектора) все 37 кодов (арх. v0.11.21, спека v0.8.22 §4.1). Текст для UI берём из словаря спеки v0.8.22 §4.1 по `code`. Подстановки (арх. v0.11.21, спека v0.8.22 §4.1): `{stage}` — имя стадии по `stageId`, `{path}` — `ValidationIssue.path`, все остальные ключи (`line`, `n`, `value`, `key`, `id`, `field`, `kind`, `harness`, `min`, `max`, `label`, `name`, `when`, `cmd`) — из `ValidationIssue.params: [String: String]` (нет поля — `[:]`). `{label}` приходит именем поля YAML и переводится в подпись по таблице подписей спеки v0.8.22 §4.1 (`bounce_limit_total`, `returns_to.limit`, `on_fail.limit`, `on_conflict.limit`, `max_waiting_human`, `max_runs_per_task`, `max_file_mb`), неизвестное имя — как есть; `{cmd}` в `git_unknown_command` — только первое слово правила. Длительности в `{min}` / `{max}` (спека v0.8.22 §4.1): «У `duration_out_of_range` `{min}` и `{max}` приходят строками длительности (`1s`, `1m`, `2h`). UI показывает их по-русски («1 с», «1 мин», «2 ч»), а незнакомый формат выводит как есть». Для этого в `KabanBoardCore` — маленькая чистая функция-форматтер с тестами: `<число>s` → «<число> с», `<число>m` → «<число> мин», `<число>h` → «<число> ч» (единицы — только те, что в синтаксисе длительностей арх. §3.1 и спеки: `s`, `m`, `h`); всё остальное, в том числе составные записи, — как пришло. Пример из спеки: «Таймаут зависания должен быть от 1 мин до 30 мин». Из черновика клиент ничего не достаёт и диапазонов не зашивает. Если для текста не хватает хотя бы одного ключа (например, старый демон с `params = [:]`), показываем `message` как есть; неизвестный код — `message` плюс код моноширинным. `params` заполняет бэкенд в PR #5. Ошибка или предупреждение определяется **только** `severity`, не кодом (арх. v0.11.21): `error` — оранжевая обводка и «Сохранить» выключена, `warning` — янтарная подсветка без оранжевой обводки, сохранению не мешает. Код `git_readonly_extend` (`ValidationCode.gitReadonlyExtend`, протокольный патч b8607e6f…; арх. v0.11.21, спека v0.8.22 UC-19, §4.1) — ошибка (`severity: error`): read-only стадия разрешает в `git.extend` известную пишущую команду из `gitCommandCatalog`, в том числе с `when` (спека v0.8.22 §4.1); `path` — `stages[i].git.extend[j]`, есть `stageId`, `params.cmd` — первое слово правила. Обрабатывается как остальные ошибки `ValidationIssue`: «Сохранить» выключена, стадия подсвечивается по `stageId`, строка `extend` в редакторе стадии (3.8, `StageGitOverrides`) — по `path` оранжевой обводкой; текст из спеки v0.8.22 §4.1 — «Стадия «{stage}» только читает: `{cmd}` разрешить нельзя» (имя стадии в «ёлочках», как у соседних кодов) (`{stage}` — имя стадии по `stageId`, `{cmd}` — из `params`), без ключа — `message`. Команда вне `gitCommandCatalog` в `extend` read-only стадии (арх. v0.11.21 §8.4: «вне каталога — не значит не пишет: `replace`, `gc`, `prune`») даёт **только** `git_unknown_command` — предупреждение, одно сообщение на строку, без `git_readonly_extend` (арх. v0.11.21 §8.4, спека v0.8.22 UC-19, §4.1): строка `extend` подсвечивается янтарным, «Сохранить» не блокируется, а в превью итоговой политики (`PipelineDraftValidation.resolved`) резолвер кладёт команду в `denied` с `source: stage`, и `EffectivePolicyView` показывает её «сужено до чтения» (3.9); в `allowed` она не попадает никогда, клиент ничего не вычисляет. Это не `readonly_violation`: тот — причина `retry_wait` (стадия изменила файлы во время запуска, 3.4), коды не пересекаются и не переиспользуются. Обычно предупреждением приходят четыре кода: `unknown_key`, `mcp_not_allowlisted`, `git_unknown_command` и `field_not_allowed_for_kind` для `wip` (подтверждено аналитиком, спека v0.8.22 §4.1). `unknown_stage` — только ссылка на id, которого нет в пайплайне. `no_return_target` (`ValidationCode.noReturnTarget`): у стадии с возвратом нет подходящей цели (у gate — `on_fail` без `stage`, а раньше по цепочке `on_success` нет `agent`-стадии с `readOnly = false`) **или** явная цель возврата (`returns_to`, `on_fail.stage`, `on_conflict.stage`) — read-only стадия или вообще не `agent`-стадия (арх. v0.11.21 §3.1, спека v0.8.22 §1.3, §4.1). Без `stageId` код приходит только для `requestChanges` (в пайплайне есть `human`-, `gate`- или `merge`-стадия, а `agent`-стадии с `readOnly = false` нет): подсвечиваем не стадию, а список ошибок уровня пайплайна, текст «Некуда вернуть: нет стадии, которая правит код» (§4.1). `stageId` — стадия, которой принадлежит этот возврат (agent, gate или merge), а не всегда gate. Эта стадия подсвечивается в списке тем же механизмом, что и остальные ошибки со `stageId`, а в её форме оранжевой обводкой — поле «Куда возвращать» (`returns_to` / `on_fail.stage` / `on_conflict.stage`) **(предложение фронта)**. В выборе цели этого поля read-only стадии не предлагаем. Коды валидации — только `ValidationCode` в `KabanProtocol`. Код придёт с протокольным PR (после PR #2).
2. «Сохранить» → атомарная запись файла + `updatePipeline(projectId, contentHash)`; список `ValidationIssue` из ответа — вторая проверка. Некорректная версия в `main` не попадает. Если демон отклонил версию, черновик остаётся в редакторе с ошибками, а файл на диске возвращаем к прежнему содержимому **(предложение фронта)**.
3. Ручная правка файла приходит эфемерным состоянием: баннер «Есть незакоммиченные правки пайплайна» с результатом проверки и кнопкой «Применить».

Если файл изменился на диске при открытом черновике — «Перезагрузить / Перезаписать» **(предложение фронта)**.

## Реализация FE-13

Рабочий контракт — `getPipelineSource`, `validatePipelineDraft`, затем
`updatePipeline` с тем же точным draft. Один editor на проект разделяет committed
source, working file и локальный текст; формы меняют только адресованные диапазоны.
Anchors/сложные конструкции и добавление целей возврата доступны в YAML без
пересериализации. Debounce — 300 мс; project/base/hash/session/generation проверяются
до принятия ответа. Семантика pipeline и resolved policy приходят от службы.

Перед apply editor перечитывает source, координирует атомарную запись, повторно
сверяет bytes и отправляет strict draft. Отказ сохраняет draft и рабочий файл
неприменёнными; предложение отката выше не используется, чтобы сохранить поздний
внешний edit. Сравнение нового YAML, выбор новой базы с сохранением ввода и
перезагрузка с подтверждением — отдельные действия. `.ok` не подтверждает apply.

В рабочих FE-14–16 каталог моделей, git/workspace/files и MCP picker подключены
к тому же точному draft. MCP picker сохраняет выключенный выбранный сервер,
разрешает добавить только имя из подтверждённого allowlist и найденного каталога,
а `kaban` не снимается. `StageSummary.mcp` содержит выбор, `effectiveMcp` — набор
по разрешениям, рассчитанный тем же backend фильтром, что и preflight. Отсутствующие
поля старого демона означают неизвестность. Смена allowlist требует новой серверной
проверки draft; старый preview не разрешает apply. Переход в MCP проекта сохраняет
черновик, стадию и раздел. [Базовый редактор и настоящие окна](../development/frontend-fe-13-2026-10-08.md).
