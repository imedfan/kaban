# Kaban: Доска и карточки

Требования выделены из frontend-plan v0.5.37 без изменения поведения.
Статус реализации — [current-state](../current-state.md); порядок работы — [frontend-plan](../frontend-plan-v0.md).
Имена DTO и команд сверять с `Sources/KabanProtocol/`; числовые ссылки 3.x сохранены из исходного плана.
Предложения фронта остаются предложениями. Макеты и токены — [design](../../design/README.md).

## 3. Экраны и ключевые компоненты

Общего «Журнала» в MVP нет: историю показывает лента задачи. Каркас по макету `01-board`: `NavigationSplitView` (сайдбар: Доска / Ждут человека / Инциденты со счётчиком (F22), список проектов с маскотом и значками «ждёт человека» / инцидент, откуда проект перетаскивают на доску (3.10), блок «Этот Мак» с потолком процессов, весами и полосами квоты Cm/Om, 3.13) | доска | `.inspector` с панелью задачи.

Liquid Glass: `.glassEffect()` на шапках столбцов (один `GlassEffectContainer` на дорожку), системный тулбар, панель задачи. Карточки сплошные (`--bg-card`, радиус 10).

**3.1 Флаги планировщика — в шапках (арх. §3.2).** Задачи под флагом остаются `queued` и выглядят как обычная очередь. Исключение по журналу решений: задача, которая ждёт квоту, стоит в `queued` **с причиной**, и карточка показывает её спокойной серой строкой (3.4). Красный цвет — только для инцидентов безопасности; флаги доступности и моделей — янтарные.

| Флаг · причина | Где | Текст и действие |
|---|---|---|
| Мак `paused` · `manual` | `SchedulerBanner` над доской | «Все запуски на паузе», «Продолжить» → `resumeAll` |
| Мак `rate_limited` | `SchedulerBanner` | «Лимит Cursor, возобновление в 16:40», «Снять сейчас» → `resumeAfterRateLimit` |
| Пул `usage_exhausted` · `cm` / `om` | `PoolBanner` над доской, тонкий, по одному на пул (янтарный); метка на шапках столбцов, чьи стадии на моделях этого пула | «Om исчерпан до 14.08 · N стадий» (спека UC-09 б; до `billingCycleEnd` или даты из текста ошибки); встают только стадии этого пула, остальные работают; «Сменить модель» (явная модель из другого пула, 3.8) |
| Мак `usage_exhausted` · `unknown` (пул не определить) | `SchedulerBanner` (янтарный), весь Мак | «Квота Cursor исчерпана до 14.08» (спека UC-09 б); дата неизвестна — «Сброс неизвестен, проверка раз в 6 ч» |
| Мак `runner_unavailable` · `agent_missing` / `agent_not_runnable` / `agent_not_logged_in` / `runner_auth` | `SchedulerBanner` (янтарный) | «Cursor недоступен: не найден / не запускается / не выполнен вход / ошибка авторизации», «Проверить снова» → `recheck(.runner)`; подсказка «выполните `cursor-agent login` в Терминале» |
| Модель `model_flag` · `unavailable` | `ModelBanner` над доской, по одному на модель; метка на шапках столбцов с этой моделью | «Opus недоступен · N стадий» (пропал из `--list-models` или `resource_exhausted`), «Сменить модель»; снимается пробой, появлением в каталоге или `clearModelFlag` |
| Модель `model_flag` · `substituted` | `ModelBanner`, по одному на модель | «Cursor подменяет <модель> · N стадий» (считаем стадии, как у пулов и `unavailable`), «Сменить модель» (тот же список, что в редакторе, 3.8), «Снять флаг» (`clearModelFlag`) |
| Проект `paused` · `manual` | `LaneHeader` | «Проект на паузе», «Продолжить» → `resumeProject` |
| Проект `intake_paused` · `max_waiting_human` | `LaneHeader` | «3/3 ждут человека — новые задачи из Backlog не берутся» |
| Проект `unavailable` · `project_missing` / `no_pipeline` / `pipeline_invalid` | `LaneHeader` | «Папка не найдена» («Указать путь» → `relinkProject`, «Удалить» → `removeProject`), «Нет пайплайна» («Создать шаблон…»: UI пишет шаблон и вызывает `updatePipeline`), «Пайплайн невалиден» (список `ValidationIssue`, «Открыть настройки»); при `no_return_target` — та же янтарная плашка «Пайплайн не запустится», что и при нехватке моделей (3.7); если не хватает моделей — янтарная плашка «Пайплайн не запустится: нет модели у Dev, Test» с кнопкой «Указать модели» (редактор на первой стадии с ошибкой) и меткой на шапках этих столбцов; задачи в Backlog создавать можно; везде «Проверить снова» → `recheck(.project(id))` |
| Проект `unavailable` · `mcp_unexpected` | `LaneHeader` (янтарный) | «Запуск не стартовал: CLI видит лишний MCP-сервер «<имя>»», «Открыть MCP» (3.9), «Проверить снова» |
| Проект `merge_blocked` · `main_dirty` | `LaneHeader` + карточка головы очереди | «Слияние ждёт: в `main` есть ваши правки, пересекающиеся с входящими» |

`LaneHeader` есть у каждой дорожки, даже если на доске один проект: в нём крестик «Убрать с доски» (3.10). Несколько флагов одновременно — один баннер со списком, порядок: `runner_unavailable` > `usage_exhausted · unknown` > `rate_limited` > `paused`, баннеры пулов и моделей — отдельными тонкими строками ниже **(предложение фронта)**.

**3.2 Дорожка проекта.** `BoardView` — горизонтальный `ScrollView` из `StageColumnView` с `LazyVStack`. `StageColumnHeader` (glass): иконка, имя, WIP «4/3» (UC-13) — только из `wipUsed` / `wipLimit` стадии: в снимке — `stageLoad`, между снимками — журнальное событие `stageLoadChanged`, которое демон шлёт в той же транзакции, что и `taskUpdated` (арх. v0.11.21 §3.2, §5; ответ Архитектора, подтвердил CEO). Проекция доски обновляет загрузку стадии по `stageLoadChanged` и сама её не считает. Сам UI WIP не считает: правило «кто занимает слот» живёт в протоколе (`occupiesWIP(in: StageKind)` вместо `TaskStatus.occupiesWIP`), в `human`-стадии слот занимают все задачи, кроме `queued`. Если `stageLoad` в снимке нет (старый демон), счётчик скрыт, запасного подсчёта на клиенте нет. В `KindGroupedBoardView` счётчика нет **(предложение фронта)**; свёрнутость по `display.collapsed`. `kind: gate` — тонкая `GateStripView` со счётчиком, раскрывается по клику. Стадии с `hidden` не рисуются, их задачи доступны через фильтр «скрытые стадии» **(предложение фронта)**.

**3.3 Дорожки и компактный вид.**
- `SwimlanesView`: `LazyVStack(pinnedViews: .sectionHeaders)`, `Section` на проект, закреплённый `LaneHeader` (маскот, ветка, вес, процессы, паузы, сворачивание, кнопка настроек и сразу после неё крестик «Убрать с доски»). Дорожки идут в порядке `BoardSetStore`. Внутри дорожки свой горизонтальный скролл. Высота ограничена, столбцы прокручиваются внутри; свёрнутая дорожка — одна строка сводки **(предложение фронта)**.
- `KindGroupedBoardView` (по проектам с доски): очередь / в работе агентов / ждёт человека / слияние / готово. На карточке `StageChip` с исходной стадией. Любая `waiting_human` (включая `review`) попадает в «ждёт человека» (арх. §11).
- Общие столбцы без дорожек — только при совпадении `id` стадий.

**3.4 Карточка: статусы §3.2 → визуал.** Анатомия по `02-cards`: наклейка маскота + id, заголовок до 2 строк, ряд бейджей, статус-строка (значок + текст + мета), фактура левого края по проекту. Цвет живёт только в статус-строке и рамке, всегда вместе со значком и текстом.

| status · reason | Статус-строка (токен) | Карточка и быстрые действия |
|---|---|---|
| `queued` | «В очереди #2» (`--st-queued`); «Ждёт места» (`queued: wip_full`) — нейтральный серый вид (`--st-queued`, без янтаря): задача стоит **в столбце той стадии, слота которой ждёт** (например, Human Review), а не в предыдущей (арх. v0.11.21); проекция кладёт карточку по `stageId`, как любую другую; «Ждёт процесс» при занятом потолке Мака (как в `02-cards`); `quota_cm` / `quota_om` (ниже порога или пул исчерпан) — серая причина «Ждёт квоту Om · сброс через N д»; `model_flag` — «Ждёт модель: Opus недоступен»; с такими причинами очередь не держит, слот не занимает | маркер «↑ первым» для `returned`/`answered`; без критериев приёмки — «не запустится» (UC-02; по `TaskCard.hasAcceptanceCriteria`, малый PR, раздел 8) |
| `running` | «Работает 12 мин» (`--st-running`), чип модели | строка «последнее действие: <текст `report_progress`>»; тонкая полоса «прошло / wall-таймаут» **(предложение фронта, вопрос 1)** |
| `gating` | «Гейты: swift test 2/3» (`--st-gating`); в Merge «Rebase + гейты» | в проекте со «Строгим» после зелёных гейтов мета «коммит сделает Kaban» (агент не коммитит, арх. §6.3) **(текст — предложение фронта)** |
| `retry_wait` · `crash` / `stall_timeout` / `wall_timeout` / `no_final_call` / `gate_failed` | «Повтор 2/3 через 1:30» (`--st-retry`) + причина словами; `gate_failed` — красные гейты `agent`-стадии после `complete_stage`: `retry_wait: gate_failed`, попытка списывается, повтор в том же клоне; красная `gate`-стадия на месте **не** повторяется и попытку не тратит, а возвращает задачу по `on_fail` (счётчик пары и «Всего возвратов» растут; арх. v0.11.21 §3.1, §3.3), карточка gate-стадии `retry_wait` не показывает; счётчик попыток — в пределах текущего захода в стадию; 3 попытки, паузы `[30s, 2m]` (утверждено 4 октября) | отсчёт `TimelineView` раз в секунду, только у видимых; после `gate_failed` / `no_final_call` подпись «продолжит в том же клоне, вывод гейта уйдёт в промпт»; после `crash` / `stall_timeout` в «Попытках» ссылка на `refs/kaban/wip/<run-id>` |

| `retry_wait` · `daemon_restart` | «Повтор после перезапуска» | попытка не списана |
| `retry_wait` · `silent_exit` | «Проверяем модель» (`--st-retry`) | попытка не списана, ждёт пробного запуска; если проба прошла чисто, попытка списывается задним числом |
| `retry_wait` · `readonly_violation` | «Read-only стадия изменила файлы · повтор через 30 с» (вторая пауза — «через 2 мин»), `--st-retry`, отсчёт как у `gate_failed` | первое нарушение за заход: изменения откатаны, в промпт добавлено замечание, попытка **списывается**, паузы как у `gate_failed` (`[30s, 2m]`); второе нарушение за тот же заход — сразу `waiting_human: invalid_result`, даже если попытки остались (арх. v0.11.21 §3.2, §6.1; спека UC-04) |

| `waiting_human` · `review` | «На ревью» (`--st-review`), diffstat «+128 −40» | открыть Human Review; чип «после конфликта», если был |
| `waiting_human` · `retries_exhausted` | «Попытки исчерпаны 3/3» | «Перезапустить» (`retryStage`), «Модель» (`setModelOverride`, только явная модель из каталога) |
| `waiting_human` · `run_limit` | «Лимит запусков на задачу, 12 из 12» (спека v0.8.22 §1.3; в модели — заголовок «Лимит запусков на задачу» и уточнение «12 из 12», на карточке слева и справа, в ленте «Лимит запусков на задачу · 12 из 12» по правилу спеки §1.3; `max_runs_per_task`, считаются только автоматические запуски, списывающие попытку) | «Замечание агенту», «Перезапустить», «Модель»; любое действие человека обнуляет счётчик |
| `waiting_human` · `model_substituted` | «Подмена: <запрошена> → <ответила>» (янтарный, `--st-waiting`) | «Повторить», «Другая модель», «В Backlog»; результат не принят, попытка не списана |
| `waiting_human` · `bounce_limit` / `conflict_limit` | янтарный (`--st-waiting`), не красный. Причина лимита по спеке v0.8.22 §1.3 состоит из двух частей — заголовок и уточнение, разделитель — дело вёрстки; в модели вида — `LimitReasonText { title, qualifier }` в `KabanBoardCore`: на карточке заголовок слева, уточнение справа, в ленте одна строка через « · » («Лимит возвратов · при конфликте, 2 из 2»). Пара `returns_to` — «<откуда> → <куда>, N из M», имена стадий из пайплайна («Test → Dev, 3 из 3», «AI Review → Dev, 2 из 2»). Заголовок «Лимит возвратов», уточнение — какой лимит сработал (точные тексты спеки v0.8.22 §1.3, в тех же словах, что подписи полей в §4.1): «общий, 5 из 5» (`board.bounce_limit_total`), «Test → Dev, 3 из 3» (`returns_to` agent-стадии), «при красном гейте, 3 из 3» (`on_fail.limit` gate-стадии; блок `on_fail` необязателен, по умолчанию `limit = 3`) или «при конфликте, 2 из 2» (`on_conflict.limit` merge-стадии, причина `conflict_limit`); то же на карточке и в ленте; в подсказке — откуда лимит (арх. v0.11.21). | `waiting_human` · `git_denials` | «Политика git: 5 отказов» | «Разрешения…», «Политика…» |
| `waiting_human` · `suspicious_files` | «Подозрительные файлы: 2» (`--st-suspicious*` — алиасы `--st-waiting*`, янтарный; значок SF Symbol `exclamationmark.shield`, у остальных `waiting_human` — `hand`, у `review` — `usercheck`) — не инцидент, не красный (3.5; макеты v0.2.1, `01-cards-suspicious.png`) | под заголовком (по анатомии карточки, как строка подмены модели; макет v0.2.1) до двух строк: короткое имя файла и пометка правила по спеке v0.8.22 UC-25.4 — «`.env.local` · по шаблону `.env*`» (`rule: pattern`, `pattern`), «`dump.sql` · больше 5 МБ» (`rule: size`; число — фактический порог `suspicious_files.max_file_mb` из пайплайна, размер из `sizeBytes` — в панели); слов «похоже на секрет» нет: шаблон проекта может ловить и не секреты, остальное «+N»; бейджей не добавляет; в Merge — серая строка «перед слиянием»; всё из `TaskCard.suspiciousFiles` — полный `SuspiciousFile {path, rule, pattern?, sizeBytes, isText, blob}` (снимок и `taskUpdated`, переживает перезапуск и `resyncRequired`); «Открыть файлы» → блок решения в панели; попытка не списана |
| `waiting_human` · `invalid_result` | «Read-only стадия изменила файлы» (второе нарушение за заход, независимо от оставшихся попыток; арх. v0.11.21 §6.1) | «Перезапустить», «Модель» |
| `waiting_human` · `incident` | «Инцидент · refs откатаны» (заливка `--st-incident`) | красная рамка на всю карточку поверх всех бейджей |
| `paused` | «Пауза» (`--st-paused`) | «Продолжить» (`resumeTask`) |
| `blocked` · `main_dirty` | «main грязная» (`--st-blocked`), только у головы очереди слияния | подсказка с пересекающимися файлами; повтор сам; флаг `merge_blocked` в `LaneHeader` |
| `done` / `cancelled` | «Готово 14:05 → main» (`--st-done`) / «Отменена» (`--st-cancelled`), заголовок зачёркнут | — |

**Бейджи (не статусы):** возвраты по причинам из `bounceByReason` («↩ Test→Dev 2/3», конфликт «1/2» в `--st-conflict`), пересечение файлов (подсказка: с какими задачами), неиспользованное git-разрешение (ключ, `--pol-cond`), переопределённая модель. Порядок по `02-cards`: видно два бейджа, остальное «+N»; приоритет: git-разрешение > возвраты и конфликт > пересечение > модель и прочее.

Контекстное меню карточки дублирует drag для клавиатуры и VoiceOver: «Переместить в ▸» (`moveTask`), «Приоритет ▸» (`setPriority`), «Пауза» (`pauseTask`), «Отменить…» (`cancelTask`, диалог с «Сохранить ветку»).
