# Kaban: спайки бэка 1, 2, 6 (запуск на Маке `mbp`)

Скрипты отвечают на вопросы §14 архитектуры (v0.10.2): как `cursor-agent` ведёт себя без головы (спайк 1), как подключить MCP-сервер доски к запуску (спайк 2), какой нужен профиль Seatbelt и сколько стоят клоны (спайк 6). Агент здесь только запускает скрипты, итоги читает человек и бэкенд.

## Перед запуском (5 минут)

1. **macOS 26, Apple Silicon.** Запускать из **Terminal.app**, а не из встроенного терминала Cursor: там другие переменные окружения (например, `CURSOR_AGENT=1`) и другой контекст разрешений macOS.
2. **Xcode Command Line Tools**: `xcode-select --install`, если ещё не стоят. Отсюда берутся `python3`, `git`, `make`, `cc`. `swift` (Xcode или CLT) нужен для проверки сборки, без него проверка пропускается.
3. **`cursor-agent` установлен, и ты в него вошёл сам**: `cursor-agent login`, затем `cursor-agent status`. Ключи и токены скриптам не нужны и в чат не нужны.
4. **Дешёвая модель.** Смотрим `cursor-agent --list-models` и берём самую дешёвую явную модель (не `auto`), например из семейства mini/composer. Её `id` (левая колонка) передаём в `KABAN_SPIKE_MODEL`.
5. Cursor IDE не обязателен. Если он стоит, проверяется ещё чтение `state.vscdb`, но только число записей, без значений.

## Одна команда

```bash
cd spikes/backend
KABAN_SPIKE_MODEL=<id-дешёвой-модели> ./run-all.sh
```

Дополнительные переменные (все необязательные):

| Переменная | Зачем |
|---|---|
| `KABAN_SPIKE_REPO=~/path/to/repo` | реальный репозиторий для замеров `git clone --local` и `cp -c` в спайке 6. Его только читаем, клоны создаются во временном каталоге. По умолчанию генерируется репозиторий на 2000 файлов |
| `KABAN_SPIKE_WARM=node_modules,.build` | какие `warm_paths` мерить. По умолчанию ищем `node_modules`, `.build`, `DerivedData`, `build`, `Pods`, `target`, `.venv` |
| `KABAN_SPIKE_ONLY="1 6"` | запустить только часть спайков |
| `KABAN_SPIKE_TIMEOUT=240` | таймаут одного запуска агента в секундах |
| `KABAN_CURSOR_AGENT=/path/to/cursor-agent` | если CLI не находится в `PATH` |
| `KABAN_SPIKE_KEEP_TMP=1` | не удалять временные каталоги (для разбора) |

Каждый спайк можно запустить и отдельно: `KABAN_SPIKE_MODEL=… ./spike2-mcp.sh`.

**Длительность:** обычно 25–40 минут. Спайк 1 занимает 10–15 минут: в нём ожидание LaunchAgent и тест SIGTERM с паузой 30 секунд. Спайк 2 занимает около 10 минут. Спайк 6 занимает 10–15 минут, а первая `swift build` может добавить ещё несколько.
**Квота:** около 20 коротких запусков дешёвой модели. Промпты в одну-две строки, один-три вызова инструментов на запуск: спайк 1 делает ~8 запусков, спайк 2 — 5–8, спайк 6 — 3–6. Один запуск без `--model` идёт на Auto: так мы фиксируем, что CLI пишет в `init.model`.

**Что может всплыть на экране**
- Уведомление «Добавлен фоновый объект» или запрос Keychain «cursor-agent хочет использовать…» во время шага 13 спайка 1 (временный LaunchAgent). Запиши дословно, что спросили. Для Keychain нажми «Разрешить» (не «Разрешать всегда»), любой другой запрос отклоняй. Нам важен сам факт запроса.
- Если в спайке 1 shell-команда без `--force` ждёт подтверждения, запуск просто дойдёт до таймаута. Это тоже ответ.

## Что прислать

- `out/kaban-spikes-<время>.zip`. Внутри сводный `REPORT-<время>.md`, сырые выводы и фикстуры.
- Перед отправкой открой `REPORT-*.md` и допиши ответы на строки 👀: про системные запросы, где токен CLI, формат `mcp list`.

Секретов в архиве нет:
- токены, ключи и значения из БД скрипты не печатают и не сохраняют;
- Keychain читается через `security dump-keychain` **без `-d`**, и из вывода берутся только элементы с «cursor» в атрибутах: класс, `svce` и `labl`, а `acct` скрыт;
- по `state.vscdb` делается только `count(*)` в режиме read-only;
- в конце весь `out/` проходит через `scrub`: JWT, `Bearer …`, `key_…`, секреты в URL и почта заменяются на `<redacted>`;
- тестовый токен MCP случайный и живёт только в env на время прогона.

## Что проверяет каждый скрипт и на какие вопросы архитектуры отвечает

### `spike1-cursor-agent.sh`: cursor-agent headless (§6.1, §6.2, §6.4, §7, §9, §13)

### `spike2-mcp.sh` + `mcp_stub_server.py`: MCP доски из клона (§9)

Поднимаются две заглушки на 127.0.0.1 со случайными портами. «Доска» требует `Bearer`, сервер «проекта» работает без авторизации. Каждый запрос пишется в `stub-*.jsonl`: метод, инструмент, совпал ли `Bearer`, сам токен не пишется.

| Проверка | Вопрос |
|---|---|
| (a) `.cursor/mcp.json` в клоне с `"Authorization": "Bearer ${env:KABAN_RUN_TOKEN}"`: `mcp list`, `mcp list-tools`, запуск без `KABAN_RUN_TOKEN` | подхватывается ли конфиг, подставляется ли env, что видно при пустой переменной |
| (a) `-p` без `--approve-mcps`, с ним, `--approve-mcps` без `--force`, повтор без флага | нужен ли `--approve-mcps`, могут ли read-only стадии вызвать `complete_stage`, сохраняется ли одобрение |
| (b) отдельный `HOME` с `~/.cursor/mcp.json`, `CURSOR_CONFIG_DIR`, `mcp.json` в родительском каталоге клона, флаги из `--help` | подключение доски **без записи в репозиторий** |
| (c) в проекте закоммичен `.cursor/mcp.json` с чужим сервером: `mcp list`, подключит ли его `--approve-mcps`, подмена файла демоном и возврат через `git checkout main -- .cursor/mcp.json` | fail closed и подмена конфига (§8.2 п.4, §9) |
| (d) сырые выводы `mcp list` → `mcp-list-formats.txt`, есть ли машинный формат | парсер для fail closed |
| имена файлов, которые CLI поменял в `~/.cursor` | где CLI хранит одобрения MCP |

### `capture-run.sh`: фикстуры лимитов для фейкового драйвера (§6.4)

Три реальных лимитных случая скриптом не вызвать. Когда такой случай случится в обычной работе, повтори тот же запуск через обёртку:

```bash
./capture-run.sh usage-exhausted        -- --model <id> --force "Reply OK"   # месячная квота кончилась
./capture-run.sh resource-exhausted     -- --model <id> --force "Reply OK"   # «Generating…» и тихий выход
./capture-run.sh peak-throttle          -- --model <id> "Reply OK"           # троттлинг в пик
```

Обёртка сама добавит `-p --output-format stream-json`, если их нет, и запустит CLI во временном git-репозитории. Если в `--help` есть флаг отладки (`--debug`, `--verbose`, `--log-file`), он тоже включается, а `--no-debug` его отключает. Результат появится в `out/fixtures/<имя>/`: `stream.jsonl`, `stderr.txt`, `exit_code`, `times.jsonl` (время каждой строки, видно «тишину» перед выходом), `meta.json`, `summary.json`, `limit-hits.txt`, `context.txt` (версия, логин, каталог моделей до и после, подсказка классификатору). Имена логов CLI, изменённых за время запуска, пишутся в `new-log-files.txt`. Содержимое логов копируется только при `KABAN_CAPTURE_COPY_LOGS=1` и тоже проходит маскирование.

## Правила безопасности (соблюдаются всеми скриптами)

- Всё временное создаётся через `mktemp` в `/tmp/kaban-spike-*` или `~/.kaban-spike6.*` и удаляется в конце, остаётся только `out/`.
- Твои репозитории, `~/.cursor`, `~/.gitconfig` и файлы Cursor IDE скрипты не меняют. `KABAN_SPIKE_REPO` только читается. Наши git-команды идут без глобального конфига (`GIT_CONFIG_GLOBAL=/dev/null`, без подписи и хуков).
- Сам `cursor-agent` по ходу работы пишет свои служебные файлы: чаты временных репозиториев появятся в `cursor-agent ls`, одобрения MCP — в его каталоге. Сборка Swift пишет свой кэш в `~/Library/Caches/org.swift.swiftpm`. Эти записи делают сами CLI и SwiftPM, скрипты их не правят.
- Временный LaunchAgent загружается из временного plist (`launchctl bootstrap gui/<uid>`) и выгружается (`bootout`) сразу после проверки, а также при любом выходе из скрипта. В `~/Library/LaunchAgents` ничего не кладётся.
- Каждый вызов `cursor-agent` идёт со своим таймаутом. Он запускается в своей группе процессов, и по таймауту группа получает SIGTERM, затем SIGKILL.
- `security dump-keychain` вызывается только **без `-d`**, `security find-generic-password` — без `-g` и `-w`.

## Что спайки не покрывают

- `GetCurrentPeriodUsage` и поле `billingCycleStart` (§7, §14 п.1). Для этой проверки нужно использовать токен, поэтому её стоит делать отдельным решением и отдельным скриптом с явным согласием.
- Спайки 3, 4 и 5 (`SMAppService` и XPC, уведомления, мини-конвейер).
- Профиль deny-default (как у Codex CLI). В спайке используется `(allow default)` с точечными запретами. Следующий шаг — сузить профиль, когда известен список из `kaban-agent.final.sb`.

## Для разработчика скриптов

- `./selftest-mcp-stub.sh` проверяет заглушку через curl, Мак не нужен.
- `KABAN_SPIKE_SELFTEST=1` вместе с `KABAN_CURSOR_AGENT=<фейковый агент>` прогоняет логику скриптов на Linux. Так скрипты проверены перед отправкой. На Маке эту переменную не ставить.
